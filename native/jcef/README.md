# Контексты запросов JCEF

`request-context-settings.patch` применяется к Java-CEF
`17e805ad387d89839fdd2b864466b6510b2a783c` с CEF
`152.0.6+g708dc14+chromium-152.0.7977.83`. Версии и SHA-256 патча закреплены
в `source-lock.json`. Для изменённых файлов сохраняется upstream-лицензия BSD.

Патч добавляет все пять полей настроек контекста CEF 152 и создание контекста
с общим хранилищем. Каждой вкладке нужен **отдельный Java-wrapper**, созданный
из опорного контекста профиля: JCEF освобождает wrapper браузера при закрытии.
Передавать один wrapper нескольким браузерам нельзя. Опорный контекст должен
освобождаться после завершения callbacks закрытия всех браузеров профиля.

## Воспроизводимая сборка

Нужны чистый checkout указанного SHA с submodules, JDK 21, CMake и платформенный
C++ SDK. Windows требует Visual Studio 2022 C++ и Windows SDK, macOS — Xcode
с command-line tools. Сначала проверить SHA-256 патча по lock-файлу, затем
в checkout JCEF выполнить `git apply --check` и `git apply` с путём к патчу.

Для каждой архитектуры использовать отдельный чистый `jcef_build`:

| Хост | Команда конфигурации |
| --- | --- |
| Windows x64 | `cmake -S . -B jcef_build -G "Visual Studio 17 2022" -A x64` |
| Windows ARM64 | `cmake -S . -B jcef_build -G "Visual Studio 17 2022" -A ARM64` |
| macOS x64 | `cmake -S . -B jcef_build -G Xcode -DPROJECT_ARCH=x86_64` |
| macOS ARM64 | `cmake -S . -B jcef_build -G Xcode -DPROJECT_ARCH=arm64` |

Затем выполнить `cmake --build jcef_build --config Release`. Java-классы собрать
из того же пропатченного checkout: из каталога `tools` запустить `compile.bat win64`
на Windows или `compile.sh macosx64` / `compile.sh macosarm64` на macOS.
Нельзя смешивать пропатченный Java API с исходной native-библиотекой.
При кросс-компиляции нужны JNI-библиотеки JDK целевой архитектуры.

## Текущее состояние и условия поставки

**Постоянный общий профиль Chromium ещё не подключён.** Приложение использует
закреплённый upstream-runtime и отдельные временные контексты вкладок. Кнопка
очистки закрывает эти вкладки и их временные контексты. Скрытие панели, изменение
размеров и переключение чатов сохраняют живые вкладки до закрытия профиля.

Проверено в Windows:

- Патч целиком применяется к чистым закреплённым исходникам; его SHA-256 совпадает.
- Добавленные Java-классы компилируются с закреплённым JCEF API.
- Тест настоящего **upstream** JCEF проходит цепочку отказ доступа → ручной клик →
  cookie → чтение текста/PDF, снимок и DOM-клик, отклонение неподдерживаемого MIME,
  изоляцию временных контекстов и повторное подключение той же native-поверхности.

Пропатченные native-артефакты не собраны; `nativeArtifacts` намеренно пуст.
На текущем Windows-хосте нет CMake/C++ SDK; macOS-хост недоступен. C++-часть патча
не скомпилирована, команды матрицы не считаются проверенными сборками.

До поставки постоянного профиля требуется:

1. Собрать и проверить согласованные Java/native-артефакты для всех четырёх целей,
   упаковать ресурсы CEF и записать реальные SHA-256. Одновременно обновить Gradle
   coordinates и verification metadata. Проверка поставки должна отклонять
   отсутствующую цель или несовпадение checksum.
2. Подключить опорный контекст к каталогу профиля, принадлежащему DataStores;
   очищать данные только после native shutdown и интегрировать удаление профиля.
3. В двух отдельных процессах проверить сохранение cookies/localStorage/IndexedDB,
   изоляцию профилей, очистку и сохранение другой вкладки при закрытии одной.
4. Проверить macOS/iOS, DPI-варианты координат, фокус и наложение диалогов настоящего
   окна Heartbeat. Тест JFrame не заменяет эту проверку Compose/native-интеграции.
