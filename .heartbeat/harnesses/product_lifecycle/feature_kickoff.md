Репозиторий шага: `{{repository}}`. Все операции GitHub выполняй явно в нём: для gh issue/pr/workflow/release добавляй `--repo {{repository}}`, для gh api — путь `repos/{{repository}}/...` или соответствующие owner/name в GraphQL. Это правило действует и для загруженных навыков. Перед локальной разработкой, verify и git log сверь origin рабочего каталога с этим репозиторием; при несовпадении подготовь правильный checkout.

Заведи фичу «{{topic}}» в продуктовом цикле Heartbeat. Если тема пуста или размыта — сначала уточни у пользователя: какую боль снимаем и для кого; не выдумывай тему сам.

Шаги:
1. Загрузи навык biz_requirements харнесса product_lifecycle (harness_skill_load product_lifecycle/biz_requirements) и следуй ему.
2. Создай эпик-issue через gh CLI: заголовок «[Feature] {{topic}}»; метки `type:feature`, `source:agent`, `stage:requirements`; тело обязательно содержит:
   - маркер `<!-- heartbeat:lifecycle v1 -->` и строку «Стадия: requirements» (по ним доска находит и синхронизирует эпик);
   - разделы: Ценность, Пользователи, Метрики успеха (заполнит этап требований);
   - чек-лист этапов: требования → дизайн → функц. требования → разработка → тестирование → приёмка → релиз.
3. Создай под-issue «Бизнес-требования: {{topic}}» (метки `type:artifact`, `source:agent`) и привяжи его к эпику как sub-issue (GitHub API sub_issues).
4. Зарегистрируй фичу на доске: ui_call product_lifecycle add_feature {"title": "<заголовок>", "epic": <номер>}.
5. Ответь пользователю: ссылка на эпик, что дальше (этап требований), какие вопросы зафиксированы.

Правила: GitHub-записи только через gh CLI (run_command); кратко; дизайн и код не начинать.
