# Переход в разработку

Загружай при `stage:development` и перед созданием ветки/PR фичи.

## Что сделать
1. Читай план работ из функц. требований (под-issue артефакт эпика).
2. Реализацию веди скиллами проекта: `new-feature` (новый раздел/сценарий), `state-machine`/`mvi-store` (поведение), `design-system` (UI), `di-metro`, `data-storage`.
3. Задачу веди в draft PR со старта сессии: скилл `open-pr` (`$open-pr <задача>`), продолжение на другой машине — `continue-pr`. Каждый законченный шаг — коммит, push, обновление описания PR.
4. Ветвление: одна фича — одна ветка от `master`; цепочки связанных ПРов — харнесс `branch_pr_flow` (его навыки `new_pr_in_chain`, `pr_chain_update`).
5. Каждый шаг: `python scripts/check_commit_size.py --staged` перед коммитом, verify перед push, push готовыми шагами (правила AGENTS.md).
6. Свяжь PR с эпиком: в описании `Refs #<эпик>` (частичный шаг) или `Closes #<эпик>` (полное закрытие фичи); не смешивай маркеры.
7. PR на доску: ui_call `link_pr` {epic, pr}.
8. Готово (verify зелёный, PR ready) → переведи этап (шаблон `stage_advance`): доказательство (ссылки на PR и прогоны verify), метка `stage:testing`, строка «Стадия:», доска; дальше — `testing_acceptance`.

## Правила
- Мерж — только после ревью: `pr-review`/`pr-review-and-fix`; `/reviewed <sha>` — только по просьбе пользователя.
- CI: сначала локально; `module-build.yml` — только для чужих ОС; не перезапускай упавшее без просьбы; не расширяй CI.
- Дефект, найденный в разработке, — сразу в ветку фичи, отдельный issue не нужен.
