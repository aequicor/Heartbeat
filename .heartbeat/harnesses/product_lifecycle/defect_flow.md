# Дефекты

Загружай при триаже issue с `type:defect` и при исправлении дефектов.

## Триаж
1. Прочитай issue (`gh issue view <n>`): ожидаемое/фактическое, шаги воспроизведения, версия/ОС.
2. Определи severity: blocker / critical / major / minor; поставь метку.
3. Проверь воспроизводимость; уточни у автора недостающее; предложи workaround.
4. Свяжь с фичей: дефект по фиче в разработке — комментарий в эпик, фикс в её PR; отдельный дефект — своя ветка/PR.

## Исправление
1. Фикс по навыку проекта `pr-fix` (если дефект из ревью — коммит с `Addresses-Review:`), иначе обычная ветка/PR; verify перед push.
2. Связь в PR: `Closes #<дефект>` (исправлено полностью) или `Refs #<дефект>` (частично; в описании — что сделано и что осталось).
3. Если дефект принят из фидбека — не теряй связь: в комментарии дефекта ссылка на исходный issue.
4. После мержа следи за релизом: дефект считается исправленным с релизом, содержащим фикс; после релиза проверь входящие жалобы (`feedback_triage`).

## Доска
- Новые дефекты попадают в очередь фидбека синхронизацией (кнопка «Синхронизация» / ui_call `sync_from_github`).
- Статус триажа отмечай комментарием в issue; доска показывает открытые.

## Правила
- `source:*` не менять; новые issues агента — `source:agent`.
- Закрытые issues не переоткрывать: повтор дефекта — новый issue со ссылкой.
- Не чини дефект без воспроизведения или внятного отчёта — сначала триаж.
