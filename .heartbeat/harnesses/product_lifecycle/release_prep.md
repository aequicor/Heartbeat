# Подготовка релиза

Загружай при подготовке публикации (кнопка «Релиз: подготовка» доски, шаблон `release_checklist`) или явной просьбе пользователя.

## Что сделать
1. Собери состав: эпики, прошедшие приёмку (доска: стадия acceptance/выше; метка `stage:acceptance`), закрытые дефекты с прошлого тега (`git log <tag>..HEAD --oneline`).
2. Определи версию: последний стабильный тег `vX.Y.Z` (`git tag --list 'v*' --sort=-v:refname`), `heartbeat.version` в `gradle.properties`; предложи patch/minor/major с обоснованием.
3. Прогони verify на `master` — локальная проверка обязательна, релизный workflow её не заменяет.
4. Выведи в чат чек-лист релиза: состав изменений, уровень версии, риски, заметка об откате (механизм автообновления — features/app-update).
5. Дай администратору готовые команды (только для человека; не запускай сам):
   - Пробный прогон: `gh workflow run release.yml --ref master -f release_level=<patch|minor|major> -F dry_run=true`
   - Релиз: Actions → Release → Run workflow (master, release_level).
6. После подтверждённого релиза: сверь тег и релиз (`gh release view`), переведи фичи в `stage:released` (доказательство — ссылка на релиз; метка, строка «Стадия:», доска), проверь входящие дефекты новой версии (`defect_flow`).

## Правила
- Запуск `release.yml` (включая dry_run) — только человек; агент не запускает workflow и не создаёт теги.
- Не меняй `release.yml` и не добавляй detekt в него; CI не расширять.
- Все пять desktop-установщиков и проверки выполняет сам workflow — локально не дублируй.
