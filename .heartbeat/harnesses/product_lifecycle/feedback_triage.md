# Обратная связь

Загружай при разборе входящих issues (кнопка «Триаж фидбека» доски, шаблон `triage_issue`).

## Что сделать
1. Возьми старший необработанный issue с `source:user` (очередь доски или `gh issue list --label source:user --state open`).
2. Классифицируй:
   - **Дефект** (сломано/ошибается) → `type:defect`, навык `defect_flow`.
   - **Пожелание/идея** (новая ценность) → `type:feedback`; оцени: фича или бэклог?
     - Фича: предложи пользователю завести эпик (кнопка «Новая фича» / шаблон `feature_kickoff` с темой из фидбека); спроси подтверждение.
     - Бэклог: оставь открытым с `type:feedback` и комментарием-статусом.
   - **Вопрос/дубль** → ответь; дубль закрой со ссылкой на оригинал.
3. Ответь автору в issue: что поняли, что дальше; вежливо, конкретно, без обещаний сроков. Каждый разобранный issue получает ответ.
4. Фидбек стал фичей — свяжь: комментарий в эпике «Из фидбека #N»; исходный issue не закрывай до реализации (`Closes #N` поставит PR).

## Доска
- После завершённого разбора отметь пункт: ui_call `mark_feedback` {number}; затем обнови очередь (`sync_from_github`). Открытый разобранный issue остаётся в списке, но кнопка общего триажа выбирает только новые, начиная с наименьшего номера.
- Разобранные закрытые issues уходят из очереди сами (синхронизация видит state).

## Правила
- `source:user` не менять; issues агента — `source:agent`.
- Не превращай мелкое пожелание в эпик без подтверждения пользователя.
- Очередь на доске — зеркало GitHub; правды больше в GitHub, чем в доске.
