# Issue → проверенное исправление → PR

Применяй к одной открытой issue aequicor/Heartbeat за запуск.

1. Сверь URL, номер, состояние и полный текст issue через `gh issue view`. Если номер задан, работай только с ним. Иначе просмотри открытые PR и выбери самую старую выполнимую issue без открытого PR; пропускай блокируемые внешними ресурсами и требующие другой ОС, записав причину. Не меняй несколько issues одним PR без явной причинной связи.
2. Работай в отдельной ветке/worktree, не теряя чужих изменений. Перед правками прочитай `AGENTS.md`, `CLAUDE.md`, применимые `.claude/rules/` и навыки. Сформулируй наблюдаемое поведение и критерии полного исправления по тексту issue.
3. Добавь проверку, которая проходит через реальный пользовательский или внешний интерфейс до результата: Desktop UI — запуск приложения и `computer_*` либо автоматизированный UI-сценарий с настоящими компонентами; API/сервис — интеграционный сценарий через публичную точку входа с реальными связями модулей; CLI/build — реальная команда и проверка выхода/артефакта. Проверка должна обнаруживать исходный дефект, по возможности покажи красный прогон до правки и зелёный после. Unit-тесты дополняют её. Называй точно, что было исполнено, на какой ОС и какие границы системы покрыты. Если e2e недоступен, не объявляй issue полностью исправленной.
4. Запусти применимые сборку, тесты и detekt по `verify`; исправь ошибки, проверь diff и `scripts/check_commit_size.py --staged` до коммита. Не останавливай Gradle-демон из приложения Heartbeat.
5. Создай PR с описанием поведения, доказательством e2e (команда/шаги, результат, платформа), остальных проверок и ограничений. Для полностью исправленной issue используй ровно `Closes #N`; для частичной — `Refs #N` или `Part of #N` и список незавершённого. Никогда не смешивай маркеры для одного номера. Выполни проверку бюджета коммитов `--base origin/master --head HEAD`.
6. Перед завершением сверь актуальные state issue и PR. После merge проверь работу `.github/workflows/close-fixed-issues.yml` и закрытое состояние; при неудаче выясни причину, не скрывая её прямым закрытием issue. Если PR ждёт ревью или merge, верни ссылку и статус ожидания.

Не выводи секреты из gh, CI или приложения. Не маскируй непроверенное поведение утверждением, что e2e пройден.
