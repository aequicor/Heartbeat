# Виртуальный Sandbox

Sandbox работает с внешними Git-проектами независимо от языка и системы сборки. Для запуска нужны существующий HEAD и чистый исходный checkout: без staged, unstaged и неигнорируемых untracked-файлов. Обычный Worktree остаётся отдельным режимом. Сохранённые задачи прежнего Sandbox продолжают работать по своему протоколу; миграция не удаляет их checkout и ветки.

## Виртуальный код

Публичный workspace различает физический каталог и виртуальный доступ. У сессии есть закреплённая база Git и сохраняемые изменения с ревизиями. Чтение, списки каталогов, glob, поиск и запись через инструменты хоста видят объединённое состояние. Создание, редактирование, удаление и перемещение не меняют исходный checkout; перемещение сохраняет Git-режим и бинарное содержимое. Данные сохраняются до успешного ответа инструмента.

Нативные файловые инструменты, shell и обходные инструменты отключаются при объявлении и проверяются при исполнении, включая resume. CLI работают в служебном каталоге, инструкции проекта поступают через виртуальное представление. Если движок не может гарантировать ограничения, запуск отклоняется. Разрешения записи привязаны к ревизии и точным аргументам операции.

Дочерние агенты и клетки получают снимок родителя на момент ответвления. `sandbox_integrate` объединяет неизменяемый результат ребёнка относительно этого снимка трёхсторонним слиянием. Предыдущие результаты и связи снимков сохраняются при переносе базы.

## Менеджер сборок

Канонический Git common directory определяет единственный менеджер проекта, общий для профилей. У каждого проекта своя очередь, конфигурация команд с ревизиями и постоянный пул переиспользуемых build-worktree. Размер пула настраивается для проекта, по умолчанию — два слота. Слоты создаются по необходимости и предпочитают прежнюю сессию, сохраняя игнорируемые сборочные выходы. Общий ограничитель приложения учитывает оценки CPU и RAM без единой очереди проектов.

Уменьшение пула удаляет свободные лишние слоты, занятые удаляются после завершения и восстановления. Явная очистка проверяет владение и блокировки. Отсутствие активных сессий не удаляет пул.

`configure_build` принимает executable, аргументы, рабочий каталог, окружение, таймаут, необязательные кеши и эксклюзивные ресурсы. `run_build` фиксирует ревизии кода и конфигурации. Go, Python, Java, Kotlin, Rust и собственные скрипты используют один механизм. Обязательных языка, кеша, системы сборки или стандартной команды проверки нет. Нужные проверки определяются инструкциями обслуживаемого проекта; агент сообщает о недоступных и невыполненных проверках.

Работник журналирует слот до изменений, подготавливает базу и снимок, выполняет команду, останавливает дерево процессов и восстанавливает исходники и новые неигнорируемые файлы. Терминальный результат публикуется после восстановления при успехе, ошибке и отмене. Игнорируемые выходы сохраняются. После сбоя восстановление предшествует повторному использованию; неисправный слот блокируется до очистки. Изменения исходников, созданные командой, не импортируются в сессию автоматически. Контейнеры и изоляция процессов средствами ОС в механизм не входят.

## Внешние изменения и результат

Внешние правки приостанавливают связанные сессии и детей. Сохраняемая пауза предшествует подтверждённой остановке ходов и сборок всех активных профилей. Окно ожидания по умолчанию составляет четыре минуты; настройка приложения применяется к следующему эпизоду. Повторные правки срок не продлевают, пауза переживает перезапуск.

Возврат чистого прежнего HEAD внутри окна продолжает работу автоматически. Чистый потомок переносит виртуальные изменения трёхсторонним слиянием. Истечение срока, reset и смена истории требуют кнопки «Продолжить». Если непрерывность reflog подтвердить нельзя, перенос на новый HEAD также требует явного продолжения. Конфликты сохраняют исходные версии и ждут выбора пользователя: поручить агенту разрешение либо оставить на паузе. `sandbox_resolve_conflict` доступен только после этого разрешения; новые внешние изменения отзывают его.

Продолжение создаёт новый ход с описанием изменения workspace. Принятый прерванный запрос повторно не отправляется. Результаты помощников сохраняются отдельно от отменённого исходного хода.

Завершение замораживает запись и идемпотентно создаёт отдельную локальную ветку с коммитом результата. Интерфейс показывает имя ветки и SHA. Исходный checkout не переключается; PR, merge и push требуют отдельного действия пользователя.

Контракты и алгоритмы описаны в KDoc workspace, переходов состояния, журнала, Git-хранилища и работника сборок.
