# Aequicor Heartbeat

ИИ-студия на Kotlin Multiplatform + Compose Multiplatform.
Платформы: **Android, iOS, Desktop macOS, Desktop Windows, Desktop Linux x64 (Ubuntu 24.04, X11/XWayland)** (desktop = один JVM-таргет, выбор UI-кита — в рантайме по ОС).
Корневой пакет: `io.aequicor.heartbeat`. Язык общения в коде/доках: русский в документации, английский в идентификаторах и KDoc.

## Где правила

Источник правды по коду — KDoc в исходниках. Правила для агентов — этот файл и `AGENTS.md`.
В Claude Code правила по путям подгружаются автоматически из `.claude/rules/`; Codex читает применимые правила явно согласно `AGENTS.md`.
Общие процедуры (создать фичу, машину, стор, тогл…) — скиллы в `.claude/skills/`.
Codex обнаруживает одноимённые навыки в `.agents/skills/`; они направляют к этим общим процедурам.

## Группы модулей

```
platform-main/   точки входа: android, desktop, ios (+ shared umbrella/framework);
                 di-bundle — единственный модуль, видящий все impl: Metro-граф (per-platform)
core/            инфраструктура: navigation, mvi, state-machine, di (api/ext/impl), profile-facade (api/impl),
                 resources, datastore, network, ai, feature-toggles, logging, common, desktop-dialogs
design-system/   tokens (единый набор, пресеты по хосту), theme, components, layouts, resources, catalog, adaptive (material | fluent | macos)
features/<name>/ api  — контракт: state-machine (состояния, интенты, переходы, эффекты), MachineKey, маршруты
                 impl — UI, FlowMVI-сторы, Decompose-компоненты, репозитории, эффекты машины, DI-контрибуции
features/{ai-studio,questionnaire,checklist}/screen-model — сериализуемые состояния и интенты экрана без domain/IO
                 screen-ui — общие Compose-экраны desktop и Wasm; сторы и навигация остаются в impl
build-logic/     convention-плагины Gradle (heartbeat.kmp.library, heartbeat.feature.api/impl, heartbeat.detekt…)
lint/            detekt-rules — собственный набор правил `heartbeat` (политика логирования и обработки ошибок)
chromium-plugin/ расширение для Chrome и других Chromium-браузеров (MV3, JS без сборки) — клиент `features:chromium-bridge`
design/          макеты pen.dev (`.pen`): библиотека токенов и компонентов, файл на фичу — `design/README.md`
```

> Текущее состояние: шаблон перенесён в `platform-main` — `shared` (общий вход, iOS framework `Shared`), `android`, `desktop`,
> Xcode-проект `ios`; пакеты `io.aequicor.heartbeat.platform.*`, applicationId `io.aequicor` сохранён.
> AI-движки: контракты `features:ai-engine:{facade,authenticator}:api`; `authenticator:impl` — источники авторизации профиля и проверки;
> `facade:impl` — каталог движков и привязок, выбор движка по умолчанию, модели, Room-индекс сессий, пул runtime, `ActiveSession` на машине.
> Адаптер `koog:{api,impl}` (OpenAI, Anthropic, OpenAI-/Anthropic-совместимые серверы по HTTPS или loopback, локальный Ollama, потоковые текстовые сессии, история и подключения профиля)
> подключён в DI, включение — тогл `ai.koog` (по умолчанию true).
> Кодинг-сессии Koog (только Desktop, тогл `ai.koog.coding_tools`): сессия на проекте получает файловые инструменты и `run_command`
> в корне проекта. Все инструменты используют общую профильную настройку безопасности. Изменения файлов
> привязаны к точному снимку и рабочей области; произвольная shell-команда требует подтверждения в автоматическом режиме.
> Локальный Desktop-адаптер `codex:{api,impl}` — app-server, сессии, текстовый стриминг, отмена и approvals (тогл `ai.codex`).
> `claude:{api,impl}` — desktop Claude Code CLI, профильный runtime текстовых сессий, CLI-авторизация, обнаружение моделей,
> частичная история наблюдённых ходов (тогл `ai.claude`, по умолчанию true). CLI ищется в PATH, у native installer
> (`~/.local/bin`), в Homebrew и у приложения Claude Code desktop (macOS: `Application Support/Claude/claude-code`,
> общий логин, обновляет его само приложение; в «Авто» — последний вариант и только на macOS).
> Подключение через приложение Claude (тогл `ai.claude.desktop_app`, по умолчанию true): способ подключения `desktop`
> (`ConnectionMethod.CliLogin.hostApp`) сохраняет в параметрах запуска `RuntimePreference.HostApp` — runtime приложения
> (новейшая проверенная сборка с маркером `.verified` или закреплённая версия; macOS и Windows `%APPDATA%\Claude\claude-code`),
> с общим каталогом `~/.claude`; вход самого приложения не читается, вход CLI — из панели движка.
> Выбранный источник runtime (копия Heartbeat / приложение / системный) не подменяется другим, если его нет;
> если вход CLI выполнен не был (приложение передаёт свой вход CLI через окружение, `~/.claude` пуст), визард подключений
> при «Подключить» сам запускает `EngineAction.Login` (CLI открывает браузер и ждёт callback; до 5 мин, без отмены в визарде),
> «Проверить» runtime не переключает и входит только на подходящем; сорванный вход решает проверка привязки;
> нативные инструменты идут через гейт доверия (`ClaudeNativeGate`),
> инструменты хоста — через MCP-мост, дерево субагентов читается из наблюдённых событий; внешней истории CLI пока нет.
> Вход картинок и допустимые effort моделей последнего обнаружения сохраняются в профиле (переживают перезапуск); чтение
> сохранённой сессии другого источника не вытесняет живой рантайм (история через отдельный рантайм без запуска ходов).
> Живой e2e на реальном CLI вне `check`: `:features:ai-engine:claude:impl:claudeLiveTest` и
> `:platform-main:di-bundle:claudeLiveGraphTest` (нужен авторизованный CLI, расходуется квота).
> Подключение движков — `features:ai-engine:connections` (визард «движок → авторизация → модели» и пространство
> «движок × подключение × модель», тогл `ai.engine_connections`) поверх `EngineFacade` и `AuthSources`; экраны показывают
> движки, объявившие `connectionMethods` (Pi, Koog, Codex, Claude); адаптеры узнают источники привязок через SPI `bind`/`unbind`.
> Управление движками (тогл `ai.engine_management`, по умолчанию true) — раздел настроек «Движки»
> (`features:ai-engine:control-panel:{api,impl}`): список движков → панель движка (машина `EngineControlMachineKey` в скоупе
> панели, операции `ControlOperation`). Блок управления поверх `EngineManagement` (`facade:api`): вкл/выкл в профиле поверх
> флагов разработки, статус и пути, своя проверенная (SHA-256) копия CLI Heartbeat (Codex, Claude; Pi — обновление с откатом
> на закреплённую версию), вход/выход CLI, параметры запуска (включая источник runtime `RuntimePreference` и
> закреплённую версию runtime приложения), перезапуск рантаймов, пакеты Pi; приложение-хост движка
> (`ManagementSpec.hostApp`, `HostAppState`: установлено ли, версия, runtime, общий каталог; кнопка «Открыть приложение»);
> адаптеры реализуют SPI `EngineManager`, длительные задачи принадлежат профилю. «Модели и движки» ведут в панель строкой «Управление движком».
> Настройка движков (тогл `ai.engine_configuration`, по умолчанию true, вместе с `ai.engine_management`) — декларативная
> схема `EngineConfigSchema` и сервис `EngineConfiguration` (`facade:api`, SPI `EngineConfigurator`): профиль с ревизиями,
> секреты — ссылками на хранилище профиля, файлы проекта с ревизиями содержимого, доверие к проектам, импорт из собственной
> конфигурации движка. Панель рисует любую схему без кода под движок: страницы полей (флаг, выбор, число, текст, список,
> записи с вариантами, пары с секретами, документы), файлы целиком, проекты (значения профиля — умолчания, неразобранный
> файл правится только как текст) и импорт. Pi первым: settings.json, mcp.json, AGENTS/SYSTEM/APPEND_SYSTEM, встроенные
> расширения и пакеты пишутся в каталог агента перед запуском, секреты MCP попадают только в файл процесса; проект грузит
> свою исполняемую конфигурацию только при доверии, до решения — лишь инструкции, а студия спрашивает плашкой над композером.
> На странице ресурсов — инвентарь расширений, навыков и шаблонов профиля и проекта (`EngineConfiguration.resources`,
> SPI `EngineConfigurator.resources`, `ConfigPage.hasResources`): относительный путь, источник и выбор по сохранённым
> настройкам и флагам запуска. Он перечитывается после сохранения, импорта и изменения доверия; внешние пути и пакеты
> не обходятся, переходы по ссылкам ограничены корнем, объём обхода ограничен. Выбор настройками не гарантирует успешную
> загрузку содержимого движком. Маски профиля Pi отсчитываются от постоянного `<profile>/home`.
> `ai-studio` использует профильный фасад, сохраняет идентичность и историю чатов; принятые ходы принадлежат профилю
> и переживают закрытие экрана (тогл `ai_studio.engine_runtime`, по умолчанию true; при выключении — демо-пространство и старт профиля с welcome).
> Ссылки в markdown чатов (`parseHbLink`/`HbLinkTarget` в ДС): web, `mailto:`, `tel:` открывает платформа, прочие схемы
> инертны; файловые (`file:`, абсолютный, `~/` или относительный путь, `:line`/`#Lline`) на Desktop открывают
> предпросмотр в правой панели студии (`SidePanelUi.File`, тогл `ai_studio.file_preview`, по умолчанию true): путь —
> от рабочей копии чата (worktree или проект), только чтение до 1 МиБ, markdown с оформлением или исходником,
> переход к строке и перечитывание при изменении файла (план). Удалённая панель Chromium файлы не открывает.
> ACP v1: `features:ai-engine:acp-interface:{api,impl}` — общий клиент JSON-RPC, сессии, updates, permissions;
> stdio на Desktop, явный отказ запуска desktop-процессов на мобильных платформах. Конкретные движки подключаются отдельно.
> `features:ai-session-engine-transfer:{api,impl}` — перенос сессии на другой движок (handoff-транскрипт, цепочка сегментов
> логической беседы в profile KV); машина в ProfileScope создаётся лениво, `EngineFacade` — опциональная зависимость, UI нет.
> Готово: `build-logic` (`heartbeat.detekt`, `heartbeat.kmp.library`, `heartbeat.metro`, `heartbeat.room`), `core:logging`, `core:common`,
> `core:di:{api,ext,impl}`, `core:profile-facade:{api,impl}`, `platform-main:di-bundle` (скоупы app → profile → feature → screen),
> `core:navigation:{api,impl,compose}`, `core:state-machine:{api,impl,flowmvi-ext}`,
> `core:network:{api,impl}`,
> `core:datastore:{api,impl}` (key-value + БД фич, владельцы app/profile, удержание записей),
> `core:secrets:{api,impl}` (защищённые секреты профиля и ссылки), `core:feature-toggles:{api,impl}` (тоглы, реестр, локальные переопределения, `FeatureToggleControl`).
> `features:ai-engine:{facade:{api,impl},pi:{api,impl}}` — встроенный движок Pi по умолчанию только на Desktop (Windows/macOS/Linux)
> (бинарь Pi загружается и проверяется по SHA-256 при первом использовании, прогресс и повтор доступны в студии и подключениях;
> `preparePiRuntime` остаётся для development, данные — в `<app data>/engines/pi`; установщик Windows на Inno Setup
> (`packageInnoSetup`) при удалении чистит данные пользователя — `platform-main/desktop/packaging/windows/heartbeat.iss`)
> за тоглами `ai.engines` + `ai.pi` (вендорные ключи и OpenAI-/Anthropic-совместимые серверы — `CompatibleProtocol` в `facade:api`).
> Раздел «Безопасность» хранит единственный профильный режим (`AgentSecuritySettings`): спрашивать / автоматически
> (по умолчанию) / полное доверие. Он действует сразу для всех чатов, помощников и ожидающих подтверждений.
> `ToolPermissions` — общий гейт hosted/native вызовов. При выключенном `ai.action_safety` полное доверие разрешает корректный вызов доступного
> инструмента без дополнительного ревью или permission-хуков. Автоматический режим разрешает чтение и доказанную
> обычную правку файла проекта; прочие эффекты, команды и неопределённость запрашивают подтверждение точного действия.
> Режим «Спрашивать» подтверждает все изменения и команды. Изменение режима отменяет старый запрос и пересчитывает решение.
> Тогл `ai.unattended_approval_timeout` (по умолчанию false): запрос подтверждения через `ToolPermissions` отклоняется, если окно Heartbeat
> 30 с подряд не в фокусе (`WindowFocus`, desktop публикует фокус окна; активный захват computer-use считается присутствием,
> возврат фокуса сбрасывает отсчёт). Агенту сообщается «No answer», а не отказ пользователя. Ответы из панели Chromium и шлюзы
> вне `ToolPermissions` (например `ClaudeNativeGate`) пока не учитываются.
> Схема аргументов, владение, ревизии/CAS, время жизни вызова и реальные возможности платформы проверяются всегда.
> Структурная политика (`ai.action_safety`, default false, фиксируется на время жизни профиля) требует проверяемый
> контракт фактического действия. В Automatic полные факты и оригинальные указания человека проходят быстрый,
> при сомнении — подробный модельный разбор; неизвестный анализ и недоступное ревью требуют подтверждения.
> В Ask подтверждаются все действия, включая чтения; Trust пропускает модельное ревью, сохраняя запреты анализа
> и обязательные Deny/Ask hooks. Разрешение повторно проверяется перед выполнением. Неподконтрольные native-пути
> Claude/Codex закрываются; перед защищённой сессией Codex офлайн и без авторизации воспроизводит эффективные флаги запуска,
> каталог моделей, config треда и полные объявления инструментов и сверяет фактический каталог с ними (имя, описание, структура параметров);
> неизвестные ключи конфига со значением не как у того же CLI в чистом home и активный `profile` — отказ; номер версии
> совместимость пробы не определяет, без пробы — CLI ≥ 0.160.0.
> Текстовые служебные сессии `IsolatedPrompts` не имеют инструментов: `isToolFree` выключает весь native/hosted каталог.
> Разрешение одноразовое, привязано к полным аргументам, источнику и снимку; изменившаяся операция требует нового вызова.
> Старые `TrustLevel`/`AgentToolDecisionMode` в протоколах — метаданные совместимости, не отдельные источники разрешений.
> GitHub PR-инструменты (`ai.github_pull_tools`, default true, Desktop) — отдельные hosted read/create-draft/update/ready
> с проверкой полного inline-текста и одноразовой привязкой к вызову. Репозиторий и аккаунт gh задаёт пользователь в разделе
> настроек «Инструменты Heartbeat» (`features:github-connector:{api,impl}`, тогл `github_connector.enabled`, кнопка «Подключить»:
> поиск gh, аккаунт, репозиторий с правом push, проверка; в профиле хранится только `GitHubConnection` без токена, owner — бандл
> `engines`); без подключения инструменты не объявляются, переменные `HEARTBEAT_GITHUB_*` — запасной путь оператора;
> REST напрямую через Ktor, ready — фиксированный GraphQL. Общая shell-политика не ослабляется;
> preflight revision не является атомарным SHA-разрешением. Настройка и границы —
> [GITHUB_PR_TOOLS.md](features/ai-engine/facade/impl/GITHUB_PR_TOOLS.md).
> Дизайн-система: `design-system:{tokens,adaptive,theme,resources,layouts,components,catalog}`;
> отдельная `platform-main:uikit-sandbox:{desktop,android,shared}` и iOS Xcode app — [запуск](platform-main/uikit-sandbox/README.md).
> `features:effort-configuration:{api,impl}` — машина выбора reasoning effort по маршруту модели (ProfileScope); ai-studio шлёт выбор
> через неё, движки Codex/Claude/Pi/Koog объявляют и применяют уровни; сохранение стартового выбора в профиле — тогл `ai.effort_configuration` (по умолчанию true); изменения effort в существующем чате остаются локальными для чата.
> Koog узнаёт поддержку effort из API (Anthropic, Ollama), иначе из каталога models.dev (тогл `ai.koog.reasoning_catalog`;
> совместимый маршрут — по разделу вендора, чей origin повторяет), иначе по семейству модели;
> отвергнутые поставщиком параметры — повтор хода без них. Обрезанные стримом tool-calls склеиваются по индексу,
> непригодные вызовы отбрасываются до инструментов и эха в промпт.
> `features:computer-use:{api,impl}` — управление компьютером для тестирования и отладки приложений (только Desktop Windows/macOS):
> два режима захвата — два семейства hosted-инструментов: `computer_*` (весь рабочий стол или монитор) и `window_*`
> (одно окно, `window_list`), общий `computer_status`; инструмент чужого семейства отвечает `CaptureModeMismatch`.
> Старые имена `computer_<глагол>` объявлены `legacyNames`: сохранённая политика, отключавшая их, отключает и `window_*`.
> ROI (rectangle of interest) — рабочая область захвата (`*_roi`, `SetRoi`): кадры, тайлы, zoom и ввод ограничены ею
> (`OutsideRoi`), пиксели кадра — относительно ROI. Видео-режим (тогл `computer_use.recording`, по умолчанию false):
> `<семейство>_record` и `observeMs` у ввода снимают кадры с частотой до успокоения экрана или лимита и возвращают
> ключевые кадры, кадрированные по области изменений (auto-ROI, `ClipRecorder`, `MotionAnalysis`). Master-кадр с кропами и тайлами в нативном разрешении, сжатие кадра под
> токен-бюджет агента (пресеты, JPEG/PNG, gray/indexed с дизерингом, лестница снижений под лимит байтов), ввод мышью и клавиатурой
> только внутри захваченной области, контракты `EngineFeature` (`computer.host` у хоста,
> `computer.control` у движка с роутером native → host). Доступ агента — один переключатель профиля (по умолчанию выключен,
> маршрут `computer-use` в настройках): агент сам выбирает семейство и цель, ввод вооружается одобренным вызовом через гейт
> доверия, захват принадлежит ходу агента и освобождается в конце хода; выключение отзывает захват (`Revoke`) и без
> открытого экрана. Во время захвата Desktop закрепляет окно сессии у правого края поверх окон с кнопкой «Стоп»
> (интент `StopAgent`), а при захвате рабочего стола — тенью по периметру экранов. Виртуальный курсор агента виден
> в обоих режимах (над окном — пока оно на переднем плане): указатель плавно скользит к цели, клик оставляет волну,
> drag — след, прокрутка и клавиши — подпись (жест `ComputerUseGesture`, без набранного текста).
> Снимок скрывает окно и индикаторы (запись — один раз на весь клип, до 10 с); ввод мышью скрывает только окно сессии.
> Скольжение начинается только от последней точки агента, перед нажатием проверки повторяются.

> `features:organic-ai:{api,impl}` — органический ИИ (тогл `organic_ai.enabled`, по умолчанию true): профильная машина
> организмов сессий. Зигота растёт из цели (`Conceive`), клетки делятся сами инструментом хоста `organism_divide`; результаты детей,
> вердикты и ответы хранятся в очереди и читаются агентом через `organism_receive` (повторное чтение — `after`).

> прочитать очередь, без текста результата в чате; ожидание и курсор переживают рестарт. Иммунитет судит
> жалобы (`organism_complain`) и споры (`organism_dispute`) каждый раз в новой сессии без инструментов; убийство лизирует клетку
> с потомками, зигота неподсудна — организм убивает только `Abort`. `Abort` помечает организм сразу, а остановку его нативных

> после `Unconfirmed` пробует снова для всех клеток, включая ранее убитые, сохраняя готовый ответ). Состояние не журналируется: новый профиль
> восстанавливает `Released`, а Sleep/Awaken в том же профиле — `Unconfirmed`, если остались хендлы или открывающиеся сессии. Организмы живут в профильном журнале и полностью
> восстанавливаются после рестарта (recovery-ход клетки); запросы разрешений клеток эскалируются через состояние машины и `Decide`.

> сообщение зачинает организм, завершение отмечено индикатором в заголовке, новое сообщение продолжает зиготу с сохранением истории (если организм не виден — принимает цель заново); справа вверху — субсессии (зигота, клетки, судьи) с состояниями,
> «Остановить» / «Продолжить», запросы разрешений клеток — в панели чата.
> Песочницы клеток (тогл `organic_ai.sandbox`, по умолчанию true, нужен `worktree_mode.enabled`; `Conception.isolation`, у организма чата с проектом):

> копия готовится и сохраняется (`Cell.workspace`, `WorkspaceBound`) до создания сессии, ключ задачи — `Organism.sandboxTask`, владелец копии,
> ветки, запусков и сборок — журнал worktree-mode. Ход клетки регистрируется там точной попыткой (`RunStarted` до submit, `RunAccepted`/`RunSettled`

> сливает коммит в свою копию. Новый запуск сбрасывает прежний снимок; после завершения зиготы студия показывает доверенную запись
> с точным коммитом результата, включая незакоммиченные файлы. Чатовый Worktree для организма по-прежнему исключён; без `worktree_mode.enabled` зачатие отклоняется,

> Общие лимиты графов и одиночных действий — 3 на владельца, 8 на профиль. Выключение тогла останавливает
> новые старты, сохраняя результаты текущих; просмотр и отмена сохранённых графов доступны.
> Команды запускаются после сохранения идентичности группы процессов/Windows Job; прерванные команды
> требуют решения родительского агента после проверки фактических эффектов и остановки прежнего процесса.
> Агентские задания сохраняют чат и квитанцию принятого хода. `RestoresSessionTurns` в Pi/Codex делает свежую
> проверку движка: совпавший ход наблюдается, подтверждённо свободный чат получает recovery-ход с историей,
> неопределённый исход остаётся ожидающим восстановления. Текст ответа не определяет успех.
> `features:context-window-optimization:{api,impl}` — оптимизация контекстного окна (тогл `context_optimization.enabled`,
> по умолчанию true; профильная машина в ProfileScope читает хранилище только после включения тогла):
> сжатие как ход через `CompactsContext` (`facade:api`; Codex `thread/compact/start`, Pi RPC `compact`,
> Claude `/compact`, Koog — своя выжимка с границей контекста), `/compact` и кнопка в индикаторе контекста ai-studio,
> автосжатие между ходами по порогу (`.auto_compaction`, гистерезис и эскалация native → rollover в `decideCompaction`),
> rollover — продолжение чата в новой сессии с выжимкой (`.rollover`, замороженные сегменты ленты), журнал прогресса,
> переживающий сжатие, и инструменты `context_status`/`context_checkpoint`/`context_compact` (`.ledger_tools`),
> маскирование старых результатов инструментов в промпте Koog (`.koog_masking`), выгрузка длинных выводов с
> `context_recall` (`.offload`), раздел настроек «Контекст» и сворачивание размышлений/инструментов в ленте.
> Журналы (строка на сессию, 30 дней) и выгруженные выводы (7 дней, общий лимит) — в профильной Room-БД фичи, настройки — в KV.
> Бриф продолжения (`.continuation_brief`, чистый `continuationBrief` в api): все сообщения пользователя из всех сегментов
> (первое и новые целиком, старые сокращаются, служебные пропускаются), выжимка работы и последний ход. При rollover
> старая сессия сначала пишет handoff-выжимку ходом без инструментов (`HANDOFF_REQUEST_PREFIX`: `ContextHandoffHook`
> запрещает вызовы, ход идёт с доверием «спрашивать» для нативных инструментов мимо хуков, например Codex); провал,
> остановка или новый ход после выжимки — механический fallback; после нативного сжатия бриф уходит со следующим ходом;
> после `context_compact` агента студия сама запускает ход продолжения (не больше 3 подряд и только если чат с тех пор
> не запускался). Журнал прогресса доставляется отдельно, в бриф не входит.
> `features:checklist:{api,impl}` — встроенные карточки с чекбоксами, одним выбором и текстом
> (`checklist.enabled`, по умолчанию true). `checklist_create`/`checklist_get` создают и читают карточки;
> ответы вводит пользователь. Атомарный профильный журнал сохраняет черновики и outbox; события и ACK идут
> через `SchedulerBus`. `ResumeSession` использует scheduler; `MarkSessionReady` меняет готовность без нового хода.
> Студия хранит проекцию событий и идентификатор текущего запроса; новый запрос отменяет старые проверки готовности.
> `features:harness:{api,impl}` — харнессы (тогл `harness.enabled`, по умолчанию true): профильная библиотека окружений
> агента под задачу или проект — скиллы, инструкции, шаблоны, Kotlin-скрипты (хуки, события, свои инструменты `hs_*`)
> и workflow помощников. Харнессы создаёт агент инструментами `harness_*`: код проходит компиляцию, а изменения,
> подключения и запуск workflow — общий гейт безопасности. Разрешение связано с кодом, аргументами, ревизией,
> подключениями и вызовом. Отдельных настроек доверия и редактора разрешений нет; старые policy-поля игнорируются.
> Deny/Ask permission-хуки дают запрос подтверждения в Ask/Automatic и не ограничивают Full Trust. Контекстные
> хуки продолжают работать. Лимит 8 активных харнессов ограничивает контент и инструменты. Правки —
> `HarnessIntent.Internal.Edit`; другие фичи шлют только `Attach`/`Detach`/`Reload`, у `HarnessRunsMachineKey`
> публичных интентов нет. Пользователь управляет и редактирует их в
> «Настройки → Харнесс», подключает к чату из меню «+»; агент подключает их через `harness_attach`.
> Настройка «Включать в новых сессиях» заранее выбирает включённый харнесс в новом обычном чате студии с учётом проекта;
> выбор можно снять до отправки. Он передаётся движку при создании сессии и сохраняется до первого промпта.
> Подключения существующих чатов не меняются; сами области Profile и Projects не активируют харнесс автоматически.
> Скрипты и workflow работают только на Desktop: K2 компилирует
> в отдельном процессе-воркере (свой малый heap, убивается по таймауту), исполняются они в процессе приложения
> (проба `--heartbeat-harness-probe`); запуски workflow восстанавливаются после рестарта.
> `WorkflowScope.organism(goal, OrganismOptions)` запускает один организм органического ИИ как owned-исполнителя
> крупного этапа и возвращает типизированный `OrganismOutcome` (`Answered` / `Refused` / `Ended`): отказ и окончание
> без ответа — данные для workflow, а `Answered` не доказывает бизнес-успех этапа. Организм шага выводится из запуска
> и ключа, привязан к шагу в журнале (`WorkflowStep.organism`) и к выданному слоту (`WorkflowOrganismJournal`, квоты
> `ORGANISMS_PER_RUN` / `ORGANISMS_PER_PROFILE`), поэтому повтор и рестарт сверяются с тем же организмом и не создают
> второй. Перед отправкой зачатия журналируется `Running`; неопределённая попытка не повторяется. Слот возвращается
> только после подтверждённого освобождения сессий (`Organism.sessions == Released`), включая успешный ответ; завершение
> или отмена запуска останавливают его организмы, пауза — нет. Мост — `OrganismHost` в `harness:impl` (публичные
> интенты `OrganicAiMachineKey`, доверие не шире Ask); `harness:api` от `organic-ai:api` не зависит. Запросы
> разрешений/ввода клеток такого организма не имеют диалога (у него нет чата): при наблюдении запроса рабочей клетки
> этап сохраняет `Ended(InteractionRequired)` и останавливает организм; результат возвращается после подтверждённого
> cleanup. Автоответа, повышения доверия и автоматического нового организма нет; workflow должен парковать процесс для участия человека.
> `ScriptData` хранит JSON мини-приложения в профильном `SecretStore`, в пространстве харнесса: данные переживают
> обновление скрипта, отключение и рестарт. Запись проверяет ревизию и активность одобренного скрипта; успешная
> фиксация обновляет `dataRevision` владельца для связанных интерфейсов, чтение ревизию не меняет.
> `ScriptProcesses` (`processes`, пакет `harness/api/process`) — durable-процессы разработки поверх `ScriptData`
> (все процессы одним конвертом в зарезервированном ключе `hb_processes`; до 8 процессов на харнесс): этап, попытки с исполнителем и привязкой к
> ревизии входа и SHA, ожидание без живого агента, явные полномочия `Write`/`Publish`/`Merge`/`Release` (самодекларация
> одобренного скрипта, не одобрение человека и не граница безопасности: граница «только человек» — работа хоста) и журнал
> внешних записей «намерение → подтверждение / неизвестно → сверка». Изменения — только командами `ProcessCommand`
> через чистый `reduce`; точный повтор даёт `Unchanged`, повторная запись с открытым исходом отклоняется. Пометка
> «неизвестно» и «не применено» называет номер попытки записи (`tries`): запоздавшая сверка прошлой попытки не сбросит
> идущий повтор. Журнал помнит 8 ключей, забытый ключ начинает новую запись — ключ называет операцию (ревизия, head).
> `ProcessRecord.recovery(now)` перечисляет, что процесс оставил открытым (идущая попытка, открытые записи, ожидание):
> харнесс вызывает `recovery(now, settleAfter)` в единственном item-владельце при активации (`Activated` приходит и
> без рестарта, и после замены исходника, и для других item, поэтому рестарт от ещё идущих вызовов не отличить) и
> повторно по прошествии `settleAfter`. `settleAfter` — аренда вызова: больше самого долгого вызова или попытки
> харнесса без записи итога (у каждого вызова таймаут); пункты моложе в список не попадают, пока вызов может идти.
> Харнесс сверяет остальное с реальным миром, а не перезапускает вслепую; живой исполнитель (запуск workflow) и
> актуальное ожидание остаются в списке — «оставить как есть» допустимый исход. Номер попытки записи (`tries`)
> сквозной на запись процесса и не переиспользуется, даже для ключа, который журнал забыл.
> `workflows.start(record.workflowKey(stage), name, input)` атомарно резервирует попытку и единственный `RunId`
> до передачи исполнителю; повтор ключа с другим workflow, входом, проектом или ревизией отклоняется. Ключ включает
> lifetime процесса, поэтому remove/open не оживляет старый запрос. `workflows.get`/`cancel` доступны только текущему
> script item владельца; запрос отмены отличается от terminal после подтверждённой очистки. Журнал активной попытки
> не истекает; после её закрытия действует обычное удержание, а забытая попытка никогда не создаётся повторно.
> Этапы и правила GitHub остаются в версионируемом харнессе.
> Оффлайн мини-аппы (тогл `harness.commands`, по умолчанию true; только Desktop): скрипт объявляет фиксированные
> команды `commands.define` (программа и аргументы в исходнике, параметры — целым аргументом по regex), а
> `commands.run` запускает их в проекте через `LocalCommands` (`scheduler:api`, без расширения и разбиения слов; на Windows спецсимволы `cmd.exe` — отказ) — из кнопок,
> включая WebView-мост, таймеров и событий без хода агента. Сохранение скрипта использует общий гейт;
> нажатия исполняют сохранённые unguarded-декларации; не из хуков, 2 запуска на харнесс, вне области проекта — отказ.
> Защищённые команды (`requiresDecision`, `commands.runForProcess`, тогл `harness.process_actions`, по умолчанию false)
> требуют отдельного решения в нативных деталях харнесса по точному process/attempt/input/SHA/project/repo/argv/timeout.
> Зашифрованный host-owned журнал не доступен через ScriptData; `Grant`, `ui_call` и callback согласия не дают.
> До Claim решение отзывается; после одноразового допуска неопределённое исполнение только сверяется, не повторяется.
> `commands.resultForProcess` читает сохранённый исход по decision id без запуска команд, включая Git: `Recorded`
> содержит только exit code или отказ, атомарно сохранённый с Completed, без stdout/stderr. Старый Completed без квитанции
> не доказывает успех; timeout/cancellation остаётся Executing. Exit code 0 не заменяет проверку внешнего результата.
> Клетки организма харнесса используют общий профильный режим, включая продолжение после restart/division.
> `features:app-logs:{api,impl}` — раздел «Логи приложения» в настройках Desktop (macOS/Windows/Linux),
> доступный без профиля, тогл `app_logs.enabled` (по умолчанию true): копирование и сохранение последних 10 минут,
> ZIP всех доступных логов и открытие папки. Хранение в `core:logging` ограничено пятью сутками независимо от тогла;
> ротация по размеру может сокращать доступную историю.
> `features:app-update:{api,impl}` — самообновление установленного desktop-приложения (macOS, Windows) из GitHub Releases
> (тогл `app_update.enabled`, по умолчанию true): машина в AppScope (`AppUpdateMachineKey`, запуск — `AppStartup` desktop)
> проверяет последний релиз `vX.Y.Z` при запуске и раз в 6 ч; кнопка «Обновить» в шапке сайдбара студии скачивает сборку
> с проверкой SHA-256, на macOS меняет бандл из DMG, на Windows тихо ставит установщик Inno Setup поверх, после выхода
> приложения helper запускает новую версию (desktop выходит штатно по `Restarting`).
> Раздел настроек «Обновления» (`SettingsSection.Updates`, `AppUpdatesRoute`, только Desktop, тогл `app_update.enabled`, без профиля):
> версия сборки, поезд и бандлы из манифеста запущенного поезда (`AppBuildInfoSource`), состояние машины обновления,
> «Проверить обновления» и «Обновить и перезапустить» (ручная установка — страница релиза). В бета-канале страница показывает поезда, подготовленные к следующему запуску, и «нужна полная установка платформы» (`isPlatformUpdateRequired`: бета включена, лаунчера нет, релиза новее нет); смена канала сразу запускает проверку, а идущая проверка перезапускается после завершения. Здоровье бандлов не показывается:
> `BundleRegistry` недоступен коду фич. Активно только в установленной
> релизной сборке (`-Dheartbeat.app.update.repository` у release-лаунчера). На Linux кнопка сразу открывает страницу

> `features:service-as-ui:{api,impl}` — интерфейсы агента (тогл `service_ui.enabled`, по умолчанию true): профильная

> полное доверие — без дополнительного вопроса; ограниченное доверие и Ask-хуки требуют подтверждения.
> Скилл `adaptive-subagents`.
> `features:project-config:{api,impl}` — живая конфигурация проекта (тогл `project_config.enabled`, по умолчанию true;
> только Desktop): харнессы (скиллы, инструкции, шаблоны, скрипты-инструменты `hs_*`, workflow, политика инструментов),
> их интерфейсы и выученные инструкции хранятся в папке `.heartbeat` проекта читаемыми файлами и переносятся файлом
> `.hbai` (ZIP той же раскладки с `manifest.json`). Фичи-владельцы реализуют SPI `ConfigSection` (`project-config:api`,
> пакет `spi`): кодируют, проверяют (код компилируется) и применяют свои сущности своими интентами — оркестратор чужие
> данные не пишет; другие фичи шлют машине только чтение и скрытие, доверие и запись файлов — `Internal` её экрана. Профильная машина `ProjectConfigMachineKey` хранит привязки «сущность ↔ юнит папки» с дайджестами
> файлов и сущности: изменились только файлы — предложение, только сущность — запись обратно, оба — конфликт;
> Переформатирование распознаётся по каноническому виду. Предложения из папок и `.hbai` проверяются по формату,
> код компилируется; явное доверие пользователя разрешает точный снимок без дополнительного LLM-ревью.
> Разделы выключенных фич не
> предлагаются и не перезаписываются. Папки читаются без следования по symlink в границах `ConfigLimits`, архивы — без
> распаковки на диск. Экран — раздел настроек «Конфигурация»: изменения на доверие, проекты и их юниты, «Сохранить в
> проект», экспорт и импорт `.hbai` (в профиль или в папку проекта).
> `features:worktree-mode:{api,impl}` — изолированные задачи кодинга (тогл `worktree_mode.enabled`, по умолчанию true;
> только Desktop): git worktree на чат, инструменты `configure_build`/`run_build`/`build_status`, завершение PR или merge.
> Sandbox mode (`worktree_mode.sandbox`, по умолчанию true) предлагает в новом чате переключатель «Песочница»
> вместо «Worktree»; обычный Worktree выбирается из меню «+». Переключатель изначально выключен, выбор сохраняется
> до подготовки и переживает рестарт; старые записи без выбора следуют тоглу. Песочница содержит только исходники: `run_build`
> снимает снимок файлов (`refs/heartbeat/snapshots/*`) и собирает его в тёплом build-слоте репозитория
> (`<git-common-dir>/heartbeat-worktree-data/slots`, до 4 на репозиторий; слоты под OS-локом чужого воркера пропускаются,
> лишние сверх лимита, без песочниц или без проекта удаляются `SandboxSlotSweeper`); оставленная песочница чистит
> игнорируемые выходы.
> Push и fetch веток из инструментов песочницы (`push` у `sandbox_commit`, `fetch` у `sandbox_checkout`/`sandbox_merge`) —
> тогл `worktree_mode.sandbox_remote` (по умолчанию false); без него аргументов нет в схемах.
> Очередь сборок одна на машину: вес по типу сборки (`WorktreeBuildKind`), бюджет по CPU/RAM или лимит из раздела
> настроек «Сборки» (`BuildCapacitySettings`, app-wide), round-robin между проектами, без обгона тяжёлой сборки.
> `configure_build`, `run_build` и `cancel_build` используют общий гейт; полные план/команда и рабочая область
> привязаны к одноразовому разрешению и сверяются перед исполнением.
> `features:planning-mode:{api,impl}` — режим планирования чатов студии (тогл `planning_mode.enabled`, по умолчанию true):
> агент и пользователь вырабатывают план задачи; план — `planning/<chat>/plan.md` в каталоге профиля (рядом ревизия и
> дайджест последней записи студии, правка файла вне студии загружается новой внешней ревизией), метаданные и привязки
> сессий — строгий KV-индекс. Профильная машина `PlanningMachineKey` проверяет ревизии записей (агент и пользователь не
> перетирают друг друга), предложение, утверждение и старт реализации. Студия привязывает нативную сессию чата к плану
> перед каждой отправкой, поэтому план и режим переходят в новые сессии; `PlanContextHook` добавляет блок плана с
> правилами режима к промпту один раз на ревизию контекста, а без ревизии контекста — с каждым промптом, и при смене
> ревизии, режима или статуса (движки с инструкциями на ход читают его из инструкций); правка пользователя или файла
> вне студии во время хода сообщается в следующем результате инструмента. Инструменты `plan_read` (перечитывает файл), `plan_write` (весь план или секция от прочитанной ревизии),
> `plan_propose` (карточка) объявлены во всех сессиях при тогле. `PlanningReadOnlyHook` сообщает о действии вне
> сценария планирования: в Ask/Automatic это запрос подтверждения; Full Trust не применяет permission-хуки.
> Классификатор `isReadOnlyCommand` ограничен известными формами; неизвестная команда требует решения общего гейта.
> В студии режим включают пунктом «Планирование» в «+» (новый или простаивающий обычный чат) или стартером «Спланировать
> фичу» (`template_plan`); выходят выключением чипа плана в композере или того же пункта (`Leave` → Detached).
> Последняя карточка `plan_propose` текущей ревизии даёт «Утвердить / Доработать / Реализовать / Открыть» (повторные,
> старые и без ревизии — только «Открыть»; «Реализовать» неактивна, пока идёт ход); редактор сохраняет правку от открытой
> ревизии и с правками закрывается только после сохранения или «Отмены»; при новой ревизии и наличии правок предлагает
> «Загрузить» или «Перезаписать», без правок подтягивает новую ревизию; «Открыть» доступна только при тогле. «Реализовать» переключает тот же чат (`ImplementPlan`, `StudioPlanImplementer`): маршрут того же движка и
> подключения применяется к текущей сессии, иначе или со свежим контекстом — rollover с выжимкой; режимы Worktree/Sandbox
> готовят изолированную копию для чата, Organism делает чат чатом организма с планом в цели (обрезка до 20 000 символов).
> `features:auto-continue:{api,impl}` — автопродолжение диалога в обычных чатах студии (тогл `auto_continue.enabled`,
> по умолчанию true; помощники и организмы не участвуют): режим чата «Выкл / Подсказки / Автопилот» в меню композера,
> умолчание для новых чатов — только Выкл или Подсказки. Профильная машина `AutoContinueMachineKey` держит режимы (KV профиля)
> и фазы чатов (в памяти); чаты в «Выкл» не читаются, включение просит хост оценить последний ход. После штатного конца хода продолжатель — служебный промпт `IsolatedPrompts` без инструментов на
> модели чата или выбранной в настройках — читает диалог (`dialogOf`: сообщения человека, реплики автопилота с пометкой,
> последний текст каждого хода агента без инструментов и размышлений; бюджет 16k) и заметку плана, отвечает JSON
> `continue / done / needs_user` с 1–3 вариантами (невалидный ответ — один повтор). Подсказки показываются над композером:
> клик отправляет вариант сообщением человека, карандаш вставляет в поле. Автопилот отправляет первый вариант после
> отсчёта («Отправить сейчас / Править / Стоп») ходом чата `autopilot-…` (не человеческий промпт, только если чат не
> менялся), пометка «Автопилот» в ленте — по нативному ходу. Он стоит на паузе, пока агент ждёт человека (анкета,
> чек-лист, предложенный план, пробуждение планировщика, сжатие; запрос разрешения держит ход открытым), и останавливается с переходом в «Подсказки»:
> готово, нужен человек, лимит авто-ходов (сбрасывается сообщением человека), повтор почти того же текста, ошибка,
> вмешательство человека, рестарт. Решений за человека (разрешения, утверждение плана) не принимает. Студия сообщает о
> ходах через `StudioTurnLifecycle` координатора запусков и отправляет реплики как SPI `AutoContinueHost`; фича живёт
> в фундаменте рядом с `ai-studio`. Раздел настроек «Автопродолжение» (`AutoContinueRoute`): режим новых чатов, модель
> продолжателя (модель чата или модель профиля по умолчанию), лимит, пауза, число вариантов.
> Обработка поезда desktop (`-Pheartbeat.trainShrink=off|shrink|obfuscate`, по умолчанию `off`): `foundation` и каждый бандл
> проходят отдельный прогон ProGuard по явной SDK-границе (`heartbeatTrain { sdk(...) }`, `verifyTrainSdk`); keep-правила SDK
> генерирует `generateTrainSdkRules`, остальное — `platform-main/desktop/train-rules.pro`. `verifyShrunkTrain` запускает
> обработанный поезд headless (все бандлы `Healthy`), маппинги — `build/train/mapping-*.txt`, имена в логах
> восстанавливает `scripts/retrace.py` (в логе строка `Launch: train=…`). CI (`bundle-train`) собирает поезд с `obfuscate`,
> гоняет `verifyShrunkTrain` перед записью и публикует маппинги ассетами пре-релиза `train-*`.
> Правила и ограничения — `.claude/rules/bundles.md`.
> Приложение: `core:mvi`, фичи `welcome`, `ai-studio`, `toggles-panel`, `ai-engine:connections` (профильные маршруты); платформенные входы подключены к root.

## Жёсткие правила (нарушение = блокер ревью)

1. **Зависимости**: `feature:impl` → только `api` других фич. От любого `…:impl` (фич и `core`) зависит только `:platform-main:di-bundle` и сборщики бандлов desktop `:bundles:<name>` (правила — `.claude/rules/bundles.md`) (проверяет `build-logic` через `heartbeat.detekt`, подключённый ко всем модулям). `core` не знает о `features` и `design-system`. `feature:api` без Compose/UI.
2. **State-machine фичи живёт в `api`** (`machineSpec { }` из `core:state-machine:api`, движок KStateMachine скрыт в `impl`): все состояния, интенты, переходы, эффекты, outputs. Машина запускается в скоупе фичи; другие фичи общаются с ней только через `MachineKey` + `MachineRegistry` → `send(key, Public intent)`. Никаких прямых ссылок на классы `impl`. Исключения для сервисных контрактов, SPI и координации с хостом перечислены в `.claude/rules/feature-api.md`.
3. **UI-состояние** — FlowMVI-стор в `impl`. Машина = бизнес-флоу фичи, стор = состояние экрана. Стор не дублирует состояние машины, а отражает его (`reflect` из `core:state-machine:flowmvi-ext`).
4. **Навигация** — только Decompose через `core:navigation`: фичи открывают друг друга `Navigator.navigate(Route)`, маршруты — `@Serializable @SerialName` в `api`, `RouteEntry` в реестре своего скоупа (`binding<ProfileRouteBinding>()` / `AppRouteBinding`), результаты — `ResultContract`. Никаких navigation-compose и ссылок на чужие компоненты.
5. **DI** — только Metro (`@Inject`, `@ContributesBinding`, `@ContributesIntoMap/Set`, `@GraphExtension`). Граф — только в `platform-main:di-bundle`; скоупы app → profile → feature → screen, граф фичи — через `retainedGraph` (`core:di:ext`). Никаких сервис-локаторов и `object`-синглтонов с состоянием. На desktop Metro статичен внутри каждого бандла; между бандлами — только рантайм-реестр `core:bundles` на границе (исключение для сборщиков `:bundles:<name>`, код фич его не видит; `.claude/rules/bundles.md`). Профильные фичи бандла — в его `@GraphExtension(ProfileScope::class)`, а состояние фундамента бандл берёт только из `Foundation*Bindings` (`core:bundles:api`) типами `api`-модулей; в `web` уже собраны plant-uml-support, browser, chromium-bridge и research-chat, в `agent-runtime` — harness, organic-ai, scheduler, adaptive-subagents, worktree-mode, project-config и agent-learning, в `studio` — feedback, effort-configuration, planning-mode, autocomplete, ai-session-engine-transfer, context-window-optimization, computer-use, questionnaire и checklist.
6. **Логирование через `core:logging` (Napier), без флуда**: действия пользователя, значимые переходы состояния, запросы и изменения конфигурации — `INFO`; одноразовые диагностические решения — `DEBUG`. Частые внутренние события (токены/дельты, ревизии, polling, проекции состояния, обычный IO БД/DataStore) — только `VERBOSE`, включаемый явно через trace. Логируй границы операции и итог, не каждый элемент на `DEBUG`/`INFO`; не дублируй централизованные логи. Частые обработчики и выделенные из них helpers помечай `@HighFrequency` из `core:logging`: detekt `HighFrequencyLog` запрещает внутри `DEBUG`/`INFO` (также в повторяемых `update`-лямбдах). Ошибки сохраняют `WARN`/`ERROR` с throwable; понижение уровня ошибки для обхода правила запрещено. `println`, `android.util.Log`, `NSLog` запрещены. Секреты и API-ключи не логируются никогда. Проверяется detekt (набор `heartbeat`, `lint/detekt-rules`).
7. **Цвета/типографика/отступы — только токены `design-system`**. `Color(0x…)`, `.sp`/`.dp`-литералы для стилей вне `design-system` запрещены.
8. **Тоглы** — через `core:feature-toggles` (`FeatureToggles` для чтения, регистрация `@IntoSet`); новая функциональность за тоглом по умолчанию.
9. **Корутины**: без `GlobalScope`, `runBlocking` в продовом коде; диспетчеры инжектятся (`DispatcherProvider`); `CancellationException` не глотаем.
   **Ошибки**: никакая ошибка не игнорируется — минимум `log.w(e)`/`log.e(e)` с throwable или проброс (rethrow / `Result.failure(e)`); исключение — `CancellationException`, она пробрасывается. `@Suppress` этих правил запрещён (`ForbiddenSuppress`).
10. **Detekt + compose-rules + ktlint** обязаны быть зелёными при локальной проверке изменений (`verify`). При сборке релиза эти линтеры не запускаются и в `release.yml` не добавляются. `@Suppress` — только с комментарием-причиной.
11. Версии библиотек приложения — только в `gradle/libs.versions.toml`. Python-инструмент проверки коммитов закреплён отдельно (`scripts/requirements-commit-policy.txt`).
12. **PR содержит законченную фичу; коммиты — отдельные логические шаги.** Каждый коммит должен оставлять проект собираемым, тесты изменённого поведения идут вместе с реализацией. Бюджет каждого коммита — **не более 25 000 токенов полного diff**; свыше 20 000 токенов или 20 файлов — предупреждение. Ориентир — 700–1000 добавленных и удалённых строк суммарно, без жёсткого лимита строк и размера PR. Команды — скилл `verify`.

## Команды

Windows: `.\gradlew.bat`, macOS: `./gradlew`.

```
./gradlew :platform-main:desktop:run           # desktop
./gradlew :platform-main:android:assembleDebug # android
./gradlew allTests                             # все KMP-тесты
./gradlew jvmTest                              # быстрые тесты всех KMP-модулей (JVM)
./gradlew :platform-main:di-bundle:jvmTest     # сборка всего Metro-графа + интеграционные тесты скоупов
./gradlew detekt                               # lint всех модулей (без type resolution, быстро)
./gradlew detekt --auto-correct                # автоформат ktlint-правил
./gradlew :<module>:detektMainJvm              # detekt с type resolution (KMP jvm; :platform-main:desktop:detektMain для JVM-модулей)
./gradlew :lint:detekt-rules:test              # тесты собственных правил detekt
./gradlew --stop                               # после правки lint/detekt-rules: detekt кэширует classloader правил в демоне
./gradlew :<module>:dependencies --configuration commonMainApi   # проверить граф
```

> **`./gradlew --stop` завершает само приложение.** Desktop, запущенный из IDE, — потомок демона Gradle, поэтому
> остановка демонов убивает всё дерево процессов вместе с Heartbeat: мгновенно, без стектрейса и без отчёта о краше,
> с потерей текущего хода агента. Агент, работающий внутри Heartbeat, такую команду не выполняет — движок Pi
> показывает последствия в запросе подтверждения (`PiHostCommands`). Останавливай демоны только
> во внешнем терминале и только не из-под агента.

iOS собирается только на macOS (Xcode, `platform-main/ios/`). На Windows iOS-таргеты не компилируются — проверяй `commonMain` через `jvmTest`.

## Как работать

- Перед изменением фичи прочитай её `api` (машину) — это спецификация поведения.
- Планируй логические коммиты до реализации; перед каждым коммитом проверяй staged diff через `python scripts/check_commit_size.py --staged`, перед ревью — весь диапазон PR через `--base <base-ref> --head HEAD`. Промежуточные fixup-коммиты объединяй с соответствующим логическим шагом перед ревью; правки по итогам ревью — отдельный коммит с трейлером `Addresses-Review:` (скилл `pr-fix`); исправление уже запушенного шага draft PR, который ведёт `open-pr`, — отдельный коммит с трейлером `Fixes-Step: <sha шага>`.
- PR, исправляющий issue, помечает полноту: `Closes #N` — полностью (бот закроет issue при мерже), `Refs #N` / `Part of #N` — часть (issue остаётся открытой). Маркеры для одной issue не смешиваются; подробнее — «Ревью PR» в `AGENTS.md`.
- UI до кода → скилл `ui-prototype`: случаи из его §0 (новый экран, режим, диалог, флоу, `Hb*`-компонент, заметное
  изменение раскладки, переход, анимация) — сначала макет в `design/` (pen.dev) и явное согласование пользователя;
  без него — блокер ревью. Макет — на всех типах экранов Phone / Tablet / Desktop, подход desktop-first: сначала
  Desktop, затем адаптации (`design/README.md` 2.5);
  исключение — фичи только для Desktop.
- После правок кода → скилл `verify` (сборка, тесты, detekt). Для крупных изменений — субагент `architecture-reviewer`.
- Перед выпуском → скилл `e2e-regression`: прогон основных функций на упакованном `HeartbeatE2E`
  (тестовый flavor) с детерминированной мок-моделью вместо запросов к боевым ИИ; блокер и критические
  дефекты чинятся сразу (`open-pr` + `pr-review-and-fix` + merge + пересборка), минорные — пакетом в конце,
  технический долг — в issues.
- CI — подтверждение, а не отладка: проверяй локально, пушь готовые шаги, держи PR draft до готовности, не перезапускай
  CI и не добавляй workflow, джобы, платформы и триггеры без согласия пользователя. Обязательных сборок на PR нет:
  затронутые модули на ОС, которой нет локально, агент при необходимости собирает сам (`module-build.yml`).
  Commit policy обязательна для каждого PR.
  Подробно — раздел «CI» в `AGENTS.md`, правила workflow — `.claude/rules/ci.md`.
- Мерж в `master` — только после ревью: комментарий `/reviewed [sha]` владельца превращается в approve бота. Правила для агента — раздел «Ревью PR» в `AGENTS.md`.

| Задача | Скилл (`.claude/skills/`) |
