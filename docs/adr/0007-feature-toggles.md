# ADR-0007: Фича-тоглы и единая платформа управления ими

- Статус: принято
- Дата: 2026-09-27
- Затрагивает: `core:feature-toggles:{api,impl}`, `platform-main:di-bundle`, фичи (объявление и регистрация тоглов)

## Контекст

ADR-0001 закрепил: новая функциональность — за тоглом, тоглы — тонкая обёртка над хранилищем плюс внутренняя панель
управления, пока только локально. Требования:

- фичи (в том числе их `api`-модули) объявляют тоглы и читают их реактивно, не зная о хранилище;
- все тоглы приложения видны в одном месте, каждое изменение логируется (политика логирования, тег `FT`);
- значения переживают перезапуск и не зависят от профиля — это настройка устройства, а не пользователя;
- позже появится удалённый источник значений: его добавление не должно менять код фич.

## Решение

Два модуля по схеме `api` / `impl` (как `core:datastore`).

**`core:feature-toggles:api`** — только `kotlinx-coroutines-core`, без Metro и DataStore; его можно подключать
в `api`-модули фич.

- `FeatureToggle<T>` — объявление: `Flag` (Boolean, по умолчанию `false`) и `Choice` (одна строка из `options`).
  Ключ `<owner>.<name>` (`[a-z][a-z0-9_]*` через точку, ≤ 128 символов), владелец — первый сегмент ключа.
  Проверки — в конструкторе.
- `FeatureToggles` — чтение для кода фич: `observe(toggle): Flow<T>`, `get(toggle)`.
- `FeatureToggleControl` — единая точка управления, бэкенд панели: `registered`, `observeStates()`
  (`ToggleState`: значение и `ToggleSource`), `setOverride`, `reset`, `resetAll`.
- `ToggleSource` — порядок источников: `LocalOverride` → `Default`. Удалённый источник встанет между ними.

**`core:feature-toggles:impl`** (подключается только в `di-bundle`)

- Регистрация — Metro-мультибиндинг `Set<FeatureToggle<*>>` в `AppScope` (`@Provides @IntoSet` в интерфейсе фичи
  с `@ContributesTo(AppScope::class)`), объявлен с `@Multibinds(allowEmpty = true)`. Два разных объявления с одним
  ключом — ошибка при создании реестра.
- Локальные переопределения — app-хранилище `core:datastore`, KV `core_feature_toggles`; запись на тогл, имя = ключ.
  Отсутствие записи = default. Сохранённое значение, которого больше нет в `Choice.options`, читается как отсутствующее.
- Переопределение, равное default, остаётся переопределением: при смене default оно сохраняется.
- Переопределять и сбрасывать можно только зарегистрированные тоглы (иначе `IllegalArgumentException`); изменения
  сериализованы. Читать можно любой тогл,
  но незарегистрированный или объявленный иначе, чем в реестре, даёт одно предупреждение на ключ.
- Логи `FT`: реестр при создании (`I`), действующие переопределения при первом чтении (`I`), каждое изменение
  `key: old (source) -> new (source)` (`I`), вычисленные значения (`D`), расхождения (`W`). Хранилище значения
  не логирует (`areValuesLogged = false`), чтобы они не дублировались.
- Сбой хранилища не доходит до кода фич: `FeatureToggles` отдаёт default (`W`). `FeatureToggleControl` пробрасывает
  ошибку — панель покажет её.
- `FeatureToggleControl` лежит в `api` (панели нужен контракт без `impl`), но импортировать его могут только
  `features/toggles-panel`, `platform-main` и сам `core:feature-toggles` — это проверяет хук `check-conventions.sh`.

UI панели — отдельная фича `features/toggles-panel` поверх `FeatureToggleControl`. Её делаем после
`design-system`: экран без токенов и `Hb*`-компонентов нарушил бы правила проекта.

## Альтернативы

| Вариант | Плюсы | Минусы | Почему нет |
|---|---|---|---|
| Один модуль `core:feature-toggles` с реализацией | меньше модулей | `api` фич тянул бы DataStore и Metro-реализацию | фичам в `api` нужен только контракт |
| `set` в `FeatureToggles` (как в первом наброске скилла) | один интерфейс | любой код фичи может менять конфигурацию | управление отделено: `FeatureToggleControl` + проверка хуком |
| Отдельный модуль `core:feature-toggles:control` | запрет на уровне Gradle | ещё один модуль ради одного интерфейса | пока хватает хука; вынесем, если появятся другие потребители |
| Переопределения в хранилище профиля | разные наборы у разных аккаунтов | тоглы — настройка сборки / устройства; при выходе переопределения пропадали бы | app-владелец |
| Отдельный `owner` в объявлении | произвольная группировка | дублирует префикс ключа, может с ним разойтись | владелец выводится из ключа |
| Типизированный `Choice<E : Enum<E>>` | безопасность типов | хранение по имени, лямбды в `data class`, сложнее панели | строки с проверкой `options`; маппинг — в фиче |
| Готовая библиотека (Firebase Remote Config и т. п.) | удалённое управление сразу | внешний сервис, нет desktop, лишняя зависимость | нужна пока только локальная платформа |

## Последствия

- Новая функциональность: тогл `Flag` с `default = false` + регистрация `@IntoSet`. Скилл `feature-toggle`.
- Удаление тогла: объявление, ветки кода и регистрация. Сохранённый ключ игнорируется, `resetAll` удаляет и его.
  Ключи не переиспользуются.
- Удалённый источник значений — отдельный ADR: новый `ToggleSource.Remote` между `LocalOverride` и `Default`,
  реализация в `impl`. Код фич не меняется.
- Панель тоглов (`features/toggles-panel`) — после `design-system`. В release она будет доступна по решению отдельного ADR.
