# ADR-0008: Общие скрываемые полосы прокрутки

- Статус: принято
- Дата: 2026-09-26
- Затрагивает: design-system:tokens/layouts/components/catalog

## Контекст

Пользователь требует scrollbar на каждой горизонтальной и вертикальной прокручиваемой
поверхности. В покое он скрыт, появляется при прокрутке или наведении на область полосы.
Длинная история содержит строки разной высоты, в том числе Markdown и результаты
инструментов. Оценка общей высоты через среднюю высоту видимых строк меняет размер
и положение ползунка по мере измерения новых строк.

## Решение

Общая реализация в `layouts` работает на Compose Foundation на всех платформах.
`hbHorizontalScroll` и `hbVerticalScroll` объединяют обычную прокрутку и overlay scrollbar.
`hbScrollbars` подключает только полосу к существующему `ScrollState` или `LazyListState`.
`HbLazyColumn` и `HbLazyRow` включают её по умолчанию. Полоса не создаёт отдельный
scrollable-контейнер и не меняет размеры содержимого при появлении.

Для измеренного `ScrollState` используются реальные размер viewport, диапазон и offset.
Для lazy-списка каждый элемент соответствует одной логической единице. Размер ползунка
зависит от viewport, фиксированного токена условного размера элемента и количества
элементов. Измеренные высоты видимых элементов не меняют размер ползунка.
Положение вычисляется по логическому содержимому до и после viewport, с дробным
прогрессом внутри пересекающих его строк. Привязки начала/конца точные. Это индикатор
позиции в элементах, а не ложная оценка ещё не измеренного количества пикселей.
Изменение самого набора данных или размера окна может изменить размер ползунка.
Переход мышью уточняет позицию ограниченным бинарным поиском по логическим координатам
и измеренному viewport назначения. Он не измеряет и не хранит всю историю.

Появление и скрытие анимируют только прозрачность. Невидимая зона полосы принимает
наведение; drag и нажатие на track перемещают тот же scroll state. Колесо над остальной
поверхностью сохраняет штатную обработку. Без переполнения полоса не рисуется и
не забирает ввод. Размеры и время скрытия находятся в токенах.

В `HbStickyHeaderHost` полоса располагается снаружи fade/capture слоя и закреплённого
заголовка. У вложенного `HbLazyColumn` устанавливается `showScrollbar = false`, чтобы
на один viewport приходилась одна полоса. Код внутри сообщения может иметь отдельную
горизонтальную полосу; вложенная вертикальная прокрутка tool payload не возвращается.

`HbTextField` и composer используют общий state-based `BasicTextField` с доступным
`ScrollState`, сохраняя публичный controlled-контракт `value`/`onValueChange`.
При принятых изменениях сохраняется состояние редактирования; внешняя замена, очистка
и отклонение ввода синхронизируются отдельно. В `Platform` поле также использует этот
редактор и токены DS: прежние версии Fluent/macOS value-based редакторов не предоставляют
свой scroll state. Нативные кнопки и темы продолжают использовать платформенные киты.
Это явный общий Foundation fallback для полей, без смены зависимостей или версий.

## Альтернативы

| Вариант | Причина отказа |
|---|---|
| Отдельные desktop scrollbar из каждого кита | Разное поведение платформ, нет общего контракта редакторов |
| Средняя высота видимых lazy-строк | Изменяет thumb при переходе между короткими и высокими строками |
| Измерить весь список заранее | Ломает виртуализацию и дорого для длинной истории |
| Постоянно видимая полоса с выделенным местом | Добавляет визуальный шум и меняет компактную компоновку |

## Последствия

Новые прокручиваемые поверхности обязаны использовать общие обёртки или явно подключать
`hbScrollbars` к своему состоянию. Нельзя добавлять второй владелец прокрутки ради полосы.
Нужно проверять hover, idle, wheel, drag, оба направления и неоднородные lazy-строки.
Правило закреплено в `.claude/rules/design-system.md`.
