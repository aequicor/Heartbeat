# Дизайн Heartbeat

Макеты интерфейсов Heartbeat — файлы [pen.dev](https://pen.dev/) (`.pen`) в этой папке. Любой новый экран, флоу,
компонент дизайн-системы или заметное изменение раскладки сначала появляется здесь, согласуется с пользователем
и только потом переносится в Compose. Процедура для агента — скилл [`ui-prototype`](../.claude/skills/ui-prototype/SKILL.md);
этот README — справочник для людей и агентов.

Ключевые принципы:

- **Код ведёт токены, макет их зеркалит.** Источник правды по цветам, типографике, отступам и размерам —
  `design-system/tokens` и KDoc. `design/system/heartbeat.lib.pen` повторяет их переменными.
- **Агент пишет `.pen` сам, без ИИ и MCP pen.dev.** Формат `.pen` — открытый JSON. Агент (Claude Code desktop,
  Codex или Heartbeat) правит его как обычный файл, а pen.dev служит человеку для просмотра и ручных правок.
- **Агент видит картинку, а не только JSON.** После правки агент открывает файл в pen.dev и смотрит снимок окна
  (раздел 4.3).
- **Макет живой.** Изменение UI правит `.pen` в том же PR, что и код.

## 1. Установка и настройка pen.dev

ИИ-провайдера, MCP и CLI pen.dev подключать не нужно: проект их не использует.

### Десктоп-приложение (основной вариант)

| ОС | Установка |
|---|---|
| macOS | Скачать DMG на [pen.dev](https://pen.dev/), перенести pen.dev в «Программы», запустить. |
| Windows | Скачать установщик, установить, запустить. |
| Linux x64 | Скачать AppImage: `chmod +x Pen-linux-x86_64.AppImage`, затем `./Pen-linux-x86_64.AppImage`. |

Вход в аккаунт pen.dev — только если приложение его потребует. В **Settings → Agents** провайдеров не подключать,
в **Settings → MCP** ничего не включать.

### Расширение VS Code / Cursor (альтернатива)

Extensions → найти **pen.dev** → Install. Файл `.pen` открывается во встроенном редакторе. Когда агент меняет файл
на диске, IDE предлагает **Reload** — выбирайте его. **Ignore** оставит старую версию и при сохранении затрёт правку
агента.

### Работа с файлами репозитория

1. Открывайте файлы прямо из рабочей копии (`File → Open` → `design/features/<feature>/<feature>.pen`), не загружайте
   их в веб-версию.
2. Сохраняйте `Cmd/Ctrl+S`. Резервная копия pen.dev не заменяет git: важное коммитит агент или вы.
3. Перед переключением ветки, `git pull` или правкой агентом закройте файл в pen.dev или сохраните его: иначе
   приложение может перезаписать новую версию с диска своей.
4. При конфликте в `.pen` сохраните обе версии, возьмите одну за основу и повторите вторую правку в pen.dev. Конфликт
   в JSON руками не разрешается.
5. Для агента в Claude Code desktop один раз выдайте доступ computer-use к приложению pen.dev (по запросу агента).
   В Heartbeat — включите в настройках «Управление компьютером» и права macOS (запись экрана).

## 2. Иерархия

### 2.1. Файлы в `design/`

```
design/
  README.md                         этот файл
  system/
    heartbeat.lib.pen               библиотека: переменные-токены и Hb*-компоненты
    assets/                         иконки и иллюстрации библиотеки (если не из встроенных наборов pen.dev)
  features/
    <feature>/                      имя совпадает с features/<feature> в коде
      <feature>.pen                 все экраны, состояния, локальные компоненты и переходы фичи
      assets/                       картинки, на которые ссылается <feature>.pen
  flows/
    <flow>.pen                      сквозные флоу через несколько фич (онбординг, первый запуск)
```

- Один `.pen` на фичу: агенту и человеку нужно открыть один файл, чтобы увидеть фичу целиком.
- Фича из нескольких экранов-разделов, которая не помещается в один файл, делится на
  `features/<feature>/<area>.pen` (`settings/engines.pen`). Каждый файл импортирует библиотеку.
- Компонент, нужный двум и более фичам, переезжает в `system/heartbeat.lib.pen` и одновременно в `design-system:components`.
- PNG, видео и экспорты в репозиторий не коммитятся: их можно сгенерировать заново.
- `*.pen` помечены `binary` в `.gitattributes`. Diff JSON не читается человеком и не расходует бюджет commit policy,
  поэтому ревьюер смотрит макет в pen.dev.

### 2.2. Внутри `.pen`

В pen.dev нет страниц: файл — один холст. Порядок задают верхнеуровневые кадры-секции, расположенные колонками
слева направо:

| Секция (`name`) | Что внутри | Соответствие в коде |
|---|---|---|
| `Screens` | Кадры экранов `<Screen> / <State>`: `Chat / Empty`, `Chat / Streaming`, `Chat / Error` | `ui/<Screen>Screen.kt`, состояния FlowMVI-стора |
| `Components` | Локальные компоненты фичи (`reusable: true`): `Chat / MessageRow` | `ui/` фичи; общие — `design-system:components` |
| `Transitions` | Раскадровки переходов и анимаций (2.3) | `core:navigation` (`NavTransition`), `HbMotion` |
| `Notes` | Открытые вопросы, решения согласования | Раздел «Дизайн» описания PR |

Правила имён и узлов:

- `id` — стабильный kebab-case путь: `chat-empty`, `chat-empty/header`, `chat-empty/header/title`. Агент не
  переименовывает существующие `id`: на них ссылаются `ref`, `descendants` и обсуждение в PR.
- `name` — человекочитаемое имя слоя: `Chat / Empty`, `Header`, `Send button`.
- Кадр экрана — реальный размер хоста: desktop **1280×800** и компактная ширина **420** (как в скриншот-тестах);
  mobile **390×844** — только если экран есть на Android/iOS.
- Каркас окна (сайдбар, шапка, titlebar) — `ref` на компоненты библиотеки `Window / *`. Фича рисует только своё
  содержимое, как и в коде.
- Состояния показываются полностью: пустое, загрузка, ошибка, длинный русский текст, hover/selected/disabled/фокус,
  если они меняют вид. Каждое состояние, которое видит пользователь, — отдельный кадр.

### 2.3. Анимации и переходы

pen.dev не умеет прототипирование и анимацию, поэтому переход — это раскадровка в секции `Transitions`:

- кадр-ряд `<From> → <To>` с ключевыми кадрами «до», «середина» (если важна) и «после» — `ref` на кадры `Screens`;
- рядом узел `note` с полями:
  ```
  trigger:    клик по строке чата
  transition: NavTransition.Expand(sharedKey = "chat-row/<id>")   # Default | None | Fade | Modal | Expand
  duration:   HbMotion.normalMillis                              # fastMillis | normalMillis | slowMillis
  easing:     стандартный (FastOutSlowIn)
  reduced:    мгновенно (HbMotion.isReducedMotion)
  ```
- микро-анимации внутри экрана (появление кнопки, раскрытие панели) — тот же формат с `trigger` и токеном длительности.

Новая длительность или кривая — сначала токен в `HbMotion`, затем ссылка на него в заметке.

### 2.4. Библиотека `heartbeat.lib.pen`

- **Темы** — две оси: `"themes": { "mode": ["light", "dark"], "host": ["desktop", "mobile"] }`. Это пресеты
  `forHost(isDark, isDesktop)` из `HbTheme`. Кит (Material / Fluent / macOS) осью не является: стиль один — плотный
  плоский. Отдельный кадр под кит рисуется только тогда, когда у кита отличается поведение или раскладка.
- **Переменные** называются как токены Kotlin, через точку:

  | Переменная `.pen` | Токен |
  |---|---|
  | `colors.<name>` (`colors.brand`, `colors.textSecondary`, `colors.outline`) | `HbTheme.colors.<name>` |
  | `surfaces.<name>` (`surfaces.sidebar`, `surfaces.composer`) | `HbTheme.surfaces.<name>` |
  | `spacing.<name>` (`spacing.m` = 8) | `HbTheme.spacing.<name>` |
  | `shapes.<name>` (`shapes.medium`) | `HbTheme.shapes.<name>` |
  | `dimensions.<name>` (`dimensions.headerHeight` = 44) | `HbTheme.dimensions.<name>` |
  | `typography.<style>.size` / `.lineHeight` / `.weight` | `HbTheme.typography.<style>` |
  | `motion.<name>` | `HbTheme.motion.<name>` |

  Значения задаются на каждую комбинацию тем, как в пресетах (`Light`, `Dark`, `DesktopLight`, `DesktopDark`).
- **Компоненты** называются как в Compose: `HbButton / Primary / Regular`, `HbSettingsRow`, `HbTextField / Focused`,
  `Window / Sidebar`. Варианты — отдельные компоненты или состояния в имени, не разные `id` с одинаковым `name`.
- Менять токены в библиотеке без кода нельзя. Новый токен предлагается в макете (заметка `proposal: …` и временная
  переменная `proposal.<name>`), а после согласования появляется в `design-system/tokens` с KDoc и переименовывается
  в обычную переменную.

## 3. Влияние на Time to Market

Обязательное согласование макета добавляет к UI-задаче один короткий шаг до кода, но убирает дорогие шаги после.

- **Исправление дешевле до кода.** Правка кадра в pen.dev — минуты: перетащить, перекрасить, переписать текст.
  Та же правка после реализации — правка экрана, стора, строк ресурсов, превью, скриншот-тестов и повторное ревью.
  Переделки из-за «не то, что я хотел» исчезают из конца цикла.
- **Человек видит интерфейс до реализации.** Сейчас интерфейс можно оценить только после того, как агент его
  собрал и запустил. С макетом вы смотрите и правите его в pen.dev сразу, своими руками, а не описанием словами.
- **Меньше тяжёлых и непонятных интерфейсов.** Агент сначала думает о раскладке, иерархии и состояниях на холсте,
  где лишний элемент сразу виден, и только потом пишет Compose.
- **Короче ревью.** Ревьюер проверяет соответствие согласованному макету, а не спорит о вкусе в PR. Спор о дизайне
  решён до кода, в PR остаются архитектура и качество.
- **Параллельность.** Пока вы согласовываете макет, агент может готовить машину, стор и данные фичи: они от
  раскладки не зависят.
- **Переиспользование.** Библиотека компонентов и токенов в pen.dev даёт быстрые макеты из готовых блоков, а
  согласованные макеты — готовые раскладки для следующих фич.
- **Живая документация.** `design/` всегда показывает, как устроен интерфейс сейчас: онбординг нового участника,
  e2e-регрессия и обсуждение следующих изменений начинаются с макета, а не с запуска приложения.

Цена этапа: время на макет и ожидание ответа пользователя. Поэтому этап не нужен для правок без визуального эффекта
(раздел 4.1), а агент просит согласовать сразу все кадры задачи, а не по одному.

## 4. Инструкции для ИИ-агентов

### 4.1. Когда этап обязателен

**Макет и согласование обязательны** для:

- нового экрана, режима, диалога или флоу;
- нового или изменённого `Hb*`-компонента дизайн-системы;
- заметного изменения раскладки, иерархии или состояний существующего экрана;
- нового перехода или анимации.

**Можно без макета:**

- изменения без визуального эффекта (логика, стор, данные);
- тексты и локализация, не меняющие раскладку;
- исправление бага, после которого UI совпадает с уже согласованным макетом;
- изменение значения токена — с обновлением переменной в `heartbeat.lib.pen` в том же PR.

Сомневаешься — делай макет. Если pen.dev недоступен или снимок окна сделать нельзя, этап не пропускается:
остановись и спроси пользователя.

### 4.2. Процесс

1. **Прочитать контекст.** `.claude/rules/design-system.md` (принципы эталона), `heartbeat.lib.pen` и существующий
   `.pen` фичи. Если файл открыт у пользователя — сначала перечитать его с диска: ручные правки человека авторитетны.
2. **Набросать макет.** Новые кадры и переходы по разделу 2, только из компонентов и переменных библиотеки.
   Чего нет в библиотеке — сначала компонент в библиотеке (и затем в `design-system:components`).
3. **Посмотреть самому** (4.3) и исправить то, что видно: перекрытия, обрезанный текст, неровные отступы, лишние
   элементы, нарушения принципов эталона.
4. **Коммит макета** отдельным шагом: `design(<feature>): макет <что>`.
5. **Согласование.** Назвать пользователю файл и кадры (`design/features/chat/chat.pen` → `Chat / Empty`,
   `Chat / Streaming`), коротко объяснить решения и открытые вопросы, ждать явного «согласовано». Правки словами —
   внести и показать снова. Правки руками в pen.dev — перечитать файл, закоммитить как
   `design(<feature>): правки пользователя`, учесть.
6. **Зафиксировать.** В описании PR — раздел «Дизайн»: путь, кадры, SHA коммита согласованного макета, кто и когда
   согласовал.
7. **Реализовать** по 4.5, затем **сверить** по 4.6.

Без согласованного макета UI-код из раздела 4.1 не пишется: `pr-review` считает это блокером.

### 4.3. Как агент видит макет

Агент не использует ИИ и MCP pen.dev. Картинку он получает снимком окна приложения pen.dev:

- **Claude Code desktop:** открыть файл (`open -a pen.dev design/features/<f>/<f>.pen` на macOS), затем
  computer-use в режиме окна приложения: снимок окна pen.dev, zoom на нужный кадр. Экран у пользователя не забирается.
- **Heartbeat:** инструменты `window_list` → `window_capture` / `window_screenshot` / `window_zoom` окна pen.dev
  (скилл `computer-use`; нужен включённый доступ агента к компьютеру).
- Навигация по холсту — штатными действиями pen.dev: выделить кадр в списке слоёв и «приблизить к выделению»,
  «Zoom to fit». Сам `.pen` через интерфейс pen.dev агент не правит: правки — только в JSON.
- Linux: computer-use недоступен — агент сообщает, что не видел картинку, и полагается на взгляд пользователя.

Снимок — для проверки агентом; в репозиторий и PR он не попадает.

### 4.4. Правила правки `.pen` как JSON

pen.dev рекомендует править файл через свои инструменты. Проект сознательно правит JSON напрямую, поэтому:

- не менять поле `version` и формат, который записал pen.dev; новая версия pen.dev — пересохранить файл в приложении
  отдельным коммитом;
- `id` уникальны в файле и стабильны (2.2); новые узлы — новыми `id`, чужие узлы не переписывать целиком;
- разметка — flex-полями (`layout: vertical|horizontal`, `gap`, `padding`, `justifyContent`, `alignItems`,
  `width/height: fill_container|fit_content`); абсолютные `x`/`y` — только у верхнеуровневых кадров на холсте;
- цвета, размеры, отступы — только `$`-переменные библиотеки (`"fill": "$colors.surface"`), без hex; число без
  переменной допустимо, только если такого токена нет и в заметке предложен новый;
- компоненты — `ref` с переопределениями и `descendants`, а не копии узлов; синтаксис ссылки на компонент
  импортированной библиотеки повторяй за тем, что записал pen.dev (импорт библиотеки в новый файл впервые делает
  человек в pen.dev: Libraries → Import);
- текст — реальный, на русском, включая длинные варианты; не «Lorem ipsum»;
- иконки — узлы `icon` из встроенных наборов, ближайшие к иконкам `design-system:resources`;
- после правки файл должен открыться в pen.dev. Не открылся — откатить свою правку и сделать её меньшими шагами,
  а не чинить вслепую;
- конфликты в `.pen` не разрешаются в JSON (раздел 1).

Минимальный кадр экрана:

```json
{
  "id": "chat-empty",
  "type": "frame",
  "name": "Chat / Empty",
  "x": 0, "y": 0, "width": 1280, "height": 800,
  "layout": "horizontal",
  "theme": { "mode": "light", "host": "desktop" },
  "fill": "$surfaces.backdrop",
  "children": [
    { "id": "chat-empty/sidebar", "type": "ref", "ref": "window-sidebar" },
    {
      "id": "chat-empty/content", "type": "frame", "name": "Content",
      "width": "fill_container", "height": "fill_container",
      "layout": "vertical", "justifyContent": "center", "alignItems": "center", "gap": "$spacing.l",
      "children": [
        { "id": "chat-empty/content/title", "type": "text", "content": "Начните новый чат",
          "fill": "$colors.textPrimary", "fontSize": "$typography.title.size", "fontWeight": "600" }
      ]
    }
  ]
}
```

### 4.5. Перенос макета в Compose

pen.dev экспортирует только HTML, поэтому перенос в Compose делает агент по таблице соответствий:

| `.pen` | Compose |
|---|---|
| `$colors.*`, `$surfaces.*`, `$spacing.*`, `$shapes.*`, `$dimensions.*`, `$typography.*`, `$motion.*` | `HbTheme.colors.*`, `HbTheme.surfaces.*`, `HbTheme.spacing.*` и т.д. (2.4) |
| `ref` на `HbX / Variant` | `HbX(style = HbXStyle.Variant, …)` |
| `ref` на `Window / *` | ничего: каркас рисует хост |
| `frame` `layout: vertical` / `horizontal` / `none` | `Column` / `Row` / `Box` |
| `gap`, `padding` | `Arrangement.spacedBy(HbTheme.spacing.*)`, `Modifier.padding(HbTheme.spacing.*)` |
| `width: fill_container` / `fit_content` | `Modifier.weight(1f)` или `fillMaxWidth()` / размер по содержимому |
| `justifyContent`, `alignItems` | `Arrangement.*`, `Alignment.*` |
| `text` | `HbText` со стилем `HbTheme.typography.*`, строка — в `strings.xml` |
| `icon` | ближайшая иконка `design-system:resources` |
| Кадры `<Screen> / <State>` | состояния FlowMVI-стора и `@Preview` на каждое |
| Раскадровка `Transitions` | `NavTransition` в `RouteEntry`/`navigate`, длительности `HbTheme.motion` |

- Число без переменной в макете не становится `.dp`/`.sp`-литералом: сначала токен с KDoc.
- Компонента нет в `design-system:components` — сначала компонент по скиллу `design-system` (реализации китов,
  превью, каталог), затем экран.
- `@Preview` повторяют кадры макета: те же состояния, light/dark.

### 4.6. Сверка после реализации

1. Снять реальный экран: desktop (`./gradlew :platform-main:desktop:run` и снимок окна) или рендер превью/скриншот-теста
   jvmTest; для компонентов — `platform-main:uikit-sandbox`.
2. Сравнить с кадрами макета в pen.dev: раскладка, отступы, иерархия, состояния, тексты.
3. Расхождение по ошибке — исправить код. Сознательное (ограничение платформы, кита) — исправить макет отдельным
   коммитом и перечислить в разделе «Дизайн» PR.
4. Перед ready — проверить, что макет в PR соответствует итоговому коду.
