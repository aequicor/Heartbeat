# Дизайн Heartbeat

Макеты интерфейсов Heartbeat — файлы [pen.dev](https://pen.dev/) (`.pen`) в этой папке. Любой новый экран, флоу,
компонент дизайн-системы или заметное изменение раскладки сначала появляется здесь, согласуется с пользователем
и только потом переносится в Compose. Процедура для агента — скилл [`ui-prototype`](../.claude/skills/ui-prototype/SKILL.md);
этот README — справочник для людей и агентов (форматы, соответствия, правила); при расхождении в последовательности
шагов источник правды — скилл.

Ключевые принципы:

- **Код ведёт токены, макет их зеркалит.** Источник правды по цветам, типографике, отступам и размерам —
  `design-system/tokens` и KDoc. `design/system/heartbeat.lib.pen` повторяет их переменными.
- **Агент пишет `.pen` сам, без ИИ и MCP pen.dev.** Формат `.pen` — открытый JSON. Агент (Claude Code desktop,
  Codex или Heartbeat) правит его как обычный файл, а pen.dev служит человеку для просмотра и ручных правок.
- **Агент видит картинку, а не только JSON.** После правки агент открывает файл в pen.dev и смотрит снимок окна
  (раздел 4.3).
- **Макет живой.** Изменение UI правит `.pen` в том же PR, что и код.

## 1. Установка и настройка pen.dev

ИИ-провайдера, MCP и CLI pen.dev подключать не нужно: проект их не использует. Процесс проверен на pen.dev 1.2.20
(macOS, приложение `Pen`, bundle id `dev.pencil.desktop`) с форматом файла `"version": "2.21"`.

### Десктоп-приложение (основной вариант)

| ОС | Установка |
|---|---|
| macOS | Скачать DMG на [pen.dev](https://pen.dev/), перенести pen.dev в «Программы», запустить. |
| Windows | Скачать установщик, установить, запустить. |
| Linux x64 | Скачать AppImage: `chmod +x Pen-linux-x86_64.AppImage`, затем `./Pen-linux-x86_64.AppImage`. |

Вход в аккаунт pen.dev — только если приложение его потребует. ИИ-провайдеров в настройках не подключать,
в **Settings (⚙️) → MCP** ничего не включать.

### Расширение VS Code / Cursor (альтернатива)

Extensions → найти **pen.dev** → Install. Файл `.pen` открывается во встроенном редакторе (открылся как текст —
команда «pen.dev: Toggle Design Mode»). Когда агент меняет файл на диске, загрузите версию с диска, прежде чем
править: сохранение старой версии затрёт правку агента.

### Работа с файлами репозитория

1. Открывайте файлы прямо из рабочей копии (`File → Open` → `design/features/<feature>/<feature>.pen`), не загружайте
   их в веб-версию.
2. Сохраняйте `Cmd/Ctrl+S`. Резервная копия pen.dev не заменяет git: важное коммитит агент или вы.
3. **Приложение не перечитывает файл, изменённый на диске.** После правки агентом, переключения ветки или
   `git pull` закройте вкладку (`File → Close Tab`) и откройте файл заново (`open -a Pen <file>` на macOS).
   Свои несохранённые правки сначала сохраните: иначе сохранение старой вкладки затрёт новую версию с диска.
4. При конфликте в `.pen` сохраните обе версии (`git show :2:<path> > ours.pen`, `git show :3:<path> > theirs.pen`),
   возьмите одну за основу (`git checkout --ours|--theirs -- <path>`) и повторите вторую правку в pen.dev.
   Конфликт в JSON руками не разрешается.
5. Для агента в Claude Code desktop один раз выдайте доступ computer-use к приложению pen.dev (по запросу агента).
   В Heartbeat — включите в настройках «Управление компьютером» и права macOS (запись экрана).

### Ручная правка макета

Раскладка в макетах свободная, поэтому любой элемент двигается мышью. Проверено на pen.dev 1.2.20.

| Что нужно | Как |
|---|---|
| выбрать элемент внутри экрана | `Cmd`+щелчок (глубокое выделение) или слой в панели Layers |
| передвинуть, изменить размер | перетащить элемент или его маркеры; точные числа — X/Y/W/H в панели свойств |
| поправить текст | двойной щелчок до текстового слоя, `Enter`, ввести текст, `Esc` |
| сменить цвет, размер шрифта, скругление | значения привязаны к токенам: щелчок по значку переменной справа от значения открывает список — выбрать другой токен или `None` и задать значение вручную (агент при переносе предложит токен) |
| передвинуть кнопку, поле, пилюлю или надпись внутри них | всё это обычные группы и слои: `Cmd`+щелчок выделяет глубже, `Esc` поднимает выделение на уровень выше; иконку внутри лучше выбрать слоем в Layers и тащить за её рамку |
| поменять текст кнопки или пилюли | размер группы не подстраивается под текст: после правки подвиньте соседей и поправьте ширину (W) |
| поправить оформление кнопки у всех экранов сразу | на экранах кнопки — отсоединённые копии, библиотека на них не влияет: правка мастера в `heartbeat.lib.pen` попадёт на экраны, только когда агент заменит копии (скажите ему) |
| тёмный вариант экрана | это ссылка на светлый экран с темой dark: правьте светлый, тёмный обновится сам |
| поведение (растяжение, прокрутка, другие размеры) | текстом в поле `Context` компонента: выделить компонент → панель свойств → «Context» |

После правки — `Cmd+S` и сообщение агенту: он перечитает файл с диска и закоммитит ваши изменения.

## 2. Иерархия

### 2.1. Файлы в `design/`

```
design/
  README.md                         этот файл
  system/
    heartbeat.lib.pen               библиотека: переменные-токены, иконки, иллюстрации, Hb*-компоненты
    design-system.pen               страница дизайн-системы: стили, иконки, иллюстрации, компоненты с описанием
    assets/                         иконки и иллюстрации библиотеки (если не из встроенных наборов pen.dev)
  features/
    <feature>/                      имя совпадает с features/<feature> в коде
      <feature>.pen                 все экраны, состояния, локальные компоненты и переходы фичи
      assets/                       картинки, на которые ссылается <feature>.pen
  flows/
    <flow>.pen                      сквозные флоу через несколько фич (онбординг, первый запуск)
```

Сейчас в `design/`:

| Файл | Что внутри |
|---|---|
| `system/heartbeat.lib.pen` | определения: токены `design-system/tokens` переменными, 113 иконок `HbIcons`, 8 иллюстраций `HbIllustration`, базовые `Hb*`-компоненты |
| `system/design-system.pen` | страница дизайн-системы: цвета (светлая и тёмная тема), типографика, отступы и формы, иконки, иллюстрации, компоненты с назначением и Compose API |
| `features/ai-studio/ai-studio.pen` | студия: пустой чат, беседа, идёт ход агента, тёмная тема, выезжающий сайдбар на телефоне (`Studio / Drawer`) |
| `features/ai-engine/connections.pen` | визард подключения движка: движок, авторизация (и ошибка), модели, тёмная тема |

- Один `.pen` на фичу: агенту и человеку нужно открыть один файл, чтобы увидеть фичу целиком.
- Фича из нескольких экранов-разделов, которая не помещается в один файл, делится на
  `features/<feature>/<area>.pen` (`settings/engines.pen`). Каждый файл импортирует библиотеку.
- Компонент, нужный двум и более фичам, переезжает в `system/heartbeat.lib.pen` и одновременно в `design-system:components`.
- PNG, видео и экспорты в репозиторий не коммитятся: их можно сгенерировать заново.
- `*.pen` помечены `-diff` в `.gitattributes`: diff JSON не читается человеком и не расходует бюджет commit policy,
  поэтому ревьюер смотрит макет в pen.dev. Перевод строк нормализуется и слияние работает как для текста.
  Содержимое `.pen` код-ревью не проходит — его проверяет согласование; полный JSON: `git show --text <sha> -- design/`.

### 2.2. Внутри `.pen`

В pen.dev нет страниц: файл — один холст. Файл фичи содержит две верхнеуровневые области, **прямо на тёмном холсте, без
белой подложки**; пользовательские пути лежат **справа** от экранов:

| Область (`name`) | Что внутри | Соответствие в коде |
|---|---|---|
| **Экраны** | Для каждого экрана и состояния — две строки: светлая и тёмная тема; в строке — Desktop, Tablet, Phone. Кадр экрана с **серой обводкой**, подпись над ним: `Desktop · светлая`. Тёмный кадр — `ref` на светлый с темой dark | `ui/<Screen>Screen.kt`, состояния FlowMVI-стора, ветки по ширине |
| **Пользовательские пути** | Только Desktop, светлая тема, **без обводки**: цепочка кадров, над каждым подпись «Состояние: …», между кадрами — гибкая стрелка (ломаная со скруглёнными углами, контрастного оранжевого цвета) с короткой подписью | сценарии, `NavOptions(transition = …)`, анимации `HbMotion` |

Компонентов в файле фичи нет: общие — в `heartbeat.lib.pen`, а показ компонентов, стилей, иконок и иллюстраций — на
странице `design-system.pen` («Дизайн-система»). Каркас окна (сайдбары студии и настроек) там же, в разделе «Каркас окна».

**Аннотации — в поле `Context` компонента.** Описание поведения (растяжение, прокрутка, прибито к краю, граница 720/1200,
размер касания) пишется в `context` того узла, к которому оно относится: выделите компонент и откройте блок «Context» в
панели свойств. Поле хранится в `.pen`, поэтому версионируется вместе с макетом. Комментарии pen.dev (инструмент
«Comment») хранятся в облаке pen.dev, а не в файле: агент не может их ни создать, ни прочитать, и в git они не попадают —
для решений, которые должен знать агент и ревьюер, их не используйте. Заметки (`note`) на холсте не рисуем: они
перекрывают вёрстку.

**Раскладка свободная.** Контейнеры экранов и компонентов — `layout: none`, каждый элемент стоит по `x`/`y` с числовыми
`width`/`height`: так человек двигает что угодно мышью. Flex (`layout: vertical|horizontal`) нет нигде, в том числе внутри
компонентов тоже нет. **На экранах компоненты — отсоединённые копии** (в pen.dev: `Detach Instance`): внутри экземпляра
pen.dev не даёт перетаскивать вложенные элементы мышью (работают только поля X/Y), а у копии двигается всё. Мастера
остаются в `heartbeat.lib.pen` и на странице `design-system.pen`; копия называется как компонент
(`HbButton / Ghost / Small`), её слои — `<id копии>-<id в библиотеке>`. Экземпляром (`ref`) остаются только цельные
узлы: иконки, иллюстрации, разделитель и тёмная копия экрана. Кадр показывает один размер окна, поэтому всё, что
зависит от размера и прокрутки, описывается текстом в `Context` компонента.

Правила имён и узлов:

- `id` — стабильный kebab-case без `/` (формат запрещает `/` в `id`): `chat-empty`, `chat-empty-header`,
  `chat-empty-header-title`. `/` встречается только в ключах `descendants` (`"send-button/label"`). Агент не
  переименовывает существующие `id`: на них ссылаются `ref`, `descendants` и обсуждение в PR.
- `name` — человекочитаемое имя слоя: `Chat / Empty`, `Header`, `Send button`.
- Кадр экрана — по одному на каждый форм-фактор: `<Screen> / <State> / Phone` (**390×844**), `/ Tablet` (**834×1112**),
  `/ Desktop` (**1280×800**), при необходимости `/ Desktop compact` (**420×800**) — правило 2.5.
- Каркас окна: светофор — `Window / Traffic lights` библиотеки; сайдбар хоста рисуется на каждом экране копией
  (образец — `design-system.pen`, «Каркас окна»). Фича рисует только своё содержимое, как и в коде.
- Тёмная тема — не копия кадра: кадр экрана светлой темы помечен `reusable: true`, рядом `ref` на него с
  `"theme": { "mode": "dark", "host": "desktop" }` и именем `<Screen> / <State> (dark)`. Переменные с темами
  перекрашивают вариант сами.
- Состояния показываются полностью: пустое, загрузка, ошибка, длинный русский текст, hover/selected/disabled/фокус,
  если они меняют вид. Каждое состояние, которое видит пользователь, — отдельный кадр.

### 2.3. Анимации и переходы

pen.dev не умеет прототипирование и анимацию, поэтому переходы показываются **стрелками** в области «Пользовательские
пути»:

- цепочка кадров `Desktop · светлая` (`ref` на экраны); над каждым — подпись «Состояние: <Screen> / <State>»;
- стрелки, их подписи, точки начала и карточки состояний (`Стрелка · шаг N`, `Подпись перехода`, `callout-*`) —
  отдельные узлы верхнего уровня холста поверх области «Пути»; ячейка кадра — подпись + кадр (отсюда высота ячейки
  больше кадра на высоту подписи);
- над стрелкой короткая подпись (1–2 строки, мелкий шрифт): что делает пользователь; подробности — как меняется
  наполнение экрана — аннотацией в `Context` компонента-триггера. Стрелка **начинается на компоненте-триггере**
  (кнопка, строка списка), гибко огибает зазор (ломаная со скруглёнными углами) и **заканчивается на компоненте
  следующего кадра, к которому относится изменение**, а если меняется весь экран — на левой границе кадра. Конец
  стрелки компонент не выделяет;
- **стрелка не режет контент экранов**: к компоненту она идёт **под кадрами** (свободная полоса под экранами) и
  подходит к нему снизу;
- элемент, который нужно выделить или описать его состояния, описывается **карточкой под экраном** (заголовок +
  текст состояний), к которой от элемента ведёт стрелка (вниз и влево к правому краю карточки). Карточки одного
  кадра — **вертикальным столбцом**, левее элемент — выше, поэтому стрелки короткие и не пересекаются;
- **прозрачность стрелок** 0,65 (`opacity`), чтобы они не заслоняли контент;
- **цвет стрелок**: основной — `annotation.accent` (оранжевый); стрелки, которые **пересекаются**, берут разные цвета
  из `annotation.accent2…4` (голубой, зелёный, фиолетовый); карточка наследует цвет своей стрелки. Это переменные
  только для пометок, не токены приложения;
- тип перехода и анимацию пишем в `Context` кадра-получателя или компонента, который двигается:
  ```
  trigger:    клик по строке чата
  transition: NavTransition.Expand(sharedKey = "chat-row-<id>")   # Default | None | Fade | Modal | Expand
  ```
  Длительность и кривую навигационных переходов задаёт `core:navigation`, макет их не выбирает;
- микро-анимации внутри экрана (появление кнопки, раскрытие панели) — в `Context` анимируемого узла:
  ```
  trigger:    наведение на строку
  duration:   HbMotion.fastMillis                                # fastMillis | normalMillis | slowMillis
  easing:     стандартный (FastOutSlowIn)
  reduced:    мгновенно (HbMotion.isReducedMotion)
  ```

Новая длительность или кривая — сначала токен в `HbMotion`, затем ссылка на него в `Context`.

### 2.4. Библиотека `heartbeat.lib.pen`

Библиотека содержит все токены (275 переменных, из них 4 пометочных `annotation.*` и 6 `effects.fade.*` — не токены приложения: цвета и поверхности четырёх пресетов, размеры, типографика, формы,
отступы, тени, анимации, шрифты), реальные иконки и иллюстрации приложения и базовые компоненты: кнопки, иконка-кнопка,
строка навигации, разделитель, поля, бейджи, переключатель, строки вызова инструмента, пилюли и кнопки композера,
баннер ошибки, знак студии, светофор окна. Документирует её страница `design-system.pen`.

- **Иконки** — компоненты `hb-icon-<name>` (`HbIcons / <Name>`): контуры из `HbIcons.kt` в сетке 20×20, узел `path`.
  Экземпляр: `{"type": "ref", "ref": "hb:hb-icon-chevron-right", "width": 14, "height": 14,
  "stroke": "$hb:colors.textSecondary", "strokeWidth": 0.98}` — толщина линии 1.4 × размер / 20; у залитых иконок
  (`HomeFilled`, `More`, `MoreVertical`, `Stop`) вместо `stroke` — `fill`. Иконку внутри копии компонента заменяют
  другим узлом `ref` на `hb:hb-icon-*` на том же месте.
  Встроенные наборы pen.dev (`icon`, lucide) не используются.
- **Иллюстрации** — компоненты `hb-illustration-<kind>` 240×180: слои из `IllustrationArtwork.kt` в цветах темы.
- **Шрифт.** Приложение рисует шрифтом хоста (SF Pro на macOS, Segoe UI на Windows), но pen.dev берёт шрифты только
  из своего каталога: системные имена (`SF Pro`, `Menlo`) молча заменяются запасным шрифтом. Поэтому
  `typography.family` = `Inter` (ближайший по метрикам), `typography.code.family` = `JetBrains Mono`; ширина строк
  в макете может немного отличаться от приложения.
Значения переменных сняты с Kotlin-пресетов (`HbColors.Light/Dark/DesktopLight/DesktopDark` и т.д.), включая
производные цвета; при изменении токена переменная правится в том же PR. Компоненты добавляются по мере надобности.

**Импорт** (проверено на pen.dev 1.2.20): превращать файл в библиотеку через меню pen.dev не нужно, достаточно
`imports`. В файле фичи всё из библиотеки адресуется через алиас:

| Что | Запись |
|---|---|
| импорт | `"imports": { "hb": "../../system/heartbeat.lib.pen" }` (путь относительный) |
| иконка, иллюстрация, разделитель | `"ref": "hb:hb-icon-plus"`, `"ref": "hb:hb-illustration-welcome"`, `"ref": "hb:hb-divider"` |
| замена иконки в копии компонента | вместо слоя иконки — узел `{"type": "ref", "ref": "hb:hb-icon-search", …}` |
| кнопка, поле, пилюля и другие составные компоненты | копия структуры из `heartbeat.lib.pen` (не `ref`), 2.2 |
| переменная | `"fill": "$hb:colors.surface"` |
| тема | `"theme": { "hb:mode": "dark", "hb:host": "desktop" }` |

Внутри самой библиотеки переменные и `id` пишутся без алиаса (`$colors.surface`).

- **Темы** — две оси: `"themes": { "mode": ["light", "dark"], "host": ["desktop", "mobile"] }`. Это пресеты
  `HbColors.forHost(isDark, isDesktop)` / `HbSurfaceColors.forHost(...)` и desktop/mobile-пресеты метрик и типографики. Кит (Material / Fluent / macOS) осью не является: стиль один — плотный
  плоский. Отдельный кадр под кит рисуется только тогда, когда у кита отличается поведение или раскладка.
- **Переменные** называются как токены Kotlin, через точку:

  | Переменная `.pen` | Токен |
  |---|---|
  | `colors.<name>` (`colors.brand`, `colors.textSecondary`, `colors.outline`) | `HbTheme.colors.<name>` |
  | `surfaces.<name>` (`surfaces.sidebar`, `surfaces.composer`) | `HbTheme.surfaces.<name>` |
  | `spacing.<name>` (`spacing.m` = 8) | `HbTheme.spacing.<name>` |
  | `shapes.<name>` (`shapes.medium`) | `HbTheme.shapes.<name>` |
  | `dimensions.<name>` (`dimensions.headerHeight` = 44) | `HbTheme.dimensions.<name>` |
  | `typography.<style>.size` / `.lineHeight` / `.weight` | `HbTheme.typography.<style>` (`lineHeight` в `.pen` — множитель `fontSize`: значение = lineHeight / fontSize) |
  | `elevation.<name>` | `HbTheme.elevation.<name>` |
  | `motion.<name>` | `HbTheme.motion.<name>` |

  Градиенты (`HbTheme.gradients`) не зеркалятся: стиль плоский, декоративные градиенты запрещены правилом ДС.

  Значения задаются на каждую комбинацию тем, как в пресетах (`Light`, `Dark`, `DesktopLight`, `DesktopDark`).
- **Компоненты** называются как в Compose: `HbButton / Primary / Regular`, `HbSettingsRow`, `HbTextField / Focused`,
  `Window / Sidebar`. Варианты — отдельные компоненты или состояния в имени, не разные `id` с одинаковым `name`.
- Менять токены в библиотеке без кода нельзя. Новый токен предлагается в макете (заметка `proposal: …` и временная
  переменная `proposal.<name>`), а после согласования появляется в `design-system/tokens` с KDoc и переименовывается
  в обычную переменную.

**Эффекты** (раздел «Design system / Effects» страницы `design-system.pen`). Однострочный текст, который не поместился,
в приложении не обрывается, не уходит за рамку и не получает многоточие, а **гаснет к правому краю**
(`HbText`, `maxLines = 1`, ширина `dimensions.textOverflowFade` = 24; полный текст — в тултипе). В макете: строка
с `clip: true` и поверх неё прямоугольник шириной 24 у правого края с линейным градиентом
`$hb:effects.fade.<поверхность>` → `$hb:surfaces.<поверхность>`, где поверхность — фон строки (`sidebar`, `selected`,
`assistant`, `composer`, `header`, `backdrop`); `rotation: 270` ведёт градиент слева направо. Текст, который
в макете может не поместиться (названия чатов в узком сайдбаре), оформляй так же. Строки сайдбара оставляют справа
место под действия по наведению (сессии 56, проект 28): текст гаснет до этого места, градиент сменяется сплошной
поверхностью.

### 2.5. Адаптивность: phone / tablet / desktop

Heartbeat — мультиплатформенное приложение (Android, iOS, desktop), поэтому верстка каждого экрана должна быть
показана на всех трёх типах экранов. Подход — **desktop-first**: сначала проектируется и согласуется Desktop (основной
кадр и эталон, `.claude/rules/design-system.md`), а Phone и Tablet — его адаптации: то, что остаётся, сжимается,
сворачивается или уходит в drawer. Границы и пресеты — из кода (`HbDimensions`, `HbTheme`):

| Форм-фактор | Ширина окна | Хост и пресет | Кадр | Что обычно меняется |
|---|---|---|---|---|
| **Phone** | `< 720` (`compactBreakpoint`) | `host: mobile` — крупные зоны касания, шрифты мобильного пресета | 390×844 | сайдбар уходит в выезжающую панель, список → раздел с «назад», один столбец, композер на всю ширину |
| **Tablet** | `720 … 1200` | `host: mobile` (планшеты Android/iOS) | 834×1112 (портрет); 1194×834 (альбом) — только если раскладка отличается | сайдбар или список + детали рядом (`HbAdaptivePane`), колонка контента ограничена по ширине |
| **Desktop** | `≥ 1200` (`expandedBreakpoint`) | `host: desktop` — плотный пресет | 1280×800 | сайдбар, до двух панелей чата рядом, окно edge-to-edge |

Правила:

0. **Порядок: Desktop → Tablet → Phone.** Сначала Desktop-кадры (и `Context` компонентов) — их согласует пользователь;
   затем из них выводятся Tablet и Phone, и в `Context` компонента фиксируется, что именно адаптируется
   относительно Desktop (что скрывается, что сворачивается, что переносится). Новую функциональность Phone/Tablet не
   добавляют: всё, что есть на Desktop, достижимо и на малых экранах, только в другой форме. В Compose так же: базовая
   вёрстка — широкая, а `compactBreakpoint` / `expandedBreakpoint` задают её адаптации.
1. **Каждый экран, диалог и флоу** рисуется кадрами `<Screen> / <State> / Phone`, `/ Tablet`, `/ Desktop` с темой
   `hb:host` = `mobile` для Phone и Tablet и `desktop` для Desktop. Размеры и шрифты на mobile-кадрах берутся из
   mobile-пресета (переменные библиотеки переключаются темой), а не масштабируются с desktop.
2. **Узкое окно desktop** (`< 720`) ведёт себя как Phone, но с desktop-пресетом; отдельный кадр `/ Desktop compact`
   рисуется, если отличаются размеры или поведение (например, студия: светофор macOS, шапка).
3. **Состояния, не меняющие раскладку** (ошибка поля, тёмная тема, hover), достаточно показать на одном форм-факторе;
   состояния, которые меняют вёрстку (пустой чат, беседа, идёт ход агента), — на всех трёх.
4. `Context` компонента перечисляет, что происходит на границах `720` и `1200`: что превращается в drawer,
   как список и детали делят ширину, что прокручивается, что прибито, каким остаётся размер касания.
5. **Исключение — фичи только для Desktop** (`computer-use`, браузер, `chromium-bridge`, харнесс-скрипты, самообновление):
   достаточно Desktop (и Desktop compact); в `Context` экрана «только Desktop» и причина. Без явной причины исключения нет.
6. **Новый или изменённый `Hb*`-компонент** показывается в двух пресетах — desktop и mobile (размеры, зона касания) —
   в `heartbeat.lib.pen` и на странице `design-system.pen`.
7. Согласование идёт в два шага: сначала Desktop (+ `Context`), потом адаптации Phone и Tablet одним сообщением (4.2).

## 3. Влияние на Time to Market

Обязательное согласование макета добавляет к UI-задаче один короткий шаг до кода, но убирает дорогие шаги после.

- **Исправление дешевле до кода.** Правка кадра в pen.dev — минуты: перетащить, перекрасить, переписать текст.
  Та же правка после реализации — правка экрана, стора, строк ресурсов, превью, скриншот-тестов и повторное ревью.
  Переделки из-за «не то, что я хотел» исчезают из конца цикла.
- **Человек видит интерфейс до реализации.** Сейчас интерфейс можно оценить только после того, как агент его
  собрал и запустил. С макетом вы смотрите и правите его в pen.dev сразу, своими руками, а не описанием словами.
- **Меньше тяжёлых и непонятных интерфейсов.** Агент сначала думает о раскладке, иерархии и состояниях на холсте,
  где лишний элемент сразу виден, и только потом пишет Compose.
- **Короче ревью.** Ревьюер проверяет соответствие согласованному макету, а не спорит о вкусе в PR. Спор о дизайне
  решён до кода, в PR остаются архитектура и качество.
- **Параллельность.** Пока вы согласовываете макет, агент может готовить машину, стор и данные фичи: они от
  раскладки не зависят.
- **Переиспользование.** Библиотека компонентов и токенов в pen.dev даёт быстрые макеты из готовых блоков, а
  согласованные макеты — готовые раскладки для следующих фич.
- **Живая документация.** `design/` всегда показывает, как устроен интерфейс сейчас: онбординг нового участника,
  e2e-регрессия и обсуждение следующих изменений начинаются с макета, а не с запуска приложения.

Цена этапа: время на макет и ожидание ответа пользователя. Поэтому этап не нужен для правок без визуального эффекта
(раздел 4.1), а агент просит согласовать сразу все кадры задачи, а не по одному.

## 4. Инструкции для ИИ-агентов

### 4.1. Когда этап обязателен

**Макет и согласование обязательны** для:

- нового экрана, режима, диалога или флоу;
- нового или изменённого `Hb*`-компонента дизайн-системы;
- заметного изменения раскладки, иерархии или состояний существующего экрана;
- нового перехода или анимации.

**Можно без макета:**

- изменения без визуального эффекта (логика, стор, данные);
- тексты и локализация, не меняющие раскладку;
- исправление бага, после которого UI совпадает с уже согласованным макетом;
- изменение значения токена — с обновлением переменной в `heartbeat.lib.pen` в том же PR.

**Экран, у которого ещё нет `.pen`**, получает макет только затронутых экранов и состояний, а не всей фичи.
**Исправление дефекта e2e-регрессии**, возвращающее задуманное поведение, — багфикс без макета. Если исправление
меняет раскладку, автономный цикл e2e для этого дефекта останавливается: макет и согласование, как обычно.

Сомневаешься — делай макет. Если pen.dev недоступен или снимок окна сделать нельзя (Linux, Codex без инструмента
снимка), этап не пропускается: скажи пользователю, что картинку не видел, и попроси проверить кадры в pen.dev
до согласования.

### 4.2. Процесс

1. **Прочитать контекст.** `.claude/rules/design-system.md` (принципы эталона), `heartbeat.lib.pen` и существующий
   `.pen` фичи. Если файл открыт у пользователя — сначала перечитать его с диска: ручные правки человека авторитетны.
2. **Набросать макет.** Desktop-first (2.5): сначала Desktop-кадры; после согласования Desktop — Tablet и Phone как их
   адаптации. Новые кадры и переходы по разделу 2, только из компонентов и переменных библиотеки.
   Чего нет в библиотеке — сначала компонент в библиотеке (и затем в `design-system:components`).
3. **Посмотреть самому** (4.3) и исправить то, что видно: перекрытия, обрезанный текст, неровные отступы, лишние
   элементы, нарушения принципов эталона.
4. **Коммит макета** отдельным шагом: `design(<feature>): макет <что>`.
5. **Согласование** в два шага (desktop-first): сначала Desktop-кадры, затем адаптации Tablet и Phone. Назвать
   пользователю файл и кадры (`design/features/chat/chat.pen` → `Chat / Empty / Desktop`,
   `Chat / Streaming / Desktop`; потом `… / Tablet`, `… / Phone`), коротко объяснить решения и открытые вопросы, ждать явного «согласовано». Правки словами —
   внести и показать снова. Правки руками в pen.dev — перечитать файл, закоммитить как
   `design(<feature>): правки пользователя`, учесть.
6. **Зафиксировать.** В описании PR — раздел «Дизайн»: путь, кадры, SHA коммита согласованного макета, кто и когда
   согласовал. История переписана (объединение шагов) — обнови SHA.
7. **Реализовать** по 4.5, затем **сверить** по 4.6.

Без согласованного макета UI-код из раздела 4.1 не пишется: `pr-review` считает это блокером.

### 4.3. Как агент видит макет

Агент не использует ИИ и MCP pen.dev. Картинку он получает снимком окна приложения pen.dev:

- **Claude Code desktop:** открыть файл в фоне (`open -g -a Pen design/features/<f>/<f>.pen` на macOS), затем
  computer-use в фоновом режиме по приложению `dev.pencil.desktop`: `app_screenshot` окна, `app_zoom` на нужный кадр.
  Экран у пользователя не забирается. После каждой своей правки JSON — `File → Close Tab` (через меню приложения)
  и снова `open -g -a Pen <file>`: открытая вкладка правку с диска не увидит.
- **Heartbeat:** `computer_status` → `window_list` → `window_capture` окна pen.dev → `window_screenshot` /
  `window_zoom` → `window_release` (скилл `computer-use`; нужен включённый доступ агента к компьютеру).
- Навигация по холсту — штатными действиями pen.dev: вкладка Layers слева, выбор слоя, «приблизить к выделению»,
  «Zoom to fit». Это ввод (клик, клавиши): в Heartbeat он подтверждается по общему режиму безопасности. Сам `.pen`
  через интерфейс pen.dev агент не правит: правки — только в JSON, приложение не сохраняет (`Save` не нажимать).
- Панель свойств выбранного слоя (справа) — проверка, что JSON понят: размеры `W`/`H`, gap, padding, значок привязки
  к переменной. Незамеченная ошибка выглядит как пустое место на кадре и `W 0` в панели.
- Linux и Codex без инструмента снимка: картинки нет — правило из 4.1 (сказать и попросить пользователя проверить).

Снимок — для проверки агентом; в репозиторий и PR он не попадает.

### 4.4. Правила правки `.pen` как JSON

pen.dev рекомендует править файл через свои инструменты. Проект сознательно правит JSON напрямую, поэтому:

- не менять поле `version` и формат, который записал pen.dev; новая версия pen.dev — пересохранить файл в приложении
  отдельным коммитом;
- `id` уникальны в файле и стабильны (2.2); новые узлы — новыми `id`, чужие узлы не переписывать целиком;
- раскладка свободная (2.2): у контейнеров `"layout": "none"`, у детей `x`/`y` относительно родителя и числовые
  `width`/`height`; у однострочного текста размер не задаётся, у многострочного — `width` и
  `"textGrowth": "fixed-width"`; flex не используется нигде, включая компоненты;
- новый экран — описание поведения в `Context` его компонентов обязательно (не `note` на холсте);
- `width`/`height` **не принимают `$`-переменные** (узел молча получает ширину 0): фиксированный размер — числом,
  равным значению токена, и `name` с токеном (`Sidebar · dimensions.sidebarWidth`). `gap`, `padding`, `fill`,
  `fontSize` переменные принимают;
- цвета, отступы, скругления, шрифты — только `$`-переменные библиотеки (`"fill": "$hb:colors.surface"`), без hex;
  число без переменной допустимо, только если такого токена нет и в заметке предложен новый;
- компонент на экране — копия его структуры из `heartbeat.lib.pen` (тот же `frame` с детьми, `x`/`y` и размеры под
  свой текст, токены с алиасом `$hb:`), а не `ref`: иначе вложенное не двигается мышью; ссылки через алиас нужны для
  иконок, иллюстраций, разделителя и тёмной копии экрана — таблица 2.4. Изменили мастер — замените копии на экранах;
- текст — реальный, на русском, включая длинные варианты; не «Lorem ipsum»;
- иконки — только `ref` на `hb:hb-icon-*` (реальные `HbIcons`, 2.4); нужной иконки нет — сначала она появляется
  в `HbIcons` и в библиотеке;
- шрифт — `"fontFamily": "$hb:typography.family"` у каждого текста;
- после правки файл должен открыться в pen.dev. Не открылся — откатить свою правку и сделать её меньшими шагами,
  а не чинить вслепую;
- конфликты в `.pen` не разрешаются в JSON (раздел 1).

Минимальный файл фичи с одним кадром (полные примеры — `design/features/*`):

### 4.5. Перенос макета в Compose

pen.dev не генерирует Compose, поэтому перенос делает агент по таблице соответствий:

| `.pen` | Compose |
|---|---|
| `$colors.*`, `$surfaces.*`, `$spacing.*`, `$shapes.*`, `$dimensions.*`, `$typography.*`, `$elevation.*`, `$motion.*` | `HbTheme.colors.*`, `HbTheme.surfaces.*`, `HbTheme.spacing.*` и т.д. (2.4) |
| `width`/`height` числом и `name` слоя с токеном (`· dimensions.headerHeight`) | `HbTheme.dimensions.headerHeight` |
| группа с именем `HbX / Variant` (копия компонента) | `HbX(style = HbXStyle.Variant, …)` |
| группы `Window / *`, `Studio / Sidebar`, `Settings / Sidebar` | ничего: каркас рисует хост |
| группы кадра (вложенные `frame`) и их взаимное положение | `Column` / `Row` / `Box`: элементы в столбик — `Column`, в ряд — `Row`, наложение — `Box` |
| расстояния между элементами и до краёв (числа) | ближайшие `HbTheme.spacing.*` / `dimensions.*`; нет подходящего — сначала токен |
| `Context` компонента | `Modifier.weight(1f)` / `fillMaxWidth()` для растягиваемого, `widthIn(max = …)` для ограниченного, `verticalScroll` / `HbLazyColumn` для прокрутки, `Alignment`/`Arrangement` для прибитого к краю или центру, адаптивные ветки для узкой ширины |
| `text` | `HbText` со стилем `HbTheme.typography.*`, строка — в `strings.xml` |
| `ref` на `hb:hb-icon-<name>`, `hb:hb-illustration-<kind>` | `HbIcon(HbIcons.<Name>)`, `HbIllustration(HbIllustrationKind.<Kind>)` |
| Кадры `<Screen> / <State>` | состояния FlowMVI-стора и `@Preview` на каждое |
| Кадры `Phone` / `Tablet` / `Desktop` и `Context` о границах | ветки по ширине: `HbBoxWithConstraints` / `HbAdaptivePane` и `dimensions.compactBreakpoint` (720), `expandedBreakpoint` (1200); пресет `Mobile` / `Desktop` — от хоста, зоны касания — `touchTarget` |
| Стрелки в «Пользовательских путях» | `NavOptions(transition = NavTransition.*)` в `navigate`; микро-анимации — `HbTheme.motion` |

- Число без переменной в макете не становится `.dp`/`.sp`-литералом: сначала токен с KDoc.
- Компонента нет в `design-system:components` — сначала компонент по скиллу `design-system` (реализации китов,
  превью, каталог), затем экран.
- `@Preview` повторяют кадры макета: те же состояния, light/dark.

### 4.6. Сверка после реализации

1. Снять реальный экран на трёх ширинах — 390 (Phone), 834 (Tablet), 1280 (Desktop): desktop (`./gradlew
   :platform-main:desktop:run`, окно нужной ширины) или рендер превью/скриншот-теста jvmTest; Phone и Tablet — превью
   с `HbDimensions.Mobile` или эмулятор/симулятор; для компонентов — `platform-main:uikit-sandbox`.
2. Сравнить с кадрами макета в pen.dev по каждому форм-фактору: раскладка, отступы, иерархия, состояния, тексты.
3. Расхождение по ошибке — исправить код. Сознательное (ограничение платформы, кита) — исправить макет отдельным
   коммитом и перечислить в разделе «Дизайн» PR.
4. Перед ready — проверить, что макет в PR соответствует итоговому коду.
