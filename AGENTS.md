# AGENTS.md

Инструкции для ИИ-агентов (Claude Code, Codex, Junie и др.) лежат в [CLAUDE.md](CLAUDE.md) — это единый источник правды.
Дополнительно: правила по путям — `.claude/rules/`, навыки Codex — `.agents/skills/*/SKILL.md`,
общие процедуры — `.claude/skills/*/SKILL.md`. Источник правды по коду — KDoc.

## Навыки проекта

Codex обнаруживает навыки в `.agents/skills/` — стандартном каталоге проекта
([OpenAI Docs](https://learn.chatgpt.com/docs/build-skills)). Выбирай подходящий по описанию
навык или используй явный вызов, например `$verify`, `$new-feature`, `$state-machine`.
Каждый навык открывает общую процедуру из `.claude/skills/`: прочитай её перед выполнением.
Относительные ссылки разрешай от исходного файла процедуры. Подробные инструкции меняй
в `.claude/skills/`; при добавлении или переименовании навыка обновляй соответствующий
`SKILL.md` в `.agents/skills/`, сохраняя согласованность имени и области применения.

## Обязательный порядок работы для Codex

- Перед изменениями прочитай `CLAUDE.md` и подходящие по путям файлы `.claude/rules/`.
  Не рассчитывай на их автоматическую загрузку: открывай применимые правила и процедуры явно.
- Перед завершением задачи используй [verify](.agents/skills/verify/SKILL.md) и выполни применимые проверки.

## PR и коммиты

- **Один PR содержит законченную фичу**, коммиты внутри него — отдельные логические шаги.
  Каждый коммит оставляет проект собираемым; тесты изменённого поведения идут вместе с реализацией.
- **Не более 25 000 токенов полного diff на коммит.** Свыше 20 000 токенов или 20 файлов —
  предупреждение. 700–1000 добавленных и удалённых строк суммарно — ориентир, а не блокер.
  Общего лимита размера PR нет.
- Перед каждым коммитом проверь подготовленные изменения:
  `python scripts/check_commit_size.py --staged`.
- Перед созданием или обновлением PR проверь каждый коммит ветки:
  `python scripts/check_commit_size.py --base <base-ref> --head HEAD`.
  `<base-ref>` — актуальная целевая ветка PR, например `origin/master`.
  Мерж целевой ветки в ветку PR с двумя родителями (второй родитель уже в `<base-ref>`) отмечается `(base sync)`
  и измеряется только ручной правкой: разрешением конфликтов и изменениями сверх автоматического мержа.
  Повторно не считаются файлы, которые существовали во всех общих базах родителей мержа, уже отсутствовали
  в первом родителе (ветке PR) и остались удалёнными в результате. Исходные коммиты удаления
  проверяются как обычно; новые удаления и возвращённые файлы входят в лимит.
  Мержи с тремя и более родителями измеряются по первому родителю: Git не поддерживает для них remerge diff.
- Превышение 25 000 токенов требует разделения логического шага на собираемые коммиты.
  Не заменяй подсчёт токенов оценкой по строкам; ошибка инструмента не означает успешную проверку.

Установка зависимостей инструмента — навык [verify](.agents/skills/verify/SKILL.md).

- Задачу можно вести в draft PR с начала сессии: `/open-pr <задача>` (Codex — `$open-pr <задача>`,
  навык [open-pr](.agents/skills/open-pr/SKILL.md)). Каждый законченный шаг сразу коммитится, пушится и отражается
  в описании PR; в ready PR переводится по завершении. На другой машине работу продолжает `/continue-pr <ссылка на PR>`
  (Codex — `$continue-pr`, навык [continue-pr](.agents/skills/continue-pr/SKILL.md)) без дополнительного контекста
  от пользователя: состояние задачи — в описании PR и истории ветки. Исправление уже запушенного шага такого PR —
  отдельный коммит с трейлером `Fixes-Step: <sha шага>`: force push запрещён, ревью не требует объединять его с шагом.

## CI

CI подтверждает проверенный результат, а не ищет ошибки: каждый push в PR перезапускает проверки. Автоматически
на PR идут только commit policy и тесты скриптов; обязательных сборок нет. Набор workflow и правила их изменения —
`.claude/rules/ci.md`.

- **Сначала локально.** Всё, что проверяет `verify` (сборка, тесты, detekt, `check_commit_size.py`), выполняй
  до push. CI не используй для отладки, поиска ошибок и прогона того, что запускается локально.
- **Push — готовыми шагами.** Пушь, когда логический шаг готов и проверен, а не каждый коммит или fixup.
  Пока PR не готов к ревью, держи его draft (`gh pr create --draft`); в ready (`gh pr ready <N>`) переводи один раз,
  когда `verify` зелёный.
- **Сборка в CI — по решению агента и только затронутых модулей.** Когда изменение нужно проверить на ОС, которой
  нет локально (iOS-таргеты с Windows, поведение фичи на Windows или macOS), запусти `module-build.yml` на
  запушенной ветке: задачи затронутых модулей, один запуск на ОС; iOS — только `os=macos-15`.

  ```bash
  gh workflow run module-build.yml --ref <branch> -f os=macos-15 \
    -f tasks=":features:<name>:api:compileKotlinIosSimulatorArm64 :features:<name>:impl:compileKotlinIosSimulatorArm64"
  gh run list --workflow module-build.yml --branch <branch> --event workflow_dispatch \
    --json databaseId,displayTitle,createdAt --limit 5   # id прогона: заголовок — «Module build on <os>: <tasks>»
  gh run watch <id> --exit-status --interval 60
  ```

  Workflow запускается, только когда `module-build.yml` есть и в `master`, и в ветке (`--ref`), и исполняется
  его копия из ветки: ветку, отрезанную раньше, сначала обнови от `master`. Новый запуск на той же ветке и ОС
  отменяет предыдущий. Задачи, которые собираются локально, туда не добавляй; задачи `run*` и iOS не на macOS
  workflow отклоняет. Сборка приложения целиком и упаковка (задачи `platform-main`: `assembleDebug`,
  `createReleaseDistributable`, `verifyReleaseHarnessCompiler`) — только по просьбе пользователя. ОС, задачи и
  ссылку на прогон укажи в «Проверке» описания PR.
- **Не перезапускай CI** (`gh run rerun`, пустые коммиты, close/reopen PR) без просьбы пользователя.
  Упало — прочитай лог (`gh run view <id> --log-failed`), воспроизведи локально, запушь исправление; сборку
  модулей повторяй только после исправления; флак или инфраструктура — сообщи пользователю. Проверка, которая
  не запустилась по `paths`, этому PR не нужна.
- **Не расширяй CI без согласия пользователя**: новые workflow, джобы, шаги сборки, платформы, матрицы, триггеры,
  расширение `paths`. Временные и диагностические workflow для своей ветки не создавай.
- **Commit policy обязательна** для каждого PR, включая draft: не отключай её, не фильтруй по путям и не
  пропускай условием.

## Ревью PR

- `master` требует approve; его ставит `github-actions[bot]` по комментарию владельца
  `/reviewed [sha]` (`.github/workflows/review-approve.yml`). Новый push снимает approve.
- Агент оставляет `/reviewed <полный head SHA>` от имени пользователя только по его просьбе (навык `pr-review`;
  после правок по замечаниям — навык `pr-fix`, который подписывает только через `pr-review`;
  полный цикл ревью и исправлений — навык `pr-review-and-fix`)
  и только после собственного ревью этого SHA (`architecture-reviewer`, `verify`) без блокеров.
  Команда без SHA — для человека: засчитывается, если head закоммичен до комментария.
- PR помечает связь с issue признаком полноты — в описании или коммите, по строке на issue:
  - `Closes #N` — исправлено полностью: при мерже в `master` `github-actions[bot]` закрывает issue со ссылкой
    на PR (`.github/workflows/close-fixed-issues.yml`);
  - `Refs #N` / `Part of #N` — исправлена часть: issue остаётся открытой, бот оставляет комментарий,
    а в описании PR перечисляется, что сделано и что осталось. Глаголы `fix`/`close`/`resolve` рядом с номером
    для частичного исправления не используются: GitHub сам закрывает issue по ним. Не смешивай полные и частичные
    маркеры для одной issue ни в описании, ни в коммитах: бот отдаст приоритет частичному маркеру, но GitHub
    может закрыть issue самостоятельно по полному.
  Issue, заведённая из ревью (`pr-fix`), ссылается на PR-источник через `Refs`.
