# План разработки: единая модель сессий Heartbeat

**Статус: в работе; стандарт утверждён пользователем 01.11.2026.**
Целевое поведение описано в [спецификации v1](../rules/session-hierarchy.md).
Этот документ содержит аудит текущей модели, миграцию и порядок внедрения.
Пользователь подтвердил стандарт и поручил проверить реализацию, устранить несоответствия
и провести регрессию в этом же PR. Миграция и последовательность внедрения остаются в этом плане.

## 1. Результат и границы

Привести инструменты студии, органического ИИ, субсессий, дочерних сессий, планировщика,
графов задач, харнессов и движков к одному стандарту типов, владения и управления.
Включить фоновые задачи инструментов: неблокирующий запуск, выполняющуюся карточку,
поток вывода и обычные действия инструмента с учётом различий движков.
Сохранить предметную логику оркестраторов и проверенные механизмы журналирования.
Вся задача, включая исправления несоответствий и регрессию, выполняется в одном PR.
До окончания работ PR остаётся draft; мерж и выпуск этим планом не разрешаются.

Порядок: согласование стандарта → аудит реализации → согласование необходимых `.pen` →
последовательные изменения с тестами → `verify` → регрессия → исправления и итоговый отчёт.
Проверки кода и существующие ограничения среды не подменяются утверждением о соответствии.

## 2. Инвентаризация и аудит

Собрать все точки создания, отправки сообщений, ожидания, отмены, освобождения, восстановления
и отображения. Для каждой заполнить матрицу:

| Точка входа | Текущий смысл и данные | Требование стандарта | Целевой тип и владелец | Изменение | Проверка и результат |
|---|---|---|---|---|---|
| Каждая операция и её потребители | Контракт/KDoc, реализация, происхождение | ID критерия и раздел | Доказанные логические связи | Общая операция и совместимость | Тест либо явно непроверенное поведение |

Обязательные области:

- `ai-engine:facade`: `SessionTrees`, идентичность `SessionRef`, active session, история,
  hosted-каталог, инструкции, capabilities и нативные операции адаптеров.
- Фоновые задачи инструментов: путь возврата управления модели, связь call/task/attempt,
  изменения карточки и output, уведомления, polling/wait, ввод, остановка, время жизни
  и восстановление в каждом движке; отдельно отличить квитанцию запуска от окончания.
- `ai-studio`: `SidebarSessionTree`, `StudioSessionTreeUi`, `StudioHelperIdentity`,
  `StudioHelperChatRecords`, конфигурация, композер, remote intents и ссылки.
- `adaptive-subagents`: `SubagentTools`, объявления `subagent_*`, реестр запусков,
  адаптивный подбор и получение результата.
- `scheduler`: `BackgroundAgents`, `HelperAgents`, квоты и lease, wake, task graph,
  квитанции точной попытки, отмена и подтверждение освобождения.
- `harness`: `ScriptSessions.spawn/send/history/list`, workflow-исполнители, подключение
  харнесса, происхождение запроса и правила допустимости действий.
- `organic-ai`: машина организма, `CellDriver`, зигота, клетки, судьи, очереди сообщений,
  деление, иммунитет, остановка и освобождение сессий, включая workflow без чата.
- `planning-mode`, перенос движка, context optimization, auto-continue: сохранение роли
  и идентичности при смене режима, контекста, нативной сессии и источника нового хода.

Из предварительного чтения известны полезные request-specific квитанции и барьеры в
`HelperAgents`. Их нужно сохранить. KDoc `HelperAgents.create` описывает общую профильную
безопасность, а `ScriptSessions.spawn` упоминает cap Ask. Сверить KDoc с реализацией и
устранить расхождение в рамках соответствующего шага; это ещё не результат аудита поведения.

## 3. Миграция понятий и публичных инструментов

| Текущее понятие | Правило перехода |
|---|---|
| Обычная сессия студии | Сессия |
| Дочерняя сессия / субсессия с полным диалогом | Единый термин «Субсессия» |
| Helper / помощник / background agent | Установить тип по контракту, происхождению и фактическому пользовательскому взаимодействию |
| Новый вызов `subagent_spawn` | Строго субагент; полноценный чат создаётся отдельной явной операцией |
| Нативный делегированный агент | Субагент при доказанном владельце; неизвестную связь не додумывать |
| Органический ИИ | Оркестратор над общей моделью; роль клеток и внутренних сообщений — по согласованному стандарту |
| Планировщик | Запуск, пробуждение или продолжение типизированной сущности; ожидание само по себе чат не создаёт |
| Граф задач / workflow / script spawn | Общие операции с сохранением предметных зависимостей, квот и журналов |
| Планирование задачи в чате | Режим сессии или субсессии; отделить терминологически от планировщика запусков |
| Shell / IsolatedPrompts / reviewer / compact / handoff | Действия или внутренние исполнения без отдельной строки сессии |
| Parentless workflow-исполнитель | Внутреннее исполнение оркестратора до явной привязки к владельцу-чату |
| Фоновый tool call / команда / задача движка | Исполнение инструмента по §5.1 и §7.5 стандарта; сохранить идентичность, поток вывода и реальные capabilities |

Объявления создания субсессий и субагентов должны различаться. Семейства `subsession_*` и
`subagent_*` — возможная форма, точные имена определяются после аудита каталога и потребителей.
Сохранить полезные `organism_*`, `scheduler_*`, `harness_*` как предметные операции поверх
общего контракта. Не требуется объединять все оркестраторы в одну большую машину.

Совместимые старые вызовы переводить адаптером. Для неоднозначного вызова определить
документированное совместимое поведение либо явное требование выбрать тип. Сохранённый
скрипт не должен молча получать другую семантику. При изменении script API учесть его версию,
компиляционный кэш и потребителей; при изменении навыка сохранить согласованность его
процедуры в `.claude/skills/` и обёртки в `.agents/skills/`.

Для фоновых вызовов проверить существующие события начала, дельт, результата и нативные
task handles. Не считать успешную квитанцию запуска окончанием задачи. Перевод наблюдения
и карточек должен сохранять уже принятую попытку и доступный вывод; polling и повторное
подключение не создают копий. Поведение после конца хода и рестарта устанавливается
по фактическому контракту адаптера, а не по факту отдельного процесса или корутины.

Одновременно обновлять схемы инструментов, результаты и доверенные runtime-инструкции.
При создании, восстановлении и смене контекста передавать роль, владельца и доступные операции.
Сведения текста задачи не могут выдавать полномочия. Ограничения роли проверяются хостом
для UI, remote intents, hosted tools, скриптов и нативных путей.

## 4. Миграция данных и живой работы

### M0. Пробная классификация

До записи построить отчёт по существующим сущностям: исходная идентичность, источник
создания, пользовательские сообщения и изменения настроек, доказанный владелец, предполагаемый
тип, основание и уверенность решения. Отдельно выделить конфликтующие и неполные записи.
Не использовать только название, `isHelper`, факт видимости или наличие native thread.

### M1. Чтение версионированной модели

Добавить версионированные поля роли и связей вместе с читателем старого формата. Сохранить
логические и нативные ID, историю, авторство, модель, рабочую область и квитанции. Решение
классификации хранит происхождение и версию; повторный проход идемпотентен.
Читатель нового формата и общий допуск готовы до переключения писателей и UI.

### M2. Однозначные записи и разбор конфликтов

Перенести доказанные роли и связи. Не назначать владельца при неизвестности, цикле или
нескольких претендентах; сохранять историю и направлять запись на сверку без новых полномочий.
До переключения представлений определить совместимость ссылок и достижимость таких записей.

**Отдельное решение для согласования в плане:** старый `subagent_spawn` мог создать
интерактивный helper-чат, где пользователь уже общался или менял настройки. Предлагается
сохранить его как субсессию либо отдельно согласовать преобразование. Происхождение вызова
само по себе не должно молча отнимать уже использованные пользовательские возможности.
Необходимость этого решения и количество затронутых записей установить на M0.

### M3. Принятые попытки

Живые попытки заканчиваются под прежним владельцем и снимком конфигурации либо переходят
через явную сверку с исполнителем. Не запускать копию, не менять модель и не останавливать
работу только ради миграции. По каждой попытке сохраняется один управляющий путь; новые
старты переводятся на общий контракт без второго владельца старого исполнения.

Сохранить результаты до ACK, подтверждения остановки, ожидающие вопросы и причины wake.
Неизвестное принятие или окончание требует сверки, а не повторной отправки. Отмена пользователем
должна запретить recovery и после переключения формата.

### M4. Переключение инструментов и UI

Перевести читателей на нормализованные данные. Субсессии получают полноценный композер
и общие действия; субагенты показываются в меню с историей и реальным завершением.
Hosted- и native-наблюдения дедуплицируются по исполнению. Старые ссылки разрешаются в
соответствующее роли представление. Архив и поиск сохраняют доступность истории.

### M5. Завершение перехода и откат

После перевода всех потребителей убрать дублирующие правила helper и самостоятельные
политики владения. Оставить требуемую совместимость сериализации и скриптов. До прекращения
записи старого формата определить совместимость со старой версией приложения и границу
отката; откат не удаляет новые события, результаты или пользовательский ввод.
Фактический прогресс миграции, её версия и необходимость ручного разбора доступны для диагностики.

## 5. Логические шаги одного PR

Архитектурное решение после аудита: полноценные субсессии создаются через узкий
`HostConversationControl` поверх обычных `StudioRunHost`/`StudioRunCoordinator`, без нового
реестра и без helper-маркера. `HelperLease.owner: ActionId` обозначает работу и её capacity,
а не владельца разговора. Начальный action не ограничивает дальнейшие пользовательские
или агентские сообщения субсессии. Каждая отправка перечитывает её актуальные настройки.
Журнал `StudioHelperAttempts` можно переиспользовать как внутренний журнал точных попыток,
отделив его от helper-specific admission; terminal наблюдается для записанной попытки,
даже если у чата нет helper-маркера. Создание идемпотентно по доверенным request/tool-call
вызвавшего чата. Неизвестный logical context не получает fallback к корневой роли.
Существующий `ScriptSessions.spawn` сохраняет сигнатуру и семантику; новые операции явные.

Каждый шаг оставляет проект собираемым и содержит тесты изменённого поведения.
Разбиение уточняется после аудита; лимит полного diff каждого коммита — 25 000 токенов.

| Шаг | Результат | Зависимость |
|---|---|---|
| P0 | Согласованный стандарт и заполненный аудит с отклонениями | Подтверждение пользователя |
| P1 | Общие типы, владение, операции и тесты инвариантов | P0 |
| P2 | Совместимый читатель, журнал решений и переход данных M0–M3 | P1 |
| P3 | Studio/helper/adaptive-subagents через общую модель | P2 |
| P4 | Scheduler и graphs: типизированные старты, wake, lease и отмена | P3 |
| P5 | Harness/scripts/workflows с совместимостью вызовов | P4 |
| P6 | Organic AI с согласованным маршрутом клеток и судей | P5 |
| P7 | Нативные адаптеры и background task: неблокирующий запуск, output, реальные capabilities, наблюдение и остановка | P6 |
| P8 | UI и remote-проекции, включая живую карточку фонового вызова и output, по утверждённым `.pen`; переключение M4 | P3–P7 и согласованный макет |
| P9 | Завершение M5, KDoc, агентские инструкции, навыки и каталоги | Все переведённые потребители |
| P10 | Verify, регрессия, исправления и итоговый отчёт | P9 |

Объявления инструментов и runtime-инструкции переводятся вместе с соответствующим
потребителем; P9 проверяет их согласованность. Макеты можно подготовить после аудита
до P1; реализация UI начинается после их явного согласования по `ui-prototype`.
Постоянные ограничения helper не переносятся на полноценную субсессию. Проверки безопасности
профиля, доверия проекта, активации харнесса и точной попытки остаются обязательными.

## 6. Проверки и регрессия

Проверить критерии A01–A35 стандарта с матрицей
«требование → контракт/KDoc → реализация → тест → результат». Дополнительно проверить переход:

| ID | Сценарий миграции | Ожидание |
|---|---|---|
| M-A01 | Повторить миграцию одной записи | Идемпотентный результат без дубликатов |
| M-A02 | История, настройки и ссылки интерактивного legacy-helper | Данные сохранены, ранее использованные права не отняты молча |
| M-A03 | Конфликт владельцев, цикл или неизвестное происхождение | Явная сверка, без самовольного назначения типа и полномочий |
| M-A04 | Переключить формат при принятом ходе | Нет повторного старта, смены модели или потери старого владельца |
| M-A05 | Рестарт с недоставленным результатом, вопросом или unconfirmed stop | Событие сохранено, точная попытка сверяется |
| M-A06 | Вызвать старый скрипт или инструмент | Предусмотренное совместимое поведение либо явная диагностика |
| M-A07 | Переключить UI и открыть прежнюю ссылку | Роль проверяется хостом, история достижима |
| M-A08 | Применить поддерживаемый откат | Новые данные и пользовательский ввод сохранены |
| M-A09 | Перевести существующий фоновый вызов и его output на общую проекцию | Нет ложного окончания по квитанции запуска, повторного исполнения и потери известного вывода |

Использовать чистые тесты контрактов и переходов, интеграции владения и хранения,
адаптерные тесты на закреплённых протоколах и UI-проекции. Общие JVM, сборка и detekt —
по `verify` для затронутых модулей и потребителей; iOS и другие ОС учитывать по `AGENTS.md`.
Для background task проверить продолжение модели до окончания, streaming и snapshot-вывод,
отсутствующий или частичный output, явное ожидание, уведомление и опрос, операции ввода и
остановки, конец хода и рестарт. Во всех сценариях сверить исходную карточку вызова и точную
попытку; ограничения взаимодействия с субагентом не должны обходиться через карточку задачи.

Регрессию проводить в изолированном `HeartbeatE2E` с детерминированной мок-моделью по

### Следующий шаг: владение работой отдельно от прав чата

Подтверждён риск `metadata.lastRequest = attempts.unresolved ?: record.lastRunRequest`:
восстановленный старый lease может принять независимый human/creator request за свою работу.
До снятия постоянных helper-ограничений ввести неизменяемую provenance каждой попытки:
Conversation, OwnedHelperWork с ActionId/снимком helper-policy и непереопределённый legacy.
Work binding проставляет фактический lease; модель JSON его не получает. Старые попытки
дополняются только из точных durable журналов владельца, без пересылки и изменения native phase.
Metadata не выбирает lease новую работу по последнему запросу чата. Неизвестная принадлежность
блокирует усыновление и ложное подтверждение безопасного освобождения, сохраняя чтение истории.

Контрактный подготовительный шаг: HelperWorkBinding, optional work в HelperPrompt,
точный request в HelperCapacityRecoveryRecord, isRequestOwnershipResolved в HelperMetadata
и безопасный SPI reconcileHelperWork (default false, без native действий). Runtime ещё не
переведён. Проверено: JVM-тесты scheduler API без ошибок; оба режима detekt успешны;
компилируются scheduler impl, harness impl и DI-граф.
Лог — `build/verification/helper-work-api-tests.log`.

старых доказанных попыток → human capability и backend role gates → request-specific directive

→ UI и remote. Профильная security.level остаётся общей: trustCap сейчас compatibility metadata,
не реальный отдельный запрет. turnEffort уже ставит stored settings выше начального helper seed.

запрещён; mediation через владельца — отдельный точный маршрут, не обход общей human capability.
