# Модуль `features/<name>/api` — контракт фичи

Это **спецификация поведения** фичи. Процедура — скилл `state-machine`.

Содержит только (всё на `core:state-machine:api`):
- `<Name>State : MachineState` — sealed-иерархия **всех** состояний (`data object` / `data class` с данными; `@Serializable`, если машина `persist`).
- `<Name>Intent : MachineIntent` — `Public` (шлют другие фичи и стор) и `Internal` (результаты эффектов, внутренний ввод).
- `<Name>Effect : MachineEffect` — команды на IO (исполняет `EffectHandler` в `impl`); `<Name>Output : MachineOutput` — одноразовые события наружу.
- `object <Name>MachineKey : MachineKey<State, Intent, Intent.Public, Effect, Output>` — единственный способ адресовать машину извне.
- `<Name>MachineSpec` — `machineSpec(<Name>MachineKey, initial) { … }`: состояния, переходы, эффекты, outputs. Лямбды чистые, без IO.
- Публичные маршруты `@Serializable @SerialName("<name>") <Name>Route : Route` и `ResultContract`-ы (если фича открывается извне / возвращает результат). Скилл `navigation`.
- Определения тоглов фичи, если их читают другие модули.

Запрещено:
- Compose / UI / `design-system`, ресурсы экранов.
- Зависимости на `core:network`, `core:ai`, `core:datastore` и любые `impl`.
- KStateMachine и FlowMVI (движок — внутренность `core:state-machine:impl`, стор — в `impl` фичи).
- Логика с IO, репозитории, реализации.

Каждое изменение состояний/переходов:
1. Обнови KDoc спеки и таблицу переходов в KDoc `<Name>MachineSpec`.
2. Обнови/добавь тесты переходов в `api/src/commonTest`: `assertTransition` / `assertIgnored` — без рантайма и фейков.
3. Проверь потребителей `<Name>MachineKey` в других фичах (`Grep`), если меняется `Intent.Public` или состояния.


## Сервисные контракты и исключения

`features/attachments/api` дополнительно содержит узкий профильный `AttachmentsCatalog`: чтение
метаданных зарегистрированных вложений и наблюдение по идентификаторам. Это исключение для
отображения сохранённых файлов; каталог не импортирует, не удаляет и не экспортирует содержимое.
Все изменяющие операции проходят через `AttachmentsMachineKey`. Содержимое для AI читается через
профильный `ResourceResolver` в `ai-engine/facade/api`, который разрешает только зарегистрированные
идентификаторы текущего профиля. IO и нативные диалоги остаются в `attachments/impl`.

`features/computer-use/api` содержит, кроме машины, сервисные контракты `HostComputerControl` /
`NativeComputerControl` (`EngineFeature` для движков, по исключению ai-engine ниже) и app-scope
`ComputerUseCapturePresentation` / `ComputerUsePresentation`: координацию временного скрытия окон приложения
на время снимка и ввода мышью, и `ComputerUsePermissionGuide` — какое разрешение macOS хост сейчас помогает выдать.
Окна регистрирует только `platform-main`, контракт без IO и UI; захват и ввод по-прежнему идут через
`ComputerUseMachineKey`. Чистая функция `computerUseActivity()` выводит из состояния машины, что хост
показывает во время захвата агентом (`ComputerUseActivity`).

`features/ai-engine/facade/api` содержит UI-независимые сервисные интерфейсы каталога, сессий,
истории, capabilities и SPI адаптеров, а также чистую машину активной сессии. Это явное исключение
из ограничения состава обычного feature:api. Движок объявляет способы подключения
(`EngineDescriptor.connectionMethods`: API-ключ, свой CLI-логин, без авторизации) — по ним строится
общий UI подключения, без кода под конкретный движок. Любой не вендорный движок (семейство не `Vendor`:
Pi, Koog, будущие ACP и др.) обязан объявить методы `CompatibleProtocol` (OpenAI-/Anthropic-совместимые
поставщики со своим базовым URL, включая путь) и принимать их источники — проверяет `di-bundle:jvmTest`. `authenticator/api` содержит общие типы источников
авторизации, проверок и ошибок, сервисы `AuthSources` / `AuthChecks` и SPI `Authenticator` / `AuthCredentials`.
`connections/api` — обычная фича (визард и пространство настроек «движок × подключение × модель»)
плюс сервисный контракт `ModelSelections` (выбранные пользователем модели), который читают другие фичи.
Зависимость направлена `connections:api → facade:api → authenticator:api`; обратная зависимость запрещена.
API конкретных движков могут зависеть от этих общих контрактов.
Пакеты `facade.api.spi` и `authenticator.api.spi` используют только модули `ai-engine` и `platform-main:di-bundle`.
Доступ к IO, UI, сторонним SDK и любым impl в этих API по-прежнему запрещён.
Машина активной сессии принадлежит объекту доступа в профиле; native runtime и принятый ход
живут в скоупе профиля и не отменяются при закрытии экрана или смене состояния машины.
Управление движками — сервисный контракт `EngineManagement` (состояние всех зарегистрированных движков и команды
`EngineCommand`) и чистые типы `LaunchSettings` / `validateLaunchSettings` в `facade:api`; SPI `EngineManager`,
`EngineLaunchConfig` и `ReleaseFeeds` (план установки `InstallPlan`) — в `facade.api.spi`. Установка, загрузка и вход
выполняются в `facade:impl` и адаптерах; UI шлёт команды через операцию машины `ConnectionOperation.ManageEngine`.
Секреты в параметрах запуска запрещены (только подключения), значения путей и окружения не логируются.
Инструменты хоста (`AgentToolContribution`) по умолчанию существуют только в сессиях с проектом; сессии без проекта
получают лишь контрибуции с `isDetachedSupported` и только при opt-in `areDetachedToolsEnabled` (его включает
вызывающий, который показывает вызовы и отвечает на запросы разрешений). Opt-in проверяет адаптер: он
прикрепляет detached-инструменты только к таким сессиям, а диспетчер (`ProfileAgentTools`) флага не видит и отвечает
на любой запрос без проекта. В Claude, Pi и Koog решает запрос, открывающий нативную сессию без текущих держателей
(создание, возобновление после рестарта или закрытия всех хэндлов); подключение к сессии, которую держит другой хэндл,
сохраняет его выбор, а принятый ход — выбор на момент приёма. Codex фиксирует detached-инструменты при старте треда
(по opt-in создавшего его запроса): открытый тред переиспользуется с этим выбором, возобновление после рестарта
объявлений не добавляет и не убирает (без opt-in возобновившего вызовы объявленных инструментов отклоняются).
Detached-инструменты необязательны: недоступный bridge или ошибка контрибуции оставляют обычный чат.
Инструкции сессии строятся через `AgentToolScope` (проект, движок × модель, объявленные треду инструменты);
`requiresDecision` контрибуции может только добавить подтверждение к таблице доверия. Ограниченное исключение —
`existingAuthorization`: контрибуция проверяет сохранённое разрешение на неизменяемый граф scheduler,
владельца и точную попытку. Гейт повторно сверяет полное `AgentToolApproval` с непустым binding;
это не повышает доверие сессии. Создание/изменение действий требует нового подтверждения всего графа,
автоматические запуски и решения восстановления используют исходное разрешение. Одиночный
`scheduler_start_action` по-прежнему требует отдельного подтверждения. Блоки `hostDirective`
в промпте пользователя — указания хоста агенту; всё, что показывает или пересылает текст пользователя, вырезает их
`stripHostDirectives`.

`StopsOwnedTurns` — engine-wide контракт явной отмены точного profile-owned запроса после рестарта.
Маршрут `OwnedTurnAccess` фиксирует target/workspace/ожидаемый TurnId; адаптер проверяет сохранённую
принадлежность запроса до остановки. Эта операция не создаёт и не возобновляет сессию, не отправляет
промпт и не пишет индекс. `Confirmed` несёт терминальный ход именно этого request; `Unknown` допустим
только после доказанного завершения. `Unconfirmed` удерживает квоту помощника. Пустая история, закрытый
transport и отсутствие хэндла не доказывают остановку. Отмена ожидания сохраняет durable stop barrier.

`SessionHook` — профильный контракт контрибуций наблюдений и перехвата промптов/инструментов.
Хуки могут только добавить контекст, запретить вызов или потребовать вопрос; разрешить вызов они не могут.
`facade.api.spi.SessionHooks` — диспетчер для фасада и адаптеров: синхронно учитывает владельца хэндла,
привязывает перехват до нативной отправки, наблюдает только принятые владельцем ходы и дедуплицирует события.
Наблюдения доставляются отдельными ограниченными очередями, перехват выполняется параллельно с общим бюджетом
(промпт 2 с, инструмент 1,2 с). Сбой beforeTool требует решения, сбои текстовых хуков не меняют текст.
Исходное исключение пользовательского кода, его сообщение и cause в лог не попадают.
`areSessionHooksEnabled` в Create/Resume — opt-in конкретного хэндла; ai-studio включает его, служебные
сессии по умолчанию оставляют выключенным. Закрытие хэндла завершает наблюдения, но перехват принятого
хода сохраняется до барьера `finishTurn`. Вопрос от хука дополняет отображаемый approval, а повторная
проверка сравнивает исходный snapshot контрибуции. Промпты, начинающиеся с `/`, не дополняются.

Политика инструментов фасада — `AgentToolPolicyProvider` (ленивый мультибиндинг профиля),
`ToolPolicyScope` и `ResolvedToolPolicy`. Нативный каталог задаётся в `EngineDescriptor.nativeTools`.
Off побеждает On; включение сверх дефолтов требует gated-каталога, проекта, отсутствия коллизии с hosted
и `harness.native_tools`. Каталог hosted не зависит от текущей доступности: `AgentToolContribution.catalog`
содержит все имена и категории, `group`/`title` объединяют их для настроек. `specifications(scope)` учитывает
сессию и возможность обновления деклараций на каждом ходе. Сбой провайдера при построении деклараций
возвращает дефолты с предупреждением; исполнение обязано закрываться при сбое. `execute` заново разрешает политику по доверенной сессии и проверяет её после approval.
MCP-capability хранит `AgentToolScope`, использует его для initialize/tools/list и проверяет workspace/session
при вызове. Инструкции видят только разрешённые declared-имена; неподелённый legacy-текст при частично
доступном наборе скрывается, scoped overrides обязаны исключать руководство запрещённых инструментов.
Поколение эффективно
равной политики стабильно, любое изменение (включая возврат к прежней политике) меняет поколение.

`ProfileAgentTools.authorizeNative` принимает классифицированный адаптером `NativeToolCall` и использует
ту же регистрацию вызова и native lifetime, что hosted execute. Порядок: Off/доступность → hook → coverage
доверия адаптера → permission → повторная policy-проверка. Native-хук получает null turn, но коррелируется
по доверенному request. После Allow адаптер обязан снова проверить захваченный native turn перед ответом
процессу. `NativeCallClassifier` в SPI разделяет bounded-эвристику завершения хоста и IO-проверку pinned
абсолютного пути; неоднозначные пути, выход через symlink и реальная Git metadata не покрываются AutoEdits.

`features/ai-engine/acp-interface/api` — сервисный контракт ACP v1: клиент, транспорт,
DTO и callbacks без реализации IO. Допускает kotlinx.serialization JSON для расширяемых полей
протокола. Собственной бизнес-машины и регистрации движка нет; конкретные ACP-адаптеры используют
этот контракт и фасад. Соединение принадлежит переданному скоупу профиля, отмена ожидания
потребителем не останавливает принятый ход. Доступность движков по-прежнему задают их descriptor/toggle.
Контракт даёт запуск процессов (`AcpStdioTransportFactory`), поэтому `acp-interface:api` используют только модули `ai-engine`
и `platform-main:di-bundle`.

`features/search-engine/api` — сервисный контракт поиска и чтения веб-ресурсов без собственной
бизнес-машины: типы результатов, конфигурация профиля и опциональные `EngineFeature` для нативных
операций. Поисковый запрос не является длительным состоянием фичи; IO и UI находятся только в `impl`.

`features/plant-uml-support/api` — сервисный контракт `PlantUmlRenderer` без бизнес-машины: рендер диаграммы —
запрос/ответ без длительного флоу (типы `PlantUmlRequest`/`PlantUmlStyle`/`PlantUmlResult`, `availability` по тоглу).
UI у фичи нет: диаграммы рисует ДС (`HbDiagramsProvider` + SPI `HbDiagramRenderer`), а desktop-хост адаптирует к нему
контракт, поэтому фича не входит в `SERVICE_CONTRACT_FEATURES`. Движок PlantUML и DI — только в `jvmMain` impl
(локально, в отдельном процессе-воркере с малым heap и таймаутом, в песочнице SANDBOX, без сети); на Android/iOS биндинга
нет, и fence остаётся кодом.

`features/scheduler/api` также содержит профильную машину `TaskGraphMachineKey`: валидация DAG,
AllOf/AnyOf, готовность, попытки, невозможные зависимости, отмена и решения восстановления.
Запуск следует только после сохранения попытки; зависимости проверяются по сохранённым результатам,
а не по событиям шины. SPI `ScheduledTaskHost` сохраняет чат, возвращает подтверждённый исход и
останавливает конкретное задание. `RestoresSessionTurns` (`facade:api`) — адаптерная квитанция хода и
свежая проверка native state; обычный `ReconcilesSession` и кешированный Ready не доказывают остановку.

`features/scheduler/api` — машина сна и пробуждения сессий (`SchedulerMachineKey`, ProfileScope) плюс единая
профильная шина событий: ключи `EventKey` (пространства `system` / `session` / `action` / `custom`, только через
фабрики `EventKeys`), события `BusEvent` и сервис `SchedulerBus` (горячий поток без replay, публикация с
`EventOrigin`). Ожидание переживает рестарт только через машину; шина событий не хранит. Сопоставление событий
и дедлайнов с пробуждениями — чистые переходы спеки. Пакет `scheduler.api.spi` — `ScheduledSessionHost` (доставка
промпта пробуждения в сессию и создание сессии-помощника; реализуют `scheduler:impl` и хосты чатов, например
`ai-studio:impl`), `ScheduledWakeOwner` (живой допуск пробуждений владельца: Allow/Defer/Drop; контрибуции фич,
например checklist и harness) и `SchedulerEventSource` (системные сигналы платформ); пакет используют только реализующие модули и
`platform-main:di-bundle` — соглашение проверяется на ревью (в `FeatureLayerDependency` пакета нет). Хост обязан
показывать вызовы инструментов и обслуживать разрешения; без владеющего сессией хоста пробуждение отбрасывается. Запуск фонового действия агентом требует решения по таблице доверия как Command. Одобрение кода скрипта
покрывает последующие запуски workflow и помощников по событиям; такие помощники получают Ask и общие квоты. Payload событий — недоверенные данные; payload и заметки не логируются.

`HelperAgents` в `scheduler:api` — исключение для профильной координации помощников: общий lease с очередью,
пустой durable чат до prompt, коррелированные result/cancel и durable outbox `finish`. Квоты заданы чистой
`BackgroundCapacityMachineSpec`; команды scheduler и helpers разделяют 8 слотов профиля. Lease закрывается
только после подтверждённого завершения native work; неопределённая отмена удерживает слот. Хост реализует
расширения `ScheduledSessionHost` с безопасными дефолтами (без fallback в старый spawn), хранит helper marker
даже без родителя, проверяет owner/parent при recovery и потолок доверия на каждом ходе. Тексты не логируются.
`ScheduledHelperCatalog` даёт точечное обратное чтение метаданных по сессии и ограниченные страницы по owner
без запуска движка; `HelperAgents` проверяет идентичность, порядок и неоднозначность хостов. Выбор target
по умолчанию допустим только у помощника без родителя; помощник с родителем сохраняет его target.

`features/harness/api` дополнительно содержит публичные пакеты `script`, `event` и `workflow`:
интерфейсы контекста одобренного скрипта, регистрации хуков/инструментов/событий, доступа к активным
сессиям, owned-пробуждениям и запуска workflow, а также чистый replayable workflow DSL и его DTO.
Это явное исключение сервисного контракта; базовые классы только получают зависимости конструктора
и регистрируют определение, без IO, компилятора или runtime-реализации. `HARNESS_API_VERSION` входит
в ключ кэша компиляции. Типы facade/scheduler/coroutines/JSON в публичных сигнатурах экспортируются
через `api(...)`. Данные скриптов и события скрывают тексты и вложенные данные в `toString`;
scheduler-события не содержат wake note, payload шины — недоверенные данные.
Рантайм повторно проверяет активацию и квоты при каждом обращении; чтение сессий ограничено теми,
где харнесс активен. Хуки только добавляют контекст, запрещают или требуют вопрос и не запускают
send/spawn/workflow. Одобрение исходника покрывает последующие запуски workflow и помощников из
скрипта, но не расширяет доверие помощника выше Ask и не отменяет общие lease/cancel barriers.
Прямой запуск агентом остаётся Command по таблице доверия. KV, лог-API и уведомления скриптов в v1 нет.

### Фичи сервисного контракта

Фича, чей `api` — только сервисный контракт без бизнес-машины и у чьего `impl` есть слой `ui` (сейчас `search-engine`),
объявляется в списке `FeatureLayer.SERVICE_CONTRACT_FEATURES` (`lint/detekt-rules`). Только для таких фич слой `impl.ui` может напрямую
использовать типы своего `api` (отображение значений контракта); чужие `api` и интенты машин из UI по-прежнему
запрещены. Проверка по имени фичи в логике правил не допускается — только через этот список. Добавление фичи
в список — решение владельца, фиксируемое здесь.

Инструменты хоста, исполняемые транспортом адаптера (поиск), регистрируют обычную контрибуцию
с `isAdapterOperated = true`: каталог, декларации доступности, action и approval принадлежат владельцу.
Они не выдаются generic hosted bridge. Адаптер вызывает `authorizeHosted` под тем же lifetime,
а затем свой транспорт; обычные контрибуции через этот путь не авторизуются. Политика использует
`hostedOff`, не native On; хук получает исходные аргументы и `isNative = false`.
