# Модуль `features/<name>/api` — контракт фичи

Это **спецификация поведения** фичи. Процедура — скилл `state-machine`.

Содержит только (всё на `core:state-machine:api`):
- `<Name>State : MachineState` — sealed-иерархия **всех** состояний (`data object` / `data class` с данными; `@Serializable`, если машина `persist`).
- `<Name>Intent : MachineIntent` — `Public` (шлют другие фичи и стор) и `Internal` (результаты эффектов, внутренний ввод).
- `<Name>Effect : MachineEffect` — команды на IO (исполняет `EffectHandler` в `impl`); `<Name>Output : MachineOutput` — одноразовые события наружу.
- `object <Name>MachineKey : MachineKey<State, Intent, Intent.Public, Effect, Output>` — единственный способ адресовать машину извне.
- `<Name>MachineSpec` — `machineSpec(<Name>MachineKey, initial) { … }`: состояния, переходы, эффекты, outputs. Лямбды чистые, без IO.
- Публичные маршруты `@Serializable @SerialName("<name>") <Name>Route : Route` и `ResultContract`-ы (если фича открывается извне / возвращает результат). Скилл `navigation`.
- Определения тоглов фичи, если их читают другие модули.

Запрещено:
- Compose / UI / `design-system`, ресурсы экранов.
- Зависимости на `core:network`, `core:ai`, `core:datastore` и любые `impl`.
- KStateMachine и FlowMVI (движок — внутренность `core:state-machine:impl`, стор — в `impl` фичи).
- Логика с IO, репозитории, реализации.

Каждое изменение состояний/переходов:
1. Обнови KDoc спеки и таблицу переходов в KDoc `<Name>MachineSpec`.
2. Обнови/добавь тесты переходов в `api/src/commonTest`: `assertTransition` / `assertIgnored` — без рантайма и фейков.
3. Проверь потребителей `<Name>MachineKey` в других фичах (`Grep`), если меняется `Intent.Public` или состояния.


## Сервисные контракты и исключения

`features/attachments/api` дополнительно содержит узкий профильный `AttachmentsCatalog`: чтение
метаданных зарегистрированных вложений и наблюдение по идентификаторам. Это исключение для
отображения сохранённых файлов; каталог не импортирует, не удаляет и не экспортирует содержимое.
Все изменяющие операции проходят через `AttachmentsMachineKey`. Содержимое для AI читается через
профильный `ResourceResolver` в `ai-engine/facade/api`, который разрешает только зарегистрированные
идентификаторы текущего профиля. IO и нативные диалоги остаются в `attachments/impl`.

`features/computer-use/api` содержит, кроме машины, сервисные контракты `HostComputerControl` /
`NativeComputerControl` (`EngineFeature` для движков, по исключению ai-engine ниже) и app-scope
`ComputerUseCapturePresentation` / `ComputerUsePresentation`: координацию временного скрытия окон приложения
на время снимка и ввода мышью, и `ComputerUsePermissionGuide` — какое разрешение macOS хост сейчас помогает выдать.
Окна регистрирует только `platform-main`, контракт без IO и UI; захват и ввод по-прежнему идут через
`ComputerUseMachineKey`. Чистая функция `computerUseActivity()` выводит из состояния машины, что хост
показывает во время захвата агентом (`ComputerUseActivity`).

`features/app-update/api` — машина самообновления приложения в `AppScope` (`AppUpdateMachineKey`): у фичи нет своего
скоупа и профиля, она живёт весь запуск desktop. Машину создаёт `AppStartup` фичи (jvmMain impl), который desktop-хост
запускает после создания графа; на мобильных биндингов нет, и машина не зарегистрирована. Кроме машины api содержит
чистые `AppVersion` (версии и теги `vX.Y.Z`) и проекцию `appUpdateOffer()` — что показывает кнопка обновления
ai-studio. Хост только завершает приложение штатно, когда машина в `Restarting`.

`features/ai-studio/api` также содержит `StudioRemoteScreens` — удалённые виды экрана студии для хостов вне окна
(боковая панель Chromium-расширения рисует тот же экран студии). Каждый вид — свой граф студии в дочернем скоупе
профиля с неадресуемой машиной; кадры состояния и интенты экрана — непрозрачный JSON модели
`features:ai-studio:screen-model`, хост их только ретранслирует. Нативные поверхности рабочего стола (выбор файлов
и папок, открытие и экспорт вложений, панели рядом) удалённо отклоняются. Без `ai_studio.engine_runtime` недоступен.

`features/chromium-bridge/api` кроме машины моста содержит сервисный контракт `ExternalBrowser` — транспорт к внешнему
Chromium-браузеру пользователя через расширение для инструментов агента `ex_control_*` в `browser:impl` (только Desktop):
активная вкладка, открытие вкладки в группе «Heartbeat», передача вкладки, навигация, DevTools-вызов, ответ на
защищённую навигацию и события вкладок. Контракт только транспортирует: владение вкладками, подтверждения и политика
навигации остаются у `browser:impl`, протокол моста не выходит за `chromium-bridge:impl`. Исключение — модуль
`features:chromium-bridge:protocol`: wire-модели захваченной страницы, идентификатор watch и коды ошибок, которые компилируют и приложение,
и Kotlin/Wasm-панель расширения (`:chromium-plugin:panel`); только сериализуемые данные, без логики и типов приложения.

`features/browser/api` кроме машины браузера содержит сервисный контракт `BrowserDocuments` — изолированные локальные
документы профиля: HTML, который фича показывает в своём экране через `BrowserDocumentRoute`, отдельно от вкладок
пользователя. Только Desktop (на Android/iOS маршрут рисует «не поддерживается»): у каждого документа свой origin,
контекст в памяти, без сети, навигации, всплывающих окон, загрузок и диалогов. Открывший документ владеет его
`BrowserDocumentHandle` (данные страницы, закрытие) и необязательным мостом `BrowserDocumentBridge` для
`heartbeat.call` страницы; границы — `BrowserDocumentLimits`. HTML, данные, аргументы и результаты не логируются.
Контракт `BrowserDocumentPreviews` проверяет переданный HTML в том же изолированном renderer: временный viewport,
тема и масштаб, ограниченный PNG и диагностики вёрстки. Он не принимает URL, owner bridge или произвольные
DevTools-команды, не снимает другие страницы и окна; документ освобождается при завершении или отмене.
Реализация и нативные ресурсы остаются в `browser:impl`; на Android/iOS возвращается `Unavailable`.
Чистая проекция `BrowserState.Running.isHumanDecisionAllowed()` — может ли человек решать по предупреждению вкладки;
её используют и guard машины, и стор экрана. `BrowserOperation.Inspect` и `BrowserRequest.review` (`BrowserReview`) —
привязка запроса агента к независимой проверке: Inspect только собирает доказательства о странице (не меняет страницу
и ссылки на элементы, но выбирает вкладку, как любая операция; для перехода страница не снимается),
запрос с утверждёнными доказательствами выполняется, лишь пока живая вкладка им соответствует; `review` задаёт
доверенный код инструментов, аргументы модели его не несут.

`features/ai-engine/facade/api` содержит UI-независимые сервисные интерфейсы каталога, сессий,
истории, capabilities и SPI адаптеров, а также чистую машину активной сессии. Это явное исключение
из ограничения состава обычного feature:api. Движок объявляет способы подключения
(`EngineDescriptor.connectionMethods`: API-ключ, свой CLI-логин, без авторизации) — по ним строится
общий UI подключения, без кода под конкретный движок. Любой не вендорный движок (семейство не `Vendor`:
Pi, Koog, будущие ACP и др.) обязан объявить методы `CompatibleProtocol` (OpenAI-/Anthropic-совместимые
поставщики со своим базовым URL, включая путь) и принимать их источники — проверяет `di-bundle:jvmTest`. `authenticator/api` содержит общие типы источников
авторизации, проверок и ошибок, сервисы `AuthSources` / `AuthChecks` и SPI `Authenticator` / `AuthCredentials`.
`connections/api` — обычная фича (визард и пространство настроек «движок × подключение × модель»)
плюс сервисный контракт `ModelSelections` (выбранные пользователем модели), который читают другие фичи.
Зависимость направлена `connections:api → facade:api → authenticator:api`; обратная зависимость запрещена.
API конкретных движков могут зависеть от этих общих контрактов.
Пакеты `facade.api.spi` и `authenticator.api.spi` используют только модули `ai-engine` и `platform-main:di-bundle`.
Доступ к IO, UI, сторонним SDK и любым impl в этих API по-прежнему запрещён.
Машина активной сессии принадлежит объекту доступа в профиле; native runtime и принятый ход
живут в скоупе профиля и не отменяются при закрытии экрана или смене состояния машины.
Управление движками — сервисный контракт `EngineManagement` (состояние всех зарегистрированных движков и команды
`EngineCommand`) и чистые типы `LaunchSettings` / `validateLaunchSettings` в `facade:api`; SPI `EngineManager`,
`EngineLaunchConfig` и `ReleaseFeeds` (план установки `InstallPlan`) — в `facade.api.spi`. Установка, загрузка и вход
выполняются в `facade:impl` и адаптерах; UI шлёт команды операцией `ControlOperation.Manage` машины панели управления
(`features:ai-engine:control-panel:api`). Секреты в параметрах запуска запрещены (только подключения), значения путей и
окружения не логируются.
Настройка движков — сервисный контракт `EngineConfiguration` и чистые типы схемы и значений (`EngineConfigSchema`,
`EngineConfigValues`, `validateEngineConfig`) в `facade:api`; SPI `EngineConfigurator` — в `facade.api.spi`. Значения
могут называть пути и серверы пользователя и не логируются; секреты — только ссылки `secretReference(slot)` на хранилище
профиля, в файлах проекта они запрещены. Панель управления не знает движков: всё, что она рисует, объявляет схема.
Результат инструмента хоста, исполняемого диспетчером, ограничен `AgentToolSpec.resultChars` (по умолчанию 128K
символов, после offload; adapter-operated инструменты — вне бюджета): превышение возвращается агенту явной ошибкой,
а не обрезается. Повышай бюджет (до `MAX_RESULT_CHARS`) только
инструментам, которые обязаны отдавать полный исходник или сами ограничивают вывод.
Инструменты хоста (`AgentToolContribution`) по умолчанию существуют только в сессиях с проектом; сессии без проекта
получают лишь контрибуции с `isDetachedSupported` и только при opt-in `areDetachedToolsEnabled` (его включает
вызывающий, который показывает вызовы и отвечает на запросы разрешений). Opt-in проверяет адаптер: он
прикрепляет detached-инструменты только к таким сессиям, а диспетчер (`ProfileAgentTools`) флага не видит и отвечает
на любой запрос без проекта. В Claude, Pi и Koog решает запрос, открывающий нативную сессию без текущих держателей
(создание, возобновление после рестарта или закрытия всех хэндлов); подключение к сессии, которую держит другой хэндл,
сохраняет его выбор, а принятый ход — выбор на момент приёма. Codex фиксирует detached-инструменты при старте треда
(по opt-in создавшего его запроса): открытый тред переиспользуется с этим выбором, возобновление после рестарта
объявлений не добавляет и не убирает (без opt-in возобновившего вызовы объявленных инструментов отклоняются).
Detached-инструменты необязательны: недоступный bridge или ошибка контрибуции оставляют обычный чат.
Инструкции сессии строятся через `AgentToolScope` (проект, движок × модель, объявленные треду инструменты);
`AgentSecuritySettings` — единственный источник режима разрешений для всех вызовов и хостов. `ToolPermissions`
читает сохранённый режим перед действием, а ожидающий запрос пересчитывается при смене настройки.
При выключенном `ai.action_safety` Trust разрешает корректные доступные вызовы без permission-хуков и LLM-ревью. Automatic разрешает чтение и
доказанную обычную правку проекта; остальные эффекты требуют подтверждения. Ask подтверждает любые изменения.
`approval` строит полный одноразовый binding; контрибуция повторно сверяет аргументы, владение, ревизии и снимок
при выполнении. Deny/Ask permission-хуки в Ask/Automatic превращаются в подтверждение, не в окончательный отказ.
При включённом `ai.action_safety` общий слой сам собирает полный вызов (описание, схему, аргументы, presentation;
для native — команду, пути и launcher) и оригинальную human authority для двухступенчатого LLM-ревью.
`analyze` добавляет необязательные структурные факты: Unknown не блокирует ревью и сам по себе не требует
подтверждения. Старый `requiresDecision` не определяет решение нового режима; точная сохранённая авторизация
существующего workflow сохраняет силу. Неясные последствия, отсутствующая authority и сбой ревью требуют
подтверждения. Описания, аргументы и документы — данные, не источник полномочий. Ask подтверждает также чтения.
Trust пропускает LLM, сохраняя обязательные Deny/Ask hooks и запреты анализа. Флаг фиксируется на время жизни
профиля; неподконтрольное native-исполнение закрывается. Снимок фактов повторно проверяется перед выполнением.
Формат, владение, capability и lifecycle остаются обязательными во всех режимах.
`IsolatedPrompts` — служебные промпты без инструментов: `ToolPolicy.isToolFree` выключает весь native/hosted каталог;
это контракт текстового сервиса. Неизвестное завершение сохраняет изоляцию; очередь и cleanup ограничены временем.
`AgentToolDecisionMode`, `TrustLevel` и `reviewTarget` сохраняются как метаданные совместимости протоколов, но не
дают отдельного разрешения. `StudioSecurityMachine` сохраняет общую настройку; UI обновляется после сохранения.
`existingAuthorization` проверяет ранее подтверждённый неизменяемый граф scheduler, владельца и точную попытку.
Блоки `hostDirective` — указания хоста; отображение/перенос пользовательского текста вырезает их через `stripHostDirectives`.

`StopsOwnedTurns` — engine-wide контракт явной отмены точного profile-owned запроса после рестарта.
Маршрут `OwnedTurnAccess` фиксирует target/workspace/ожидаемый TurnId; адаптер проверяет сохранённую
принадлежность запроса до остановки. Эта операция не создаёт и не возобновляет сессию, не отправляет
промпт и не пишет индекс. `Confirmed` несёт терминальный ход именно этого request; `Unknown` допустим
только после доказанного завершения. `Unconfirmed` удерживает квоту помощника. Пустая история, закрытый
transport и отсутствие хэндла не доказывают остановку. Отмена ожидания сохраняет durable stop barrier.

`SessionHook` — профильный контракт контрибуций наблюдений и перехвата промптов/инструментов.
`SessionPromptAddition` сохраняет целостность блока с host-only `SessionPromptReceipt`: подтверждение
только после native Accepted точного хода/запроса, один раз и до следующей подготовки в этой сессии.
Callback синхронно ставит запись в очередь владельца, без IO и авторского кода; очередь наблюдений
не является квитанцией. Усечение или отказ не подтверждают блок, закрытие хэндла не отменяет факт принятия.
`SessionContextRevision` — read-only capability нативного контекста, независимая от статистики использования.
Opaque identity меняется при замене процесса и compaction; null запрещает дедупликацию доставки.
Адаптер обновляет её только после проверки источника события; фасад читает её при подготовке и Accepted.
Хуки могут только добавить контекст, запретить вызов или потребовать вопрос; разрешить вызов они не могут.
`CompactsContext` (`session.compact`) — сжатие нативного контекста как ход: `PromptRequest.compaction` без частей
проходит тот же `SendsPrompts` (Busy, привязка хода, Accepted/Finished, отмена, recovery), хуки его не дополняют, а
фасад отказывает до приёма, если сессия фичу не разрешает или инструкции не поддержаны. Итог хода —
`SessionItem.Notice` с `NoticeKind.ContextCompacted`. Чистая `sessionEssence` строит текстовую выжимку транскрипта
(без reasoning и аргументов инструментов) для сжатия и переноса в новую сессию.
Ленивые профильные мультибиндинги `ContextPolicyProvider` (маскирование старых результатов инструментов в промптах,
которые движок пересобирает каждый ход, — Koog) и `ToolOutputOffload` (длинный вывод инструментов заменяется началом,
концом и ссылкой на чтение остатка) реализует фича `context-window-optimization`; без провайдеров промпт и вывод
остаются как есть, сбой провайдера оставляет вывод целым. Нативный вывод инструментов Codex/Claude/Pi не заменяется.
`facade.api.spi.SessionHooks` — диспетчер для фасада и адаптеров: синхронно учитывает владельца хэндла,
привязывает перехват до нативной отправки, наблюдает только принятые владельцем ходы и дедуплицирует события.
Наблюдения доставляются отдельными ограниченными очередями, перехват выполняется параллельно с общим бюджетом
(промпт 2 с, инструмент 1,2 с). Сбой beforeTool требует решения, сбои текстовых хуков не меняют текст.
Исходное исключение пользовательского кода, его сообщение и cause в лог не попадают.
`areSessionHooksEnabled` в Create/Resume — opt-in конкретного хэндла; ai-studio включает его, служебные
сессии по умолчанию оставляют выключенным. Закрытие хэндла завершает наблюдения, но перехват принятого
хода сохраняется до барьера `finishTurn`. Вопрос от хука дополняет отображаемый approval, а повторная
проверка сравнивает исходный snapshot контрибуции. Промпты, начинающиеся с `/`, не дополняются.

Политика инструментов фасада — `AgentToolPolicyProvider` (ленивый мультибиндинг профиля),
`ToolPolicyScope` и `ResolvedToolPolicy`. Нативный каталог задаётся в `EngineDescriptor.nativeTools`.
Провайдеры политики разрешений харнессов удалены. Resolver принимает только capability-изоляцию внутренних
сервисов (`isIsolation`). Доступные gated-инструменты работают через общий гейт; независимых флагов разрешения нет.
Каталог hosted содержит все имена/категории; `specifications(scope)` учитывает возможности движка и сессии.
Исполнение перепроверяет scope, поколения и изоляцию после подтверждения.
MCP-capability хранит `AgentToolScope`, использует его для initialize/tools/list и проверяет workspace/session
при вызове. Инструкции видят только разрешённые declared-имена; неподелённый legacy-текст при частично
доступном наборе скрывается, scoped overrides обязаны исключать руководство запрещённых инструментов.
Поколение эффективно
равной политики стабильно, любое изменение (включая возврат к прежней политике) меняет поколение.

`ProfileAgentTools.authorizeNative` принимает классифицированный адаптером `NativeToolCall` и использует
ту же регистрацию вызова и native lifetime, что hosted execute. Порядок: Off/доступность → hook → coverage
доверия адаптера → permission → повторная policy-проверка. Native-хук получает null turn, но коррелируется
по доверенному request. После Allow адаптер обязан снова проверить захваченный native turn перед ответом
процессу. `NativeCallClassifier` в SPI разделяет bounded-эвристику завершения хоста и IO-проверку pinned
абсолютного пути; неоднозначные пути, выход через symlink и реальная Git metadata не покрываются AutoEdits.

`features/ai-engine/acp-interface/api` — сервисный контракт ACP v1: клиент, транспорт,
DTO и callbacks без реализации IO. Допускает kotlinx.serialization JSON для расширяемых полей
протокола. Собственной бизнес-машины и регистрации движка нет; конкретные ACP-адаптеры используют
этот контракт и фасад. Соединение принадлежит переданному скоупу профиля, отмена ожидания
потребителем не останавливает принятый ход. Доступность движков по-прежнему задают их descriptor/toggle.
Контракт даёт запуск процессов (`AcpStdioTransportFactory`), поэтому `acp-interface:api` используют только модули `ai-engine`
и `platform-main:di-bundle`.

`features/search-engine/api` — сервисный контракт поиска и чтения веб-ресурсов без собственной
бизнес-машины: типы результатов, конфигурация профиля и опциональные `EngineFeature` для нативных
операций. Поисковый запрос не является длительным состоянием фичи; IO и UI находятся только в `impl`.

`features/autocomplete/api` — сервисный контракт `ComposerAssists` без бизнес-машины: подсказки композера —
запрос/ответ без длительного бизнес-флоу. В API находятся типы области поиска и подсказок, тогл,
чистые `composerTrigger` / `applyComposerSuggestion`; IO и объединение источников остаются в `impl`.
Собственного UI нет: ai-studio проецирует контракт в модели своего стора, а ДС получает только UI-модели.
Поэтому autocomplete не входит в `SERVICE_CONTRACT_FEATURES`. Execution workspace задаёт каталог файлов
и нативных скиллов; логический проект отдельно задаёт область выученных инструкций.

`features/plant-uml-support/api` — сервисный контракт `PlantUmlRenderer` без бизнес-машины: рендер диаграммы —
запрос/ответ без длительного флоу (типы `PlantUmlRequest`/`PlantUmlStyle`/`PlantUmlResult`, `availability` по тоглу).
UI у фичи нет: диаграммы рисует ДС (`HbDiagramsProvider` + SPI `HbDiagramRenderer`), а desktop-хост адаптирует к нему
контракт, поэтому фича не входит в `SERVICE_CONTRACT_FEATURES`. Движок PlantUML и DI — только в `jvmMain` impl
(локально, в отдельном процессе-воркере с малым heap и таймаутом, в песочнице SANDBOX, без сети); на Android/iOS биндинга
нет, и fence остаётся кодом.

`features/scheduler/api` также содержит профильную машину `TaskGraphMachineKey`: валидация DAG,
AllOf/AnyOf, готовность, попытки, невозможные зависимости, отмена и решения восстановления.
Запуск следует только после сохранения попытки; зависимости проверяются по сохранённым результатам,
а не по событиям шины. SPI `ScheduledTaskHost` сохраняет чат, возвращает подтверждённый исход и
останавливает конкретное задание. `RestoresSessionTurns` (`facade:api`) — адаптерная квитанция хода и
свежая проверка native state; обычный `ReconcilesSession` и кешированный Ready не доказывают остановку.

`features/scheduler/api` — машина сна и пробуждения сессий (`SchedulerMachineKey`, ProfileScope) плюс единая
профильная шина событий: ключи `EventKey` (пространства `system` / `session` / `action` / `custom`, только через
фабрики `EventKeys`), события `BusEvent` и сервис `SchedulerBus` (горячий поток без replay, публикация с
`EventOrigin`). Ожидание переживает рестарт только через машину; шина событий не хранит. Сопоставление событий
и дедлайнов с пробуждениями — чистые переходы спеки. Пакет `scheduler.api.spi` — `ScheduledSessionHost` (доставка
промпта пробуждения в сессию и создание сессии-помощника; реализуют `scheduler:impl` и хосты чатов, например
`ai-studio:impl`), `ScheduledWakeOwner` (живой допуск пробуждений владельца: Allow/Defer/Drop; контрибуции фич,
например checklist и harness), `ScheduledEventOwner` (дополнительный допуск по доверенному источнику события)
и `SchedulerEventSource` (системные сигналы платформ); пакет используют только реализующие модули и
`platform-main:di-bundle` — соглашение проверяется на ревью (в `FeatureLayerDependency` пакета нет). Хост обязан
показывать вызовы инструментов и обслуживать разрешения; без владеющего сессией хоста пробуждение отбрасывается. Запуск фонового действия агентом требует решения по таблице доверия как Command. Одобрение кода скрипта
покрывает последующие запуски workflow и помощников по событиям; такие помощники получают Ask и общие квоты. Payload событий — недоверенные данные; payload и заметки не логируются.

`HelperAgents` в `scheduler:api` — исключение для профильной координации помощников: общий lease с очередью,
пустой durable чат до prompt, коррелированные result/cancel и durable outbox `finish`. Квоты заданы чистой
`BackgroundCapacityMachineSpec`; команды scheduler и helpers разделяют 8 слотов профиля. Lease закрывается
только после подтверждённого завершения native work; неопределённая отмена удерживает слот. Хост реализует
расширения `ScheduledSessionHost` с безопасными дефолтами (без fallback в старый spawn), хранит helper marker
даже без родителя, проверяет owner/parent при recovery и потолок доверия на каждом ходе. Тексты не логируются.
`BackgroundAgents` в `scheduler:api` — фоновые помощники, которых другая фича (адаптивные субагенты) запускает для сессии
и читает сама: это scheduler-действия с общей ёмкостью, журналом, восстановлением и событием `action.<id>.finished`
(wake на нём будит родителя). Запись хранит владельца `retainedBy`: готовый результат не удаляется без ожидающего wake,
пока владелец не подтвердит его `acknowledge`. `start` возвращается после создания чата-помощника, первый промпт
доезжает в профиле; помощник фиксирует `HelperModelOptions` (effort; прежние поля ревью — только совместимость). `schedule` подтверждает wake
только после проверки хоста, принятия машиной и durable-записи через общий планировщик. Без scheduler actions — отказ.
`LocalCommands` в `scheduler:api` — запуск программы с точными аргументами в сохранённом проекте вне хода агента
и scheduler-действий, на том же ограниченном раннере (дерево процессов, таймаут, без секретных переменных окружения):
слова экранируются буквально для shell раннера, без расширения и разбиения; на Windows слова со спецсимволами
`cmd.exe` (их повторно разбирают `.bat`/`.cmd`), `"` и пустые отклоняются (`Invalid`). Контракт не даёт полномочий и не зависит
от тоглов и ёмкости планировщика: допуск и ревью — у вызывающего (команды скриптов харнесса). Только Desktop.
`HelperCapacityRecoverySource` восстанавливает подтверждённые слоты общим барьером до любого нового acquire,
даже если фича выключена. Источник читает только свой журнал: granted-метка записывается после получения слота
и до create, helper id — до любого prompt; Planned/queued не восстанавливаются. Старый producer должен быть
остановлен. Stable reservation связывается по точным owner/parent/helper без новой очереди; ошибка adoption
не освобождает слот. Запись без helper доказывает pre-prompt и разрешает только cleanup-only lease, без create/prompt.
`HelperPrompt.handoff` — неизменяемый host-контекст точного исходного запроса
и владельца-фичи; хост сохраняет его до открытия native session, затем отдельно фиксирует точный target
до передачи контекста и допуска prompt. `ScheduledHelperPromptOwner` — профильный SPI переноса контекста и живого допуска перед первым prompt;
явный владелец единственный, observers точного инициатора пересекаются независимо от toggles. Durable IO
заканчивается до Allow; хост повторяет проверку после записи Submitting, перед native send.
Подготовленный target не является квитанцией native acceptance;
повторное использование request с иным handoff запрещено. Payload и текст prompt не доказывают ancestry.
`ScheduledHelperCatalog` даёт точечное обратное чтение метаданных по сессии и ограниченные страницы по owner
без запуска движка; `HelperAgents` проверяет идентичность, порядок и неоднозначность хостов. Выбор target
по умолчанию допустим только у помощника без родителя. Если target не передан, помощник с родителем
наследует его сохранённый target; неизвестный target родителя запрещает создание, без fallback к настройкам профиля.

`features/harness/api` дополнительно содержит публичные пакеты `script`, `event`, `workflow`, `process` и `github`:
интерфейсы контекста одобренного скрипта, регистрации хуков/инструментов/событий, доступа к активным
сессиям, owned-пробуждениям и запуска workflow, чистый replayable workflow DSL и его DTO, а также чистую модель
durable-процессов (`ProcessRecord`, `ProcessCommand`, `reduce`, `recovery`) без IO.
Это явное исключение сервисного контракта; базовые классы только получают зависимости конструктора
и регистрируют определение, без IO, компилятора или runtime-реализации. `HARNESS_API_VERSION` входит
в ключ кэша компиляции. Типы facade/scheduler/coroutines/JSON в публичных сигнатурах экспортируются
через `api(...)`. Данные скриптов и события скрывают тексты и вложенные данные в `toString`;
scheduler-события не содержат wake note, payload шины — недоверенные данные.
Рантайм повторно проверяет активацию и квоты при каждом обращении; чтение сессий ограничено теми,
где харнесс активен. Хуки только добавляют контекст, запрещают или требуют вопрос и не запускают
send/wake/spawn/workflow. Ограничения (Off/hosted_off, Deny/Ask-хуки) действуют от всех подходящих харнессов
сессии, лимит активных — только на вклад. Внешние фичи шлют харнессу только `HarnessIntent.Public`
(`Attach`/`Detach`/`Reload`); правки — `HarnessIntent.Internal.Edit` внутри фичи, у `HarnessRunsMachineKey`
публичных интентов нет. Одобрение исходника покрывает последующие запуски workflow и помощников из
скрипта, но не расширяет доверие помощника выше Ask и не отменяет общие lease/cancel barriers.
`ScheduledRequestOriginObserver` переносит ограничения точных причин обычных host-промптов (включая TaskGraph)
до хуков и native submission. Это монотонная durable-запись без выдачи разрешения; ошибки запрещают отправку,
существующий live gate остаётся владельцем допуска. Провайдеры ленивы и сохраняют перенос при выключенной фиче.
`RequestInitiator` планировщика сохраняет точную пару сессия/запрос из фасада для переноса ограничений:
это не право собственности и не разрешение. Допуск учитывает инициатора и источник события независимо,
в том числе при пробуждении по времени; неизвестный legacy-запрос не восстанавливается по тексту или turn id.
Прямой запуск агентом остаётся Command по таблице доверия. Лог-API и уведомлений скриптов нет.
`ScriptData` даёт ограниченное JSON-хранилище всего харнесса с атомарной записью по ревизии: реализация в `impl`
использует профильный `SecretStore`, проверяет опубликованную активацию и уведомляет поверхности после фиксации.
`ScriptProcesses` (пакеты `script` и `process`) хранит durable-процессы разработки в том же пространстве: запись
процесса — чистая сериализуемая модель `ProcessRecord`, изменяемая только командами `ProcessCommand` через чистый
`reduce` без IO (таблица переходов — в KDoc `ProcessCommand`); сервис в `impl` читает, редуцирует и пишет её по
ревизии пространства. Все процессы харнесса лежат одним конвертом в зарезервированном ключе `hb_processes`, поэтому
открытие, изменение и удаление — одна атомарная запись, без индекса, который мог бы разойтись с записями. Идентификаторы, результаты и записи журнала не логируются; ссылки ограничены видимым ASCII
без кавычек, поэтому `ProcessLimits.RECORD_BYTES` — доказанный потолок (проверяет тест). Новые поля записи обязаны
иметь значения по умолчанию; хранимые имена вариантов и перечислений фиксируются `@SerialName` и тестом, поля
записи не переименовываются.
Контракт распределённого владения — отдельная чистая модель `ProcessOwnership` / `OwnershipCommand` /
`reduceOwnership` в том же пакете `process`: key, host identity, epoch, revision и фазы явной передачи.
Она не даёт владение локальному `ProcessRecord`: host обязан использовать линейризуемый общий CAS,
держать admission permit до завершения вызова и проверять остановку native-исполнителей перед export.
Команды и receipts не выдаются скриптам как host-операции; потеря сети и истечение аренды не разрешают takeover.

`ScriptGitHub` — типизированный порт GitHub без IO в `api`: наблюдения, сверка и устойчивые внешние ссылки.
Транспорт, постоянный реестр ключей `hb_github` в защищённом пространстве харнесса и проверки допуска — в `impl`;
тексты GitHub не выдают полномочий, а гранты скрипта не заменяют независимый host-owned допуск merge/release/dispatch.

`ProcessArchiveReader` — профильный сервис только чтения защищённых immutable snapshots процессов вне `ScriptData`:
он разрешает устойчивые `ProcessArchiveRef` и даёт ограниченные страницы/поиск даже после удаления харнесса.
Реализация — профильный `SecretStore`, очищаемый явным wipe профиля; архив не экспортирует техническое состояние
в публичные системы. Запись архива и освобождение активной квоты принадлежат `harness:impl`.
`ScriptUi` (`ui.method`) публикует методы для интерфейсов service-as-ui: их вызывает нажатие пользователя без хода
агента, с полномочиями одобренного скрипта; `harness:impl` реализует для этого `ServiceUiProvider`.

`features/adaptive-subagents/api` кроме профильной машины библиотеки описаний моделей (`ModelProfilesMachineKey`) содержит
чистые типы описаний и запроса субагента и сервисный контракт `AdaptiveModels`: выбор конфигурации субагента
(движок × подключение × модель × effort) среди включённых пользователем моделей по приоритету качества, скорости и
стоимости — запрос/ответ без длительного флоу, поэтому без машины. Вызывающие (organic-ai, harness, обычные чаты)
сохраняют прежнее поведение на `ModelChoice.Inherit`; текст задачи не логируется. `ModelProfilesView` — только чтение
библиотеки, изменения — `Public` интенты машины.

`features/context-window-optimization/api` кроме машины содержит чистые функции без IO: `decideCompaction`, журнал
прогресса (`updated`/`render`), бриф продолжения `continuationBrief` и `handoffSplit`. Ход handoff-выжимки опознаётся
по конвенции `HANDOFF_REQUEST_PREFIX` в request id (перехват инструментов) и по директиве-маркеру в транскрипте;
другие хосты не используют этот префикс для своих запросов.

`features/project-config/api` кроме машины `ProjectConfigMachineKey` содержит раскладку дерева конфигурации
(`ConfigLayout`, `ConfigPath`, `ConfigLimits`), модель юнитов, проверок и предложений, чистые `reconcile` /
`bundleProposals` и SPI `projectconfig.api.spi.ConfigSection` — разделы дерева, которые реализуют фичи-владельцы
(`harness:impl`, `service-as-ui:impl`, `agent-learning:impl`) и связывают в профильный мультибиндинг. Пакет `spi`
используют только реализующие модули и `platform-main:di-bundle` (проверяется на ревью). Раздел кодирует свои сущности
детерминированно, проверяет юнит без применения и применяет его только после доверия пользователя — своими интентами,
поэтому `Internal`-интенты других машин наружу не выходят. Другие фичи шлют машине только чтение и скрытие
(`Reload`, `Sync`, `Dismiss`, `OpenBundle`, `CloseBundle`); доверие и запись папок и архивов (`Trust`, `KeepApp`,
`RemoveFromProject`, `SaveToProject`, `Export`, `ImportToProject`) — `Internal`-команды экрана самой фичи.
Пути проектов не покидают `project-config:impl`; тексты, код и причины ревью не логируются.

`features/service-as-ui/api` — интерфейсы агента: профильная библиотека поверхностей (`UiSurface`, чистые
`UiLibrary.apply` — создание/замена по ожидаемой ревизии, включение, удаление, `Purge` удалённых владельцев) и SPI
`serviceasui.api.spi.ServiceUiProvider`: владельцы поверхностей (харнессы) и их методы, которые поверхности вызывают
нажатием пользователя без хода агента, с полномочиями владельца. Пакет `spi` используют только реализующие модули
(`harness:impl`) и `platform-main:di-bundle` — соглашение проверяется на ревью. Спека поверхности (узлы, действия,
привязки, валидатор) — внутренняя модель `impl`: наружу уходит только исходный JSON в `UiSurfaceContent.spec`.
Данные вызовов (`UiCallContext`, `UiMethodCall`, `UiMethodResult`) скрывают аргументы, значения и пути в `toString`.
Профильная машина `ServiceUiMachineKey` (без persist) держит библиотеку, места хостов и панели доков. Хосты (ai-studio)
шлют только `BindHost`/`UnbindHost`/`OpenPanel`/`ClosePanel`/`Reload`, читают `panels` и outputs `PromptRequested` /
`CardFocusRequested`; запрос фокуса повторно проверяется студией по чату и наличию карточки в транскрипте;
правки библиотеки — `Internal.Edit` внутри фичи (инструменты агента, экраны настроек), один слот записи (`Busy` —
повтор вызывающим). Поверхности удалённого владельца удаляются только по полному снимку его провайдера.

`features/planning-mode/api` кроме машины `PlanningMachineKey` (ProfileScope) содержит чистые функции без IO: правку
секции markdown `applyEdit` (заголовки внутри code fence не считаются), `planTitle`, блок плана для промпта
`renderPlanBlock`, `externallyEdited`, а также только читающий `PlanningView`, имена инструментов `PlanningTools` и
лимиты `PlanLimits`. Классификатор читающих shell-команд `isReadOnlyCommand` — деталь реализации хука режима только
чтения и живёт в `impl` (`impl/domain`). Изменения планов — только `Public`
интенты машины; текст плана — пользовательские данные и не логируется.

`features/auto-continue/api` кроме профильной машины `AutoContinueMachineKey` (режимы чатов «Выкл / Подсказки /
Автопилот», запросы к продолжателю, отсчёт и отправка) содержит чистые `dialogOf` (диалог для продолжателя из истории:
сообщения пользователя и последний текст каждого хода агента, без инструментов и размышлений) и `isNearRepeat`,
только читающий `AutoContinueView` и SPI `AutoContinueHost` — отправку реплики автопилота в чат; его реализует хост
чатов (`ai-studio:impl`). Хост сам сообщает машине события хода (`TurnStarted`/`TurnSettled`/`TurnAwaitsHuman`/
`TurnFailed`) и решает, ждёт ли ход человека. Тексты диалога и вариантов — пользовательские данные и не логируются.

### Фичи сервисного контракта

Фича, чей `api` — только сервисный контракт без бизнес-машины и у чьего `impl` есть слой `ui` (сейчас `search-engine`),
объявляется в списке `FeatureLayer.SERVICE_CONTRACT_FEATURES` (`lint/detekt-rules`). Только для таких фич слой `impl.ui` может напрямую
использовать типы своего `api` (отображение значений контракта); чужие `api` и интенты машин из UI по-прежнему
запрещены. Проверка по имени фичи в логике правил не допускается — только через этот список. Добавление фичи
в список — решение владельца, фиксируемое здесь.

Инструменты хоста, исполняемые транспортом адаптера (поиск), регистрируют обычную контрибуцию
с `isAdapterOperated = true`: каталог, декларации доступности, action и approval принадлежат владельцу.
Они не выдаются generic hosted bridge. Адаптер вызывает `authorizeHosted` под тем же lifetime,
а затем свой транспорт; обычные контрибуции через этот путь не авторизуются. Политика использует
`hostedOff`, не native On; хук получает исходные аргументы и `isNative = false`.

`questionnaire/api` и `checklist/api` содержат узкие remote-screen контракты для вложенных экранов студии:
открытие хэндла по source/card id, поток JSON-проекций с ревизиями и dispatch с барьером применения ввода.
UI-типы и FlowMVI остаются в screen-model/impl. Хэндл владеет отдельным стором, профильная машина общая;
закрытие хэндла освобождает его scope и ожидающие dispatch. Это не альтернативный domain API.
