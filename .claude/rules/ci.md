# CI (`.github/workflows`)

CI проверяет необходимый минимум. Автоматически на PR идут только проверки без сборки: commit policy и тесты
скриптов. Обязательных Gradle-сборок нет: собираются только затронутые модули, вручную через `module-build.yml`,
когда агент решает, что ему нужна ОС, которой нет локально, или по просьбе пользователя. Полная сборка и тесты —
только при выпуске релиза (`release.yml`). Правила пользования CI —
раздел «CI» в `AGENTS.md`.

| Workflow | Когда | Что |
|---|---|---|
| `commit-policy.yml` | каждый PR, включая draft | токенный бюджет каждого коммита — обязательна по политике репозитория (в ruleset не required check) |
| `scripts.yml` | PR меняет `scripts/`, проверяемый ими workflow или ресурсы Pi | unit-тесты Python-инструментов |
| `module-build.yml` | вручную: агент или пользователь | задачи затронутых модулей (`:<module>:<task>`) на выбранной ОС |
| `jcef-runtime.yml` | вручную: метка `jcef-runtime` на PR или `workflow_dispatch` | нативный рантайм JCEF (`native/jcef`) на пяти хостах, проба и `jcef-release`; без публикации |
| `review-approve.yml`, `close-fixed-issues.yml` | `/reviewed`, мерж PR | действия бота, без сборки |
| `release.yml` | вручную из `master`: уровень `patch` / `minor` / `major`; `dry_run` — без публикации, допускает рабочую ветку | версия → JVM-тесты на Linux → Linux DEB и общая Wasm-панель → параллельно отдельные Android и iOS, остальные desktop-сборки и платформенные тесты → публикация пяти установщиков macOS/Windows/Linux; без detekt; тег вычисленной версии и релиз для автообновления |

Новые workflow, джобы, шаги сборки, платформы, матрицы и триггеры, расширение `paths` — только с согласия
пользователя. Изменяя или добавляя workflow:

- **Commit policy** не фильтруй по путям, не пропускай условием `if` и не отключай. Пропущенная джоба отчитывается
  успехом поверх прежнего падения, поэтому обязательные проверки не пропускаются ни по событию, ни по путям.
- **Автоматические проверки PR** — без сборки Gradle, триггер `pull_request`. Не `push` в рабочие ветки (вместе
  с PR это двойной прогон) и не `push` в `master`. Бот-workflow (`issue_comment`, `pull_request_target`) код PR
  не собирают и не выгружают.
- **Сборка** — только через `module-build.yml`: отдельный workflow под фичу, модуль или ОС не создавай. Он принимает
  только задачи модулей и отклоняет задачи всего проекта (`build`, `allTests`, `check`), опции Gradle, задачи `run*`
  и iOS-задачи не на macOS. Запуск исполняет копию workflow из ветки `--ref`: проверки входа — часть workflow,
  а не защита от правки в ветке. Согласованные исключения:
  - `release.yml` собирает и проверяет проект на Linux, macOS и Windows только для выпуска релиза;
    задачи отладки и проверки PR туда не добавляй. Detekt (включая ktlint и compose-rules)
    при сборке релиза не запускай: они проверяют изменения локально через `verify`.
    Тесты правил `:lint:detekt-rules:test` сохраняются — это unit-тесты, а не запуск линтера по проекту.
  - `jcef-runtime.yml` собирает нативный рантайм JCEF, который не является Gradle-модулем, на всех пяти
    хостах сразу, без входов; запуск по метке исполняет копию из PR.
- **`paths`** — только файлы, меняющие результат проверки; тесты, ресурсы, схемы и документацию, которые проверка
  не использует, исключай (`!…`).
- **Платформы** — `ubuntu-latest`, если результат не зависит от ОС; macOS/Windows — только для поведения,
  которое отличается на этой ОС (упаковка, нативный код, iOS). Матрица — без дублирующих комбинаций.
- **Каждая джоба** — `timeout-minutes`, минимальные `permissions`; проверки PR — `concurrency` с
  `cancel-in-progress: true` на PR: номер PR или `github.ref` (для `pull_request` это `refs/pull/<N>/merge`).
  Бот-workflow задают `concurrency` по своей семантике или обходятся без неё (approve не отменяется).
- **Диагностические и временные workflow** (триггер на свою ветку, отладочные матрицы, выгрузка логов) не создавай:
  проверка на другой ОС — `module-build.yml`.
- Изменённый workflow проверь локально: синтаксис YAML и выражения (`actionlint`, если установлен), разбор входов
  `workflow_dispatch` — скриптом на типичных и вредных значениях.

## Кэш и артефакты релиза

- `.github/actions/gradle-cache` разделяет переносимые результаты Gradle и зависимости/инструменты хоста.
  Кэш задач лежит в `.gradle-build-cache` (путь `HEARTBEAT_BUILD_CACHE_DIR`, одинаковый для основной сборки и
  `build-logic`) и передаётся между ОС. Общий снимок сохраняют JVM- и Linux-этапы. Desktop-потребители только читают его;
  iOS- и тестовый macOS-этапы дополнительно сохраняют свои native-результаты между релизами. Сначала
  восстанавливается native-снимок, затем поверх него текущий Linux: файлы кэша адресуются хэшем и объединяются.
  Native-снимок привязан к активным версиям Xcode и SDK macOS/iPhoneOS/iPhoneSimulator, без fallback между ними.
  Зависимости и wrapper Gradle привязаны к ОС, архитектуре, конфигурации сборки и этапу: новый релиз без
  изменения конфигурации не создаёт очередную копию этих зависимостей.
  Распакованные JDK и Kotlin/Native не архивируются: их размер вытесняет полезные кэши сборки из квоты Actions.
- CI явно выбирает установленные Microsoft JDK 17 (компиляция, включая Windows ARM64) и JBR 21 (desktop);
  случайный JDK из образа runner не меняет ключи задач. Демон требует Java 21 без привязки к вендору,
  поэтому использует установленный JBR и не скачивает третий JDK. Локально подходит любой JDK 21;
  закреплённые download URLs остаются fallback, если подходящей установки нет.
- Kotlin/Native отключает Gradle-кэш для framework: стандартное восстановление теряет симлинки.
  iOS сохраняет отдельный tar-архив только после успешной release-линковки. Ключ включает точные commit/tree,
  версию релиза, Xcode/SDK и фактические JDK; fallback отсутствует. Перед пропуском линковки проверяются
  metadata, SHA-256 и содержимое архива. Это ускоряет повтор того же билда; изменённые исходники линкуются заново.
- JVM-тесты учитывают ОС и архитектуру в ключе задачи: переносимый кэш компиляции не подменяет проверку поведения
  на другом хосте. Поэтому macOS выполняет JVM-тесты повторно вместе с iOS-тестами.
- Linux один раз собирает оптимизированную Chromium-панель (`prepareChromiumPanelArtifact`). Остальные desktop
  jobs скачивают артефакт `chromium-panel` этого запуска и передают `-Pheartbeat.chromiumPanelDir=.release-panel`.
  При неполном артефакте упаковка завершается ошибкой. Без свойства локальная сборка собирает панель сама.
- ProGuard остаётся отдельным для каждой ОС: его результаты не объявляются переносимыми принудительно.
  `--profile` и артефакты `gradle-reports-*` сохраняют длительности задач и XML результатов тестов.
- Linux x64 (Ubuntu 24.04, X11/XWayland) публикуется как `desktop-linux-x64` вместе с остальными установщиками.
  Перед упаковкой проходят нативные проверки Secret Service в изолированной D-Bus-сессии и встроенного браузера
  под Xvfb. DEB объявляет зависимости libsecret/JCEF; пользовательская сессия требует разблокированный Secret Service.
  Обновление Linux открывает страницу DEB: системным пакетом управляет пакетный менеджер.
