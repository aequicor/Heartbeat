# CI (`.github/workflows`)

CI проверяет необходимый минимум. Автоматически на PR идут только проверки без сборки: commit policy и тесты
скриптов; на push в `master` — только `prerelease.yml`. Обязательных Gradle-сборок нет: собираются только затронутые модули, вручную через `module-build.yml`,
когда агент решает, что ему нужна ОС, которой нет локально, или по просьбе пользователя. Полная сборка и тесты —
только при выпуске релиза (`release.yml`). Правила пользования CI —
раздел «CI» в `AGENTS.md`.

| Workflow | Когда | Что |
|---|---|---|
| `commit-policy.yml` | каждый PR, включая draft | токенный бюджет каждого коммита — обязательна по политике репозитория (в ruleset не required check) |
| `scripts.yml` | PR меняет `scripts/`, проверяемый ими workflow или ресурсы Pi | unit-тесты Python-инструментов |
| `module-build.yml` | вручную: агент или пользователь | задачи затронутых модулей (`:<module>:<task>`) на выбранной ОС |
| `jcef-runtime.yml` | вручную: метка `jcef-runtime` на PR или `workflow_dispatch` | нативный рантайм JCEF (`native/jcef`) на пяти хостах, проба и `jcef-release`; без публикации |
| `review-approve.yml`, `close-fixed-issues.yml` | `/reviewed`, мерж PR | действия бота, без сборки |
| `prerelease.yml` | push в `master` | только Linux, ≤ 20 мин: `affectedBundles` по diff пуша (и изменение `platform-main/launcher` — поезд с новым подписанным лаунчером при тех же бандлах) → `jvmTest` затронутых бандлов (и тесты лаунчера) и `verifyBundleMembership` → `assembleBundle` + `bundleManifest` → `scripts/train_manifest.py` → pre-release `train-t<sha12>` с `train-manifest.json` и только изменившимися jar. Пуш без затронутых бандлов ничего не публикует |
| `release.yml` | вручную из `master`: уровень `patch` / `minor` / `major`; `dry_run` — без публикации, допускает рабочую ветку | версия → JVM-тесты на Linux → Linux DEB и общая Wasm-панель → параллельно Android (APK, подпись ключом окружения `android-signing`) и iOS (неподписанный IPA), остальные desktop-сборки и платформенные тесты → поезд бандлов (продвижение `train-t<sha12>` этого коммита или сборка) → гейт `scripts/check_installer_size.py` (≤ 160 МиБ: платформа и полный seed поезда, цель — 50 МиБ; пять установщиков) → публикация установщиков macOS/Windows/Linux, APK, IPA и поезда; без detekt; тег вычисленной версии и релиз для автообновления |

Новые workflow, джобы, шаги сборки, платформы, матрицы и триггеры, расширение `paths` — только с согласия
пользователя. Изменяя или добавляя workflow:

- **Commit policy** не фильтруй по путям, не пропускай условием `if` и не отключай. Пропущенная джоба отчитывается
  успехом поверх прежнего падения, поэтому обязательные проверки не пропускаются ни по событию, ни по путям.
- **Автоматические проверки PR** — без сборки Gradle, триггер `pull_request`. Не `push` в рабочие ветки (вместе
  с PR это двойной прогон) и не `push` в `master`. Бот-workflow (`issue_comment`, `pull_request_target`) код PR
  не собирают и не выгружают. Исключение — `prerelease.yml` (push в `master`, публикация поезда).
- **Сборка** — только через `module-build.yml`: отдельный workflow под фичу, модуль или ОС не создавай. Он принимает
  только задачи модулей и отклоняет задачи всего проекта (`build`, `allTests`, `check`), опции Gradle, задачи `run*`
  и iOS-задачи не на macOS. Запуск исполняет копию workflow из ветки `--ref`: проверки входа — часть workflow,
  а не защита от правки в ветке. Согласованные исключения:
  - `release.yml` собирает и проверяет проект на Linux, macOS и Windows только для выпуска релиза;
    задачи отладки и проверки PR туда не добавляй. Detekt (включая ktlint и compose-rules)
    при сборке релиза не запускай: они проверяют изменения локально через `verify`.
    Тесты правил `:lint:detekt-rules:test` сохраняются — это unit-тесты, а не запуск линтера по проекту.
  - `jcef-runtime.yml` собирает нативный рантайм JCEF, который не является Gradle-модулем, на всех пяти
    хостах сразу, без входов; запуск по метке исполняет копию из PR.
- **`paths`** — только файлы, меняющие результат проверки; тесты, ресурсы, схемы и документацию, которые проверка
  не использует, исключай (`!…`).
- **Платформы** — `ubuntu-latest`, если результат не зависит от ОС; macOS/Windows — только для поведения,
  которое отличается на этой ОС (упаковка, нативный код, iOS). Матрица — без дублирующих комбинаций.
- **Каждая джоба** — `timeout-minutes`, минимальные `permissions`; проверки PR — `concurrency` с
  `cancel-in-progress: true` на PR: номер PR или `github.ref` (для `pull_request` это `refs/pull/<N>/merge`).
  Бот-workflow задают `concurrency` по своей семантике или обходятся без неё (approve не отменяется).
- **Диагностические и временные workflow** (триггер на свою ветку, отладочные матрицы, выгрузка логов) не создавай:
  проверка на другой ОС — `module-build.yml`.
- Изменённый workflow проверь локально: синтаксис YAML и выражения (`actionlint`, если установлен), разбор входов
  `workflow_dispatch` — скриптом на типичных и вредных значениях.

## Поезд бандлов и переход пользователей

- `prerelease.yml` — единственный workflow, который запускается на `push` в `master` (согласованное исключение:
  он публикует, а не проверяет PR). Linux-only, без установщиков, `contents: write` только у джобы публикации.
  Сборка использует `.github/actions/bundle-train`: `assembleBundle` и `bundleManifest` с
  `-Pheartbeat.bundleVersion=<train>`, затем `scripts/train_manifest.py`. Поезд несёт только jar, чей SHA-256
  изменился относительно предыдущего `train-*`; неизменный бандл сохраняет прежние версию, имя jar и поле `url`
  (абсолютный https-адрес jar в релизе, который его впервые опубликовал: по нему качает лаунчер при первом запуске,
  `missingDownloads` в app-update находит jar в более раннем релизе). Поэтому пре-релизы `train-*` не удаляются.
  Смена `platformApi` публикует всё заново. База `affectedBundles` — коммит последнего опубликованного поезда.
- **Подпись лаунчера** (`.claude/rules/launcher.md`). Поезд несёт jar лаунчера записью `kind=launcher`, подписанной Ed25519.
  Приватный ключ — секрет `HEARTBEAT_LAUNCHER_SIGNING_KEY` окружения GitHub `launcher-signing` (политика веток — только
  `master`); джобы, которым он нужен (`build` в `prerelease.yml`, `train` в `release.yml`), объявляют это окружение, а
  `bundle-train` получает ключ входом `launcher-signing-key`. `dry_run` релиза берёт окружение `launcher-dry-run` без секретов:
  лаунчер в таком поезде без подписи, и установленные приложения его не принимают. Публичные ключи (основной и запасной)
  лежат в репозитории, в `trusted-keys.txt` селектора; приватный запасной хранится офлайн у владельца. Уровень лаунчера
  `-Pheartbeat.launcherApi` — число коммитов первой родительской истории (`master`), менявших `platform-main/launcher`
  (`git rev-list --count --first-parent`, нужна полная история, `fetch-depth: 0`): растёт вдоль `master` и не меняется,
  пока лаунчер не тронут. Подпись покрывает `version`, то есть id поезда, поэтому в каждом поезде одна и та же jar
  подписывается по-разному; `train_manifest.py` не сравнивает подписи и переиспользует неизменную запись вместе с её
  версией и своей подписью (уровень и подписанность должны совпасть). Ключ и уровень передаются во все вызовы Gradle,
  которые зависят от `bundleManifest` (иначе манифест перезапишется без подписи), но не доходят до JavaExec смоука
  (`verifyShrunkTrain` снимает переменную: в смоуке работает код репозитория). Вход `launcher-signing-required` (`true` в
  `prerelease.yml` и в обычном релизе) роняет сборку без ключа, а перед записью поезда `bundle-train` проверяет, что запись
  подписана. Встроенный лаунчер установщика при опубликованном seed берётся из этого seed. Смена ключей — новый
  установщик: ключи зашиты в селектор, а не в поезд.
- Идентификатор поезда — `t<sha12>`, тег — `train-<id>`; поле `train` и ассет `train-manifest.json` — контракт
  с app-update и лаунчером. Меняя формат, правь `scripts/train_manifest.py`, его тест и `TrainManifest.kt` вместе.
- `release.yml` продвигает поезд своего коммита (скачивает ассеты `train-t<sha12>`; если пре-релиза нет —
  собирает) и прикладывает его к полному релизу. Размер установщиков — гейт `scripts/check_installer_size.py`
  перед публикацией. Установщик — платформа (JRE, селектор `SelectorMain` как `-javaagent`, встроенный лаунчер файлом
  `launcher-embedded.seed`, сторонние библиотеки своей ОС без proguard) и seed: полный опубликованный поезд коммита. Джоба `train` собирает seed (`scripts/train_seed.py`: jar
  поезда плюс недостающие по `url`, с проверкой SHA-256, как `<jar>.seed`) и выгружает артефакт `train-seed`; desktop-джобы
  передают его как `-Pheartbeat.seedDir=.release-seed`. Состав платформы задаёт упаковка `platform-main/desktop`.
- **Переход пользователей.** 1) Последний монолитный релиз выходит вместе с новой платформой (лаунчер + загрузчик,
  `platformApi` ≥ 1; с селектором слотов лаунчера — `platformApi` 2, поезда с записью лаунчера старые установки не берут): его обновление ставится как раньше, полным установщиком. 2) Дальше стабильный канал получает
  полные релизы только при смене платформы (JRE, лаунчер, `platformApi`, схема БД); остальное идёт поездами.
  3) Бета-канал (`app_update.beta`) принимает каждый пре-релиз `train-*`; поезд с более новым `platformApi`
  пропускается и откатывается на полный релиз. 4) Откат — лаунчер возвращает предыдущий поезд при `BundleHealth.Failed`.
  Пользователи не переустанавливают приложение: установщик нужен лишь новой установке и смене платформы.

## Кэш и артефакты релиза

- `.github/actions/gradle-cache` разделяет переносимые результаты Gradle и зависимости/инструменты хоста.
  Кэш задач лежит в `.gradle-build-cache` (путь `HEARTBEAT_BUILD_CACHE_DIR`, одинаковый для основной сборки и
  `build-logic`) и передаётся между ОС. Общий снимок сохраняют JVM- и Linux-этапы. Desktop-потребители только читают его;
  iOS- и тестовый macOS-этапы дополнительно сохраняют свои native-результаты между релизами. Сначала
  восстанавливается native-снимок, затем поверх него текущий Linux: файлы кэша адресуются хэшем и объединяются.
  Native-снимок привязан к активным версиям Xcode и SDK macOS/iPhoneOS/iPhoneSimulator, без fallback между ними.
  Зависимости и wrapper Gradle привязаны к ОС, архитектуре, конфигурации сборки и этапу: новый релиз без
  изменения конфигурации не создаёт очередную копию этих зависимостей.
  Распакованные JDK и Kotlin/Native не архивируются: их размер вытесняет полезные кэши сборки из квоты Actions.
- CI явно выбирает установленные Microsoft JDK 17 (компиляция, включая Windows ARM64) и JBR 21 (desktop);
  случайный JDK из образа runner не меняет ключи задач. Демон требует Java 21 без привязки к вендору,
  поэтому использует установленный JBR и не скачивает третий JDK. Локально подходит любой JDK 21;
  закреплённые download URLs остаются fallback, если подходящей установки нет.
- Kotlin/Native отключает Gradle-кэш для framework: стандартное восстановление теряет симлинки, поэтому
  iOS-релиз линкует framework заново в фазе Gradle Xcode-проекта (она же копирует compose-resources в приложение).
- JVM-тесты учитывают ОС и архитектуру в ключе задачи: переносимый кэш компиляции не подменяет проверку поведения
  на другом хосте. Поэтому macOS выполняет JVM-тесты повторно вместе с iOS-тестами.
- Linux один раз собирает оптимизированную Chromium-панель (`prepareChromiumPanelArtifact`). Остальные desktop
  jobs скачивают артефакт `chromium-panel` этого запуска и передают `-Pheartbeat.chromiumPanelDir=.release-panel`.
  При неполном артефакте упаковка завершается ошибкой. Без свойства локальная сборка собирает панель сама.
- ProGuard остаётся отдельным для каждой ОС: его результаты не объявляются переносимыми принудительно.
  Поезд обрабатывается ProGuard (`.github/actions/bundle-train` — им же `release.yml` собирает поезд, если пре-релиза коммита
  нет; вход `shrink`, по умолчанию `obfuscate`; правила и режимы —
  `.claude/rules/bundles.md`): `assembleBundle` идёт с `-Pheartbeat.trainShrink`, затем `:platform-main:desktop:verifyShrunkTrain`
  под xvfb (все бандлы `Healthy`, иначе поезд не пишется), затем `scripts/train_manifest.py --mappings`: маппинг каждого jar
  (`mapping-bundle-<id>-<версия>.txt`) публикуется ассетом того пре-релиза `train-*`, который первым опубликовал jar
  (контракты не обрабатываются и маппинга не имеют; неизменный jar маппинг не повторяет), по нему `scripts/retrace.py`
  восстанавливает стек-трейсы из лога с `Launch: train=<id>`. ProGuard требует JBR 21 с `jmods` (по расчёту его даёт `setup-java`
  `jetbrains`; на CI не проверено) и до 2 ГБ кучи; в пределы 20 минут `prerelease.yml` обработка пока не измерена на CI — при превышении
  проверь время `shrink*`-задач в `--profile`. Меняя состав поезда, SDK или правила, держи вместе `bundles.md`, `train-rules.pro`
  и `train_manifest.py` с тестом.
  `--profile` и артефакты `gradle-reports-*` сохраняют длительности задач и XML результатов тестов.
- Linux x64 (Ubuntu 24.04, X11/XWayland) публикуется как `desktop-linux-x64` вместе с остальными установщиками.
  Перед упаковкой проходят нативные проверки Secret Service в изолированной D-Bus-сессии и встроенного браузера
  под Xvfb. DEB объявляет зависимости libsecret/JCEF; пользовательская сессия требует разблокированный Secret Service.
  Обновление Linux открывает страницу DEB: системным пакетом управляет пакетный менеджер.

## Мобильные сборки релиза

- **Android**: `assembleRelease` подписывается, когда заданы `HEARTBEAT_ANDROID_KEYSTORE` (путь), `…_KEYSTORE_PASSWORD`,
  `…_KEY_ALIAS`, `…_KEY_PASSWORD` (`platform-main/android/build.gradle.kts`); без них APK не подписан. Ключ лежит в окружении
  GitHub `android-signing` (только `master`, keystore — `HEARTBEAT_ANDROID_KEYSTORE_BASE64`), `dry_run` берёт `android-dry-run`
  без секретов и собирает неподписанный APK. Джоба проверяет подпись `apksigner` и публикует `Heartbeat-<ver>-android.apk`.
  Потеря ключа ломает обновление поверх установленных APK: копия keystore хранится у владельца вне репозитория.
- **iOS**: Apple-аккаунта и сертификатов в CI нет. Джоба запускает `xcodebuild archive` без подписи (Gradle внутри
  build phase, его настройки, heap 8 ГБ и `org.gradle.daemon=false` — в пользовательском `gradle.properties`: кэш Gradle
  архивируется после выхода демона; `--profile` фаза не получает, `gradle-reports-ios` несёт только XML тестов) и пакует `Payload/*.app` в `Heartbeat-<ver>-ios.ipa` — для установки сайдлоадом (AltStore, Sideloadly).
