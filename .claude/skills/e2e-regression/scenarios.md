# Сценарии E2E-регрессии

Чек-лист прогона упакованного приложения `HeartbeatE2E` с мок-моделью. Иди по уровням сверху вниз:
S0 → S1 → S2; уровень ниже не начинают, пока S0 не пройден (иначе всё падает по одной причине).

Вердикт каждого сценария — один из:

- `PASS` — ожидание совпало;
- `FAIL` — не совпало (к сценарию приложи уровень дефекта по матрице из `SKILL.md`);
- `BLOCKED` — не проверен из-за другого дефекта (укажи, из-за какого);
- `SKIPPED` — не применим в этом окружении (укажи причину: нет CLI, нет расширения, macOS/Windows-only).

Обязательное доказательство для каждого сценария: что увидел на снимке окна (1–3 предложения
конкретики: тексты элементов, состояние кнопок), плюс для сценариев с моделью — запись из журнала
мока (`GET /__e2e/requests` или JSONL), плюс при `FAIL` — выдержка из лога приложения.

Уровень прогона выбирает пользователь: `smoke` = S0, `core` = S0+S1, `full` = S0+S1+S2.

| ID | Шаги | Ожидание |
|---|---|---|
| S0.1 | Запустить `HeartbeatE2E` из артефакта сборки с изолированным корнем (§2 `SKILL.md`) | Процесс жив ≥ 60 с, в `window_list` появилось новое окно `Heartbeat`, принадлежащее E2E-процессу (сопоставление по §4); в логах корня нет `FATAL`/`ERROR` на старте |
| S0.2 | Первый снимок окна | Окно отрисовано (не белое/чёрное), виден либо welcome-экран, либо студия; заголовок содержит имя приложения |
| S0.3 | Пройти welcome-мастер (если он показан): создать профиль | Профиль создан и выбран; приложение дошло до основного экрана без падения |
| S0.4 | Создать подключение на мок (§3 `SKILL.md`): openai-compatible, `http://127.0.0.1:8000`, ключ-заглушка, модель `e2e-small` | Подключение сохранено, движок доступен для выбора; в журнале мока есть запрос `GET /v1/models` |
| S0.5 | Выбрать явный «Выход»/Quit в меню/tray E2E-процесса (крестик с tray лишь скрывает окно) | Окно исчезло и процесс завершился сам за ≤ 15 с; в логах нет исключений при завершении; lock-файл не держит процесс |

`S0.5` с зависшим после явного Quit процессом или `S0.1` без окна — блокер: дальше не идти, чинить сразу.

## S1 — Core: основной пользовательский сценарий

Для S1.5–S1.6 создай отдельный временный проект в `build/e2e/project`, положи туда тестовый
`README.md` и открой coding-сессию Koog с мок-подключением (`ai.koog.coding_tools` включён).
Проверь в журнале запроса наличие `read_file` и `write_file` в `tools`; обычный чат без проекта
не предоставляет эти инструменты. Проверки подтверждения выполняй в режиме профиля «Спрашивать»;
после S1.6 верни предыдущий режим. Чтение не требует подтверждения даже в этом режиме.

| ID | Шаги | Ожидание |
|---|---|---|
| S1.1 | Создать новую сессию/чат с движком на мок-модели | Сессия появилась в списке, открыта пустая лента, поле ввода активно |
| S1.2 | Отправить `ping` | Ответ `pong: мок-модель отвечает` виден в ленте; состояние «идёт ход» сменилось на «готово»; в журнале мока ровно один запрос с этим текстом |
| S1.3 | Отправить `stream please` | Текст появляется частями (несколько снимков/`_record` фиксируют промежуточное состояние), итог — `Потоковый ответ пришёл тремя кусками.` |
| S1.4 | Отправить `отмена` и во время ожидания нажать «Стоп»/отмену | Ход прерван, индикатор остановлен, лента не содержит текст из отложенного ответа мока, приложение не зависло; в журнале мока запрос есть, соединение разорвано |
| S1.5 | Сбросить журнал мока и отправить `вызови инструмент` в подготовленной coding-сессии | `read_file` читает тестовый README без подтверждения; после результата — текст `Инструмент отработал…`; в журнале два запроса, во втором есть роль `tool` |
| S1.6 | В режиме «Спрашивать» отправить `запиши файл`, подтвердить `write_file`; проверить файл, удалить его вручную и в новой сессии повторить запрос с отказом | Подтверждённая запись создаёт `e2e-permission.txt` с текстом `e2e mock write`; отклонённая не создаёт файл, модель получает отказ, оба хода завершаются. В журнале есть имя инструмента и результат, отсутствие файла доказывает отказ |
| S1.7 | Отправить `ошибка сервера` | Ошибка 500 показана пользователю понятным сообщением (не пустая лента, не «вечная загрузка»), сессию можно продолжить |
| S1.8 | Отправить `429` | Ошибка лимита показана как ошибка провайдера/ретрая, приложение не падает |
| S1.9 | Многоходовый диалог: 3 сообщения подряд | История сохранена в порядке отправки; контекст предыдущих сообщений уходит модели (в журнале мока в последнем запросе ≥ 3 пользовательских сообщения) |
| S1.10 | Перезапустить приложение (S0.5 → S0.1) и открыть ту же сессию | Лента восстановлена целиком (resume), история не потеряна |
| S1.11 | Создать вторую сессию, переключаться между ними | Переключение мгновенное, содержимое не путается, обе сессии видны в списке |
| S1.12 | Переключить профиль (или создать второй) и вернуться | Настройки и сессии каждого профиля не смешиваются |
| S1.13 | В настройках изменить любой параметр (тема/масштаб/тогл), перезапустить | Изменение сохранилось после перезапуска и применилось к UI |
| S1.14 | Открыть раздел движков/подключений | Список движков отрисован; отсутствующие в системе CLI помечены как недоступные с причиной, а не падают |

## Что не проверяется этим прогоном

- Производительность и нагрузочные сценарии (нет целевых метрик).
- iOS/Android: прогон десктопный.
- Качество ответов настоящей модели: мок детерминирован, «умность» не оценивается
  (для этого есть режим `--real-model` и отдельные сценарии по просьбе пользователя).
- Релизная упаковка и автообновление «в бою»: `release.yml` запускает только пользователь.
