# E2E-регрессия основных функций

Прогон упакованного приложения как настоящий пользователь: мышь, клавиатура, окно, mok-модель —
без обращения к боевым провайдерам ИИ. Всё, что требует участия пользователя, запрашивается один раз
в начале (§0); дальше прогон идёт без вмешательства.

**Порядок всегда один:** права и авторизация → сборка → изоляция данных → мок-модель → запуск окна →
сценарии (`scenarios.md`) → триаж → исправления → пересборка и повторный прогон → отчёт и уборка.

## Границы навыка

- Не запускать `release.yml`, не создавать теги, не публиковать релиз — это делает только пользователь.
- Не менять CI (workflow, джобы, триггеры) и не перезапускать прогоны без просьбы пользователя.
- Не писать в реальный data root установленного Heartbeat и не запускать E2E-экземпляр без изоляции (§2):
  агент живёт внутри того же приложения и разделит с ним lock и данные.
- Не пушить в `master` напрямую и не делать force push: fixes идут через draft PR (навыки `open-pr`, `pr-fix`).
- Merge — только после `/reviewed <sha>` и зелёной commit policy (§7).

## 0. Один раз в начале: права, авторизация, предупреждение

1. Спроси у пользователя одним вызовом `questionnaire_ask` (в других рантаймах — одним сообщением) три вещи:
   - уровень прогона: `smoke` (S0) / `core` (S0+S1) / `full` (S0+S1+S2);
   - модель: детерминированный мок (по умолчанию) или `--real-model` (боевое подключение, расход токенов);
   - авторизацию полного цикла без промежуточных вопросов: «фикс → draft PR → `pr-review-and-fix` →
     `/reviewed` → merge → пересборка → повторный прогон» для блокеров и критических дефектов,
     и одним пакетным PR для минорных. Без явного «да» merge не выполнять: доводить фикс до `/reviewed`
     и останавливаться с вопросом.
   Уже заданные пользователем уровень, режим модели и разрешения сохрани; спрашивай только недостающее.
2. `computer_status` → прочитай `blockers`, `captureAvailable`, `windowCaptureAvailable`, `inputArmed`.
   - **macOS:** нужны Screen Recording и Accessibility для приложения Heartbeat (System Settings →
     Privacy & Security); после выдачи прав приложение перезапускается — предупреди пользователя заранее.
   - **Windows:** специальных разрешений не требуется; защищённый рабочий стол и UAC-диалоги недоступны.
   - Если `blockers` не пуст — покажи его пользователю и жди выдачи прав; не начинай прогон «вслепую».
3. Как только права выданы, вооружи ввод одним действием: `window_list` → `window_capture` любого окна →
   `window_screenshot`. Подтверждение на ввод запрашивается один раз на сессию при текущем уровне доверия;
   если рантайм спрашивает разрешение на каждый клик — сообщи об этом пользователю и предложи повысить
   уровень доверия сессии, иначе прогон превратится в ручное подтверждение сотен действий.
4. Предупреди: во время прогона агент владеет мышью и клавиатурой, трогать компьютер нельзя;
   длительность — от ~20 минут (`smoke`) до нескольких часов (`full` с исправлениями);
   прерывание — кнопка «Стоп» в Heartbeat (агент получит `StoppedByUser` и больше не трогает компьютер).
5. Проверь окружение: место на диске (~4 ГБ на артефакт), свободные порты 8000 и 8123, наличие внешних CLI
   (`claude`, `codex`, `node`, `py -3`/`python3`) — их отсутствие не блокирует прогон, но переводит
   сценарии S2.14 в `SKIPPED`.

## 1. Версия под тестом и сборка E2E-приложения

1. Зафиксируй версию под тестом и убедись, что дерево чистое:
   `git status --porcelain`, `git rev-parse HEAD`, `git log -1 --format=%h %s`, `git branch --show-current`.
   Грязное дерево — спроси пользователя: прогон на незакоммиченных правках даёт невоспроизводимый результат.
   Актуализируй `master`: `git fetch origin` + `git switch master` + `git pull --ff-only` (или прогоняй
   на той ветке, которую назвал пользователь, — и запиши её в отчёт).
2. Собери тестовый flavor (установщики для него запрещены — только дистрибутив):

   ```powershell
   # Windows
   .\gradlew.bat -Pheartbeat.flavor=testing :platform-main:desktop:createReleaseDistributable
   ```

   ```bash
   # macOS
   ./gradlew -Pheartbeat.flavor=testing :platform-main:desktop:createReleaseDistributable
   ```

   Сборка занимает 15–40 минут вхолодную. Запускай её **фоново средствами своего рантайма**
   (Heartbeat: `scheduler_start_action kind=command`; Claude Code: `Bash run_in_background`;
   Codex: фоновый процесс) и параллельно выполняй §0 и §3; если фонового режима нет — запусти
   синхронно с максимальным таймаутом и запроси права сразу после завершения.
   Gradle-демон не останавливай (`--stop` убьёт и Heartbeat, в котором работает агент).
3. Артефакт и проверка его существования:
   - Windows: `platform-main\desktop\build\compose\binaries\main-release\app\HeartbeatE2E\HeartbeatE2E.exe`
   - macOS: `platform-main/desktop/build/compose/binaries/main-release/app/HeartbeatE2E.app/Contents/MacOS/HeartbeatE2E`
4. Preflight упакованного рантайма (рекомендуется перед релизом, необязательно для `smoke`):
   `.\gradlew.bat -Pheartbeat.flavor=testing :platform-main:desktop:verifyReleaseHarnessCompiler` —
   запускает упакованный лаунчер с пробой компиляции харнесса и падает, если рантайм скриптов сломан.
   Аналогично доступны `verifyWindowRuntime` и `verifyBrowserRuntime`.
   Эти задачи в `AGENTS.md` отнесены к «только по просьбе пользователя» (сборка приложения целиком):
   вызов этого навыка пользователем и есть такая просьба — отдельно переспрашивать не нужно.
5. Запиши в отчёт: ОС, SHA, ветку, команду сборки, длительность, путь к артефакту.

## 2. Изолированный корень данных

E2E-приложение использует те же пути, что установленный Heartbeat: data root, single-instance lock
`<root>/run/instance.lock`, логи и регистрацию Native Messaging. Запуск без изоляции либо не стартует
(процесс перешлёт активацию уже открытому Heartbeat и завершится), либо повредит данные пользователя.

1. Создай изолированный корень в gitignored `build/` (никогда не в реальном профиле):

   ```powershell
   # Windows: build\e2e\root\{Roaming,Local}
   New-Item -ItemType Directory -Force -Path build\e2e\root\Roaming, build\e2e\root\Local | Out-Null
   $env:APPDATA      = (Resolve-Path build\e2e\root\Roaming).Path
   $env:LOCALAPPDATA = (Resolve-Path build\e2e\root\Local).Path
   $env:HEARTBEAT_TRACE = 'true'
   ```

   ```bash
   # macOS: отдельные native HOME и JVM user.home, без export в оболочку агента
   mkdir -p build/e2e/root/home
   e2e_home="$(pwd)/build/e2e/root/home"
   e2e_jvm_options="-Duser.home=\"$e2e_home\""
   ```

   Переменные ставь только в окружении дочернего процесса E2E-приложения, не в оболочке агента.
   Windows-блок выполняй в отдельном дочернем PowerShell, из него запускай приложение.
   На macOS одного `HOME` недостаточно: data root, lock, логи и dev secrets читают JVM `user.home`.
   Найди JBR, выбранный сборкой (`desktopRuntime` в `platform-main/desktop/build.gradle.kts`), и до
   запуска приложения проверь на его `bin/java` то же дочернее окружение:

   ```bash
   env HOME="$e2e_home" JAVA_TOOL_OPTIONS="$e2e_jvm_options" \
     "$e2e_jbr/bin/java" -XshowSettings:properties -version
   ```

   `e2e_jbr` — абсолютный путь к Home этого JBR. В выводе `user.home` обязан совпасть с `e2e_home`.
   Проверь также, что launcher `.cfg` и унаследованные `_JAVA_OPTIONS`/`JDK_JAVA_OPTIONS` не задают
   другого `user.home`; при конфликте устрани его только в дочернем окружении и повтори проверку.
   До успешной проверки E2E-приложение не запускай. В §4 передай те же `HOME` и `JAVA_TOOL_OPTIONS`.
   `HEARTBEAT_TRACE=true` включает подробное логирование — проще собирать доказательства.
2. Пути, откуда брать логи и данные (для доказательств и локализации дефекта):
   - Windows: `%APPDATA%\Aequicor\Heartbeat` (данные), `%LOCALAPPDATA%\Aequicor\Heartbeat\logs` (логи);
   - macOS: `$HOME/Library/Application Support/Heartbeat`, `$HOME/Library/Logs/Heartbeat`.
3. Корень по умолчанию чистый: нет профилей, подключений и секретов (тестовый flavor хранит секреты
   в локальном dev-хранилище, а не в Keychain/DPAPI). Профиль и подключение создаются в S0.3–S0.4.
   Не копируй реальный корень «чтобы работало»: это уносит личные данные и боевые ключи в прогон.
4. **Chromium-мост (S2.10) — только с явного согласия пользователя.** Регистрация Native Messaging пишет
   вне изолированного корня: Windows — `HKCU\Software\<vendor>\NativeMessagingHosts\io.aequicor.heartbeat`,
   macOS — `~/Library/Application Support/<browser>/NativeMessagingHosts/io.aequicor.heartbeat.json`.
   E2E-экземпляр перезапишет её путём к своему бинарю и сломает мост установленного Heartbeat.
   Если сценарий всё же выполняется — сначала сохрани текущее значение (файл/ключ), после прогона восстанови
   и проверь, что расширение снова видит основной Heartbeat.

## 3. Детерминированная мок-модель

Настоящие запросы к ИИ в регрессии не нужны: они медленные, платные и невоспроизводимые. Мок закрывает
все невендорные движки одним протоколом — `openai-compatible` (`CompatibleProtocol.OpenAI`): origin
`http://localhost:8000`, эндпоинты `/v1/chat/completions` и `/v1/models`, plain HTTP разрешён политикой
`isCompatibleOriginAllowed` для loopback-адресов.

1. Запусти сервер из состава навыка (только stdlib, фоново):

   ```powershell
   # Windows
   py -3 .claude\skills\e2e-regression\mock_model_server.py --port 8000 `
     --script .claude\skills\e2e-regression\mock_scenarios\core.json `
     --log build\e2e\mock-requests.jsonl
   ```

   ```bash
   # macOS
   python3 .claude/skills/e2e-regression/mock_model_server.py --port 8000 \
     --script .claude/skills/e2e-regression/mock_scenarios/core.json \
     --log build/e2e/mock-requests.jsonl
   ```

2. Проверь сам мок перед прогоном — самопроверка поднимает сервер на случайном порту и прогоняет
   HTTP-контур (models, обычный и потоковый ответ, tool call, журнал, сброс, 404):

   ```powershell
   py -3 .claude\skills\e2e-regression\mock_model_server.py --selftest `
     --script .claude\skills\e2e-regression\mock_scenarios\core.json
   ```

   Без `--script` самопроверка загружает встроенный `core.json`; её ожидаемые ответы соответствуют
   этому сценарию. Произвольные сценарии проверяй отдельными запросами.
   Ожидание — `selftest OK: … checks…` и код возврата 0. Затем убедись, что порт мока отвечает:
   `Invoke-RestMethod http://127.0.0.1:8000/v1/models` (`curl` на macOS) — модели `e2e-small`, `e2e-large`.
3. Подключи мок в приложении (S0.4): протокол «OpenAI-совместимый», origin `http://127.0.0.1:8000`,
   ключ-заглушка `e2e-mock`, модель `e2e-small`.
4. Что умеет сценарий `core.json` (правило выбирается первым совпадением `match`):

   | Триггер в тексте пользователя | Ответ мока | Проверяет |
   |---|---|---|
   | `ping` | `pong: мок-модель отвечает` | базовый ход, usage |
   | `stream` | 5 потоковых кусков с паузой 0.35 с | стриминг и частичную отрисовку |
   | `инструмент` | tool call `read_file {"path":"README.md"}` | чтение без подтверждения, второй ход |
   | `запиши файл` | tool call `write_file` для `e2e-permission.txt` | подтверждение/отказ в режиме «Спрашивать» |
   | (после последнего сообщения пользователя есть роль `tool`) | `Инструмент отработал…` | завершение цикла инструмента |
   | `отмена` | ответ через 40 с | отмену хода и разрыв соединения |
   | `ошибка сервера` | HTTP 500 | обработку ошибки провайдера |
   | `429` | HTTP 429 rate limit | ретраи/сообщение о лимите |
   | второй запрос (`callIndex: 1`) | отдельный текст | историю диалога в запросе |

   `contains`/`regex` проверяют последнее сообщение пользователя; прошлые ходы и системные инструкции
   не активируют триггеры. Результат инструмента учитывается только в текущем ходе.
   Свои правила добавляй в копию сценария (например `build\e2e\scenario.json`): поля `label`, `match`
   (`model`, `contains`, `regex`, `callIndex`, `hasToolResult`, `requiresTools`), `kind`
   (`text`/`tool_call`/`error`/`delay`/`empty`), `text` или `chunks`, `streamDelay`, `tool`+`arguments`,
   `status`+`message`, `seconds`, `usage`. Файл сценария не редактируй на месте, если прогон идёт.
5. Доказательства и отладка: `GET /__e2e/requests` возвращает всё, что приложение реально отправило
   (модель, stream, tools, роль сообщений, какое правило сработало); `GET /__e2e/health` — состояние мока;
   `POST /__e2e/reset` — сброс журнала и счётчика перед сценарием, где важен `callIndex`.
   Ключи в журнал не пишутся (только факт наличия `Authorization`).
6. Режим `--real-model` (только по явной просьбе): используй боевое подключение профиля, фиксируй расход
   и не проверяй точные тексты ответов — такие сценарии дают `PASS` по факту завершения хода без ошибок.
7. Ограничение мока: реализован только OpenAI-совместимый протокол. Anthropic-wire (`/v1/messages`) и
   нативные CLI-движки (Claude Code, Codex, ACP) моком не покрываются: их проверяй как «корректный
   `Unavailable`/понятная ошибка подключения» либо с настоящим CLI, если он установлен (S2.14).

## 4. Запуск приложения и привязка к окну

1. Сохрани список `window_list` до запуска. Запусти E2E-экземпляр с окружением §2 и сохрани PID
   (Windows — `Start-Process -FilePath <exe> -PassThru` в дочернем PowerShell; macOS — прямой запуск):

   ```bash
   env HOME="$e2e_home" JAVA_TOOL_OPTIONS="$e2e_jvm_options" HEARTBEAT_TRACE=true \
     platform-main/desktop/build/compose/binaries/main-release/app/HeartbeatE2E.app/Contents/MacOS/HeartbeatE2E &
   e2e_pid=$!
   ```

   Не используй `open`: окружение должно попасть прямо в launcher. Убедись, что новые данные и логи
   появляются в изолированном корне. Все повторные запуски используют то же окружение.
2. Дождись нового `windowId` в `window_list` по сравнению со списком до запуска, сверь `application`
   и заголовок `Heartbeat`, затем `window_capture {windowId, clientAreaOnly: true}`. Заголовок совпадает
   с основным приложением; `HeartbeatE2E` — имя бинаря, не окна. `window_list` не возвращает PID.
   Если новых подходящих окон несколько, установи владельца нативными средствами ОС и сопоставь
   с сохранённым PID; не выбирай случайное окно. PID используй также для проверки завершения процесса.
   Нет окна за 60–90 с — читай логи корня, проверяй процесс; это блокер S0.1.
3. Работай семейством `window_*` по навыку `computer-use`:
   - окно E2E-приложения захватывать **можно** (`isSelfOwned` определяется по PID — это другой процесс);
     окно того Heartbeat, в котором живёт агент, захватить нельзя (`SelfCaptureNotAllowed`) — не пытайся;
   - ROI по области окна, чтобы кадры были крупнее; мелкий текст читай `_zoom` по ROI или тайлу;
   - после каждого действия — свежий снимок; для анимаций используй `_record {observeMs, untilStable}`
     вместо серии снимков; координаты ввода — пиксели последнего полученного кадра (`space: preview`);
   - отказы `StaleFrame`/`TargetResized` — сделай новый снимок и повтори действие.
4. Ввод текста: на Windows `window_type` передаёт точные символы независимо от раскладки; на macOS — только
   US ASCII, поэтому русский текст вставляй через буфер (`pbcopy` + `cmd,v`), а не набором.
5. Не жди фиксированными паузами: состояние проверяй снимком или `_record` с `untilStable`.
6. Не трогай другие окна и приложения, не нажимай деструктивные связки (`alt+f4` в чужом окне, `cmd+shift+esc`),
   не сворачивай окно агента. По завершении — `window_release`.

## 5. Прогон сценариев

1. Открой `scenarios.md` (рядом с этим файлом) и иди по уровню прогона: S0 → S1 → S2.
   Аргумент `--only <id,…>` ограничивает прогон перечисленными сценариями (плюс S0.1–S0.2 как минимум).
2. Перед каждым сценарием, где важен порядок запросов, делай `POST /__e2e/reset`.
3. На каждый сценарий фиксируй: вердикт, конкретику увиденного (тексты и состояния элементов),
   запись из журнала мока, при `FAIL` — выдержку лога приложения и уровень дефекта.
   Скриншоты остаются в диалоге как доказательство; в отчёт переноси их текстовое описание и ID сценария.
4. `FAIL` не останавливает прогон, кроме блокера: при блокер-дефекте все зависимые сценарии помечай
   `BLOCKED` с указанием причины и переходи к §7 немедленно.
5. Локализуй дефект до фикса: лог-фрагмент + журнал мока + KDoc/api-машина фичи + карта модулей в `CLAUDE.md`.
   Это ускоряет фикс и не даёт «починить симптом» в UI-слое.

## 6. Триаж дефектов

| Уровень | Критерий | Примеры | Куда идёт |
|---|---|---|---|
| **Blocker** | Приложение непригодно или теряет данные | не стартует, нет окна, падение при открытии раздела, основной сценарий чата не работает, зависание при выходе, секрет/ключ виден в UI или логе | немедленно в фикс (§7) |
| **Critical** | Основная функция работает неверно | ответ не доходит до ленты, отмена не отменяет, история не восстанавливается после перезапуска, настройки не сохраняются, изменяющий tool call обходит подтверждение в режиме «Спрашивать», регрессия против прошлого прогона | немедленно в фикс (§7) |
| **Minor** | Не блокирует сценарий | косметика, кривой текст, несогласованные отступы/иконки, неудачная подсказка | в пакетный PR в конце (§8) |
| **Tech debt** | Не дефект этого прогона | хрупкое место, отсутствие автоматизации, «переделать бы» | в issues (§8) |

Правила:

- Спорный уровень решай по худшему варианту (Critical) и отмечай сомнение в отчёте; не блокируй прогон
  вопросами о классификации.
- Один дефект — одна запись по шаблону:

  ```
  E2E-<NN> | уровень | сценарий S<x.y> | версия: <SHA>, ОС, артефакт
  Шаги: 1) … 2) … 3) …
  Ожидалось: …
  Фактически: … (что видно на снимке, текст ошибки)
  Воспроизводимость: всегда / N из M
  Доказательства: журнал мока #<index>, выдержка лога, описание снимка
  Подозрение: <модуль/слой> — <почему>
  ```

- Несколько проявлений одной причины — один дефект и один PR; разные причины — разные дефекты и PR.
- Отличай дефект от артефакта мока: если поведение объясняется правилом сценария (например текст не тот,
  потому что сработало другое правило) — это не дефект приложения; поправь сценарий и повтори.

## 7. Blocker и Critical — чинить сразу

1. `$open-pr <описание дефекта>` (Codex) / `/open-pr` (Claude) — ветка от актуального `origin/master`,
   draft PR, шаги-коммиты; описание PR сразу содержит шаблон дефекта из §6.
2. Воспроизведи дефект на уровне кода: найди причину по логу/журналу мока/KDoc, напиши **падающий тест**
   (`commonTest`, а для десктоп-специфики `jvmTest`; правила — `.claude/rules/tests.md`), затем фикс.
   Тест обязателен: без него регрессия вернётся, а ревью нечем подтвердить. Фикс, меняющий раскладку UI, а не
   возвращающий задуманное, требует макета и согласования (скилл `ui-prototype` §0) — остановись и спроси. Прогони навык `verify`
   (сборка затронутых модулей, тесты, detekt, `check_commit_size.py`).
3. `$pr-review-and-fix <N>` (Codex) / `/pr-review-and-fix <N>` (Claude) — цикл ревью и правок до
   `/reviewed <sha>` без блокеров.
4. Merge: `gh pr merge <N> --squash --delete-branch` — только если есть approve бота (после `/reviewed`)
   и зелёная commit policy. Approve нет — не мерджь, сообщи пользователю и жди.
5. Обнови `master` (`git switch master; git pull --ff-only`) и пересобери артефакт (§1).
6. Повтори прогон: упавший сценарий + S0 (smoke) + соседние сценарии той же фичи; при `full`-прогоне —
   продолжай с того места, где остановился, не начиная сначала прошедшие `PASS`.
7. Запиши в отчёт связку: дефект → PR → SHA фикса → вердикт повторного прогона.
8. Цикл «фикс → merge → пересборка → повтор» повторяй не более 3 раз подряд для одного сценария;
   после третьей неудачи остановись и доложи пользователю с анализом (возможно, дефект глубже).

## 8. Minor — пакетом, tech debt — в issues

1. Минорные дефекты копи весь прогон, не прерывая его. В конце — один draft PR пакетом:
   `$open-pr` со списком дефектов; каждый дефект — отдельный коммит-шаг, с тестом там, где поведение
   проверяемо (косметику без теста не «тестируй» фиктивно). Затем `pr-review-and-fix` → merge →
   пересборка → повторный прогон только затронутых сценариев.
2. Tech debt оформляй issue по одному наблюдению:

   ```powershell
   # Windows: не-ASCII только через UTF-8 файл в gitignored build/
   gh issue list --search <ключевые слова>   # сначала проверь дубликаты
   gh issue create --title (Get-Content build\e2e\issue-title.txt -Raw -Encoding UTF8).Trim() --body-file build\e2e\issue-1.md
   ```

   ```bash
   # macOS
   gh issue create --title "$(cat build/e2e/issue-title.txt)" --body-file build/e2e/issue-1.md
   ```

   В теле: контекст прогона (SHA, ОС, сценарий), наблюдение, почему это долг, предлагаемое направление.
   Метки — только существующие (`gh label list`); новые не создавай.
3. Если минор на самом деле критичен (например «кривой текст» — это потерянное сообщение об ошибке),
   переклассифицируй и чини по §7.

## 9. Завершение, отчёт, уборка

1. Заверши E2E-приложение явной командой «Выход»/Quit в меню или tray и проверь сохранённый PID.
   Крестик при наличии tray только скрывает окно — это штатное поведение, не завершение.
   Останови мок-сервер по его PID.
   `window_release` (и `ex_control_release`, если открывал свои вкладки).
2. Восстанови всё, что менял вне изолированного корня (Native Messaging — §2.4).
3. Изолированный корень удали, если пользователь не попросил `--keep-data`; при наличии нерешённых
   дефектов оставь и укажи путь в отчёте (логи нужны для разбора).
4. Отчёт положи в gitignored `output/e2e/<дата>-<короткий-sha>/report.md`:
   - версия под тестом: SHA, ветка, ОС, команда сборки, путь к артефакту, режим модели;
   - окружение прогона: монитор/масштаб, уровень доверия, какие права выдавались, длительность;
   - таблица сценариев: ID, вердикт, что увидели, доказательства;
   - дефекты: уровень, судьба (PR + SHA + вердикт повтора / пакетный PR / issue / остался открытым);
   - что не проверено и почему (`SKIPPED`/`BLOCKED`), известные ограничения мока;
   - вывод: готово к релизу / не готово (с перечнем блокеров);
   - следы прогона: какие временные файлы и каталоги созданы, что удалено.
5. Релиз не запускай: решение о `release.yml` принимает пользователь.

## Отказы среды: что делать

- **Windows, PowerShell 5.1:** `python`/`python3` — заглушки Store, настоящий интерпретатор `py -3`;
  `&&` не работает — используй `;`; двойные кавычки в команде вырезаются — только одинарные;
  не-ASCII аргументы передавай из UTF-8-файлов в gitignored `build/`; для чтения кириллицы в выводе —
  `[Console]::OutputEncoding=[System.Text.Encoding]::UTF8`.
- **`Invoke-WebRequest` в неинтерактивной оболочке** требует `-UseBasicParsing`.
- **`git push` / `gh pr create` отклонены safety-проверкой хоста** — механизм обхода из чата отсутствует:
  попроси пользователя выполнить точные команды в своём терминале, затем продолжай. Ретраи бесполезны.
- **`localGitEvidence unavailable`** при `git add`/`git commit` — подготовь всё локально (правки, тесты,
  detekt, сообщения коммитов в `build/pr/*.txt`) и передай пользователю готовые команды
  `git add -- <пути>` / `git commit -F build/pr/stepN.txt` / `git push`.
- **Сборка не влезает в таймаут** — запускай фоново (см. §1.2), а не увеличивай таймаут до бессмысленного.
- **macOS:** после выдачи прав Screen Recording/Accessibility приложение нужно перезапустить;
  `window_type` не вводит не-ASCII — используй буфер обмена.
- **Приложение не стартует молча** — читай `%LOCALAPPDATA%\Aequicor\Heartbeat\logs` (Windows) /
  `~/Library/Logs/Heartbeat` (macOS) внутри изолированного корня и проверь lock-файл: чаще всего
  E2E-экземпляр запустили без изоляции и он передал активацию установленному Heartbeat.
