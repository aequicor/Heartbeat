# Прототип UI: `$ARGUMENTS`

Справочник — [design/README.md](../../../design/README.md): иерархия файлов и кадров (раздел 2), правила JSON (4.4),
таблица переноса в Compose (4.5). Здесь — исполнимая последовательность.

## 0. Нужен ли этап

Обязателен для нового экрана, режима, диалога, флоу, нового или изменённого `Hb*`-компонента, заметного изменения
раскладки, нового перехода или анимации. Без него — логика без визуального эффекта, тексты, багфикс до уже
согласованного макета, значение токена (тогда обнови переменную в `design/system/heartbeat.lib.pen`),
исправление дефекта e2e, возвращающее задуманное поведение. У экрана нет `.pen` — макет только затронутых экранов
и состояний. Сомневаешься — делай макет. pen.dev или снимок окна недоступны (Linux, Codex без снимка) — этап не
пропускается: скажи пользователю, что картинку не видел, и попроси проверить кадры до согласования.

## 1. Контекст

1. `.claude/rules/design-system.md` — принципы эталона: плотность, типографика, тихие состояния, режимы вместо экранов.
2. `design/system/heartbeat.lib.pen` и `design/features/<feature>/` — если есть.
3. Определи доступные инструменты текущего движка и хоста, не предполагая, что у всех движков Heartbeat одинаковый MCP.
   Если доступен MCP pen.dev, проверь активный документ и прочитай актуальное состояние холста через его инструменты;
   перед правкой узла перечитай его. Несохранённые правки пользователя на холсте авторитетны. Проверь путь рабочей
   копии и не подменяй документ одноимённым файлом из другого worktree.
4. При доступном MCP pen.dev используй его для правки открытого документа: изучи предоставленные сервером инструкции
   и схему, соблюдай правила проекта ниже. Все операции с pen.dev выполняй через MCP: чтение, правки, навигацию,
   снимки и сохранение. При работающем MCP не используй computer-use, даже для Ctrl+S, проверки вкладки или снимка
   окна; не меняй одновременно тот же файл напрямую на диске. Если нужной операции нет, проверь документацию
   сервера, затем сообщи об ограничении; при необходимости попроси пользователя сохранить документ. Не подменяй
   отсутствующую операцию вводом через computer-use. Проверь сохранённый результат до коммита; не предполагай
   автосохранение и не называй документ сохранённым без подтверждения.
5. Если MCP недоступен у текущего движка, используй поддерживаемый им способ работы с файлом и правила README 4.4.
   Перед прямой правкой перечитай файл с диска и сохрани пользовательские правки открытой вкладки; после правки
   закрой и открой вкладку заново без сохранения устаревшего содержимого. Не уничтожай несохранённые правки.

## 2. Макет

- Файл `design/features/<feature>/<feature>.pen`: область «Экраны» (форм-фактор × светлая/тёмная тема, серая обводка кадров)
  и справа от неё «Пользовательские пути» (только Desktop, светлая тема, без обводки); фон прозрачный, компонентов
  в файле нет — они в `design-system.pen`; `id` без `/`; каждый экран, включая тёмный и кадры путей, — самостоятельная
  отсоединённая копия с собственной темой и уникальными `id`, не `ref`; `width`/`height`
  без `$`-переменных (README 4.4).
- **Desktop-first**: сначала Desktop-кадры, после согласования — Tablet и Phone как их адаптации; кадры на **всех
  форм-факторах** `<Screen> / <State> / Phone` (390×844), `/ Tablet` (834×1112), `/ Desktop` (1280×800), при отличиях
  `/ Desktop compact` (420) — README 2.5; `hb:host` = `mobile` для Phone и Tablet, `desktop` для Desktop;
  Desktop-only фича — только Desktop с причиной в `Context` экрана.
- **Стрелки переходов** (README 2.3): начинаются на компоненте-триггере, заканчиваются на компоненте следующего кадра
  (конец не выделяется) или на левой границе кадра, если меняется весь экран; идут **под кадрами**, не поверх их
  контента; скруглённые углы, прозрачность 0,65; подпись — 1–2 строки мелким шрифтом над горизонтальным участком,
  подробности — в `Context` триггера. Элемент, который нужно выделить или описать его состояния, — **карточка под
  экраном** (столбцом, левее элемент — выше) со стрелкой от элемента. Основной цвет `annotation.accent`,
  пересекающиеся стрелки — разных цветов `annotation.accent2…4`.
- Составные компоненты на экране — копия структуры из `heartbeat.lib.pen` (не `ref`: внутри экземпляра нельзя двигать мышью); `ref` — иконки, иллюстрации, разделитель; токены — `$`-переменные библиотеки. Чего нет — сначала компонент или предложение токена
  (`proposal.<name>` + пояснение в `Context`) в библиотеке. Адресация через алиас: `"ref": "hb:<id>"`, `"$hb:<переменная>"`,
  `"theme": {"hb:mode": "dark", "hb:host": "desktop"}` (README 2.4); иконки — только `ref` на `hb:hb-icon-*`, шрифт —
  `$hb:typography.family`; справочник стилей и компонентов — `design/system/design-system.pen`, образцы —
  `design/features/*`.
- Светлые, тёмные и повторённые в путях экраны редактируются независимо: при изменении экрана синхронизируй все его
  копии вручную, сохраняя их тему, положение и уникальные идентификаторы. Проверь, что внутрь каждого кадра можно
  добавлять и перемещать слои, а не только менять свойства экземпляра.
- Текст, который может не поместиться в одну строку, — затухание к краю, не обрыв и не многоточие: строка `clip` + градиент
  `effects.fade.<поверхность>` → `surfaces.<поверхность>` (README 2.4, «Эффекты»).
- Описание поведения — в поле `Context` компонента: границы `720` и `1200` (сайдбар → drawer, список → раздел,
  панели), растяжение, прокрутка. Пояснения для просмотра на холсте оформляй по правилам комментариев ниже.
- Все видимые состояния отдельными кадрами: пустое, загрузка, ошибка, длинный русский текст, значимые hover/selected/
  disabled/фокус. Переход — стрелка в «Пользовательских путях» с описанием, тип — в `Context` (`trigger / transition`);
  микро-анимация — в `Context` узла (`trigger / duration / easing / reduced`, README 2.3).
- Все способы правки — по README 4.4: `version` и чужие узлы не трогать, `id` стабильные, раскладка свободная (`layout: none`,
  `x`/`y`), поведение при растяжении, прокрутке и других размерах — в `Context` компонента.

### Правила добавления комментариев

1. Поверх компонента размести отдельный бейдж с номером, связывающим его с пояснением. Бейдж — аннотация макета,
   а не часть интерфейса приложения; не заслоняй им существенный текст и элементы управления.
2. Под макетом того же экрана размести `sticky-note` с тем же номером и пояснением. При нескольких комментариях
   используй разные номера и размещай заметки под экраном так, чтобы они не перекрывали друг друга и соседние кадры.
3. Бейдж и заметка — сохраняемые в `.pen` узлы; текст должен оставаться доступен после открытия файла. Содержательное
   поведение компонента также записывай в его `Context`. Облачные комментарии pen.dev не заменяют заметки в файле.

## 3. Посмотри сам

При работающем MCP осмотри каждый изменённый кадр его визуальным инструментом. Снимок окна через computer-use —
запасной способ только при недоступном MCP (README 4.3). После прямой правки файла сначала безопасно переоткрой
вкладку. Проверь размеры и привязки, исправь перекрытия, обрезанный текст и неровные отступы. Не утверждай, что
макет проверен визуально, если инструмента снимка нет; попроси пользователя проверить его до согласования (§0).

## 4. Согласование

1. Коммит `design(<feature>): макет <что>` (в draft PR — отдельный шаг по `open-pr`).
2. Пользователю: путь к файлу, список кадров, решения и открытые вопросы одним сообщением. Жди явного «согласовано».
3. Правки словами — внеси, проверь снимком, покажи снова. Правки руками в pen.dev — перечитай файл, закоммить
   `design(<feature>): правки пользователя`, учти в реализации.
4. В описании PR — раздел «Дизайн» (шаблон `open-pr`): файл, кадры, SHA согласованного коммита, кто и когда
   согласовал; после переписывания истории SHA обнови.

Без согласования UI-код не пиши: `pr-review` считает это блокером.

## 5. Реализация и сверка

1. Перенос по таблице README 4.5: переменные → `HbTheme.*`, `ref` → `Hb*`, кадры-состояния → состояния стора
   и `@Preview`, раскадровки → `NavTransition` и `HbTheme.motion`. Число без переменной — сначала токен с KDoc.
2. Сверка: снимок desktop (`./gradlew :platform-main:desktop:run`) или рендер превью jvmTest рядом с кадрами pen.dev.
   Ошибка — правь код; сознательное расхождение — правь макет отдельным коммитом и перечисли в разделе «Дизайн».
3. Макет живой: любые следующие UI-правки этого экрана меняют `.pen` в том же PR.
