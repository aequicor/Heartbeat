# Прототип UI: `$ARGUMENTS`

Справочник — [design/README.md](../../../design/README.md): иерархия файлов и кадров (раздел 2), правила JSON (4.4),
таблица переноса в Compose (4.5). Здесь — исполнимая последовательность.

## 0. Нужен ли этап

Обязателен для нового экрана, режима, диалога, флоу, нового или изменённого `Hb*`-компонента, заметного изменения
раскладки, нового перехода или анимации. Без него — логика без визуального эффекта, тексты, багфикс до уже
согласованного макета, значение токена (тогда обнови переменную в `design/system/heartbeat.lib.pen`).
Сомневаешься — делай макет. pen.dev или снимок окна недоступны — не пропускай этап, спроси пользователя.

## 1. Контекст

1. `.claude/rules/design-system.md` — принципы эталона: плотность, типографика, тихие состояния, режимы вместо экранов.
2. `design/system/heartbeat.lib.pen` и `design/features/<feature>/` — если есть.
3. `.pen` перечитывай с диска перед каждой правкой: пользователь мог поправить его в pen.dev, его правки авторитетны.

## 2. Макет

- Файл `design/features/<feature>/<feature>.pen`, секции `Screens` / `Components` / `Transitions` / `Notes`,
  кадры `<Screen> / <State>` в размере хоста (desktop 1280×800 и ширина 420).
- Только `ref` на компоненты и `$`-переменные библиотеки. Чего нет — сначала компонент или предложение токена
  (`proposal.<name>` + заметка) в библиотеке.
- Все видимые состояния отдельными кадрами: пустое, загрузка, ошибка, длинный русский текст, значимые hover/selected/
  disabled/фокус. Переходы — раскадровка и заметка `trigger / transition / duration / easing / reduced`.
- Правки JSON — по README 4.4: `version` и чужие узлы не трогать, `id` стабильные, разметка flex-полями.

## 3. Посмотри сам

Открой файл в pen.dev и сними окно приложения: Claude Code desktop — computer-use по окну pen.dev; Heartbeat —
`window_list` → `window_capture`/`window_zoom` (скилл `computer-use`). Приблизь каждый изменённый кадр, исправь
перекрытия, обрезанный текст, неровные отступы, лишние элементы. Файл не открылся — откати правку и сделай её
меньшими шагами. На Linux снимка нет — так и скажи пользователю.

## 4. Согласование

1. Коммит `design(<feature>): макет <что>` (в draft PR — отдельный шаг по `open-pr`).
2. Пользователю: путь к файлу, список кадров, решения и открытые вопросы одним сообщением. Жди явного «согласовано».
3. Правки словами — внеси, проверь снимком, покажи снова. Правки руками в pen.dev — перечитай файл, закоммить
   `design(<feature>): правки пользователя`, учти в реализации.
4. В описании PR — раздел «Дизайн»: файл, кадры, SHA согласованного коммита, кто и когда согласовал.

Без согласования UI-код не пиши: `pr-review` считает это блокером.

## 5. Реализация и сверка

1. Перенос по таблице README 4.5: переменные → `HbTheme.*`, `ref` → `Hb*`, кадры-состояния → состояния стора
   и `@Preview`, раскадровки → `NavTransition` и `HbTheme.motion`. Число без переменной — сначала токен с KDoc.
2. Сверка: снимок desktop (`./gradlew :platform-main:desktop:run`) или рендер превью jvmTest рядом с кадрами pen.dev.
   Ошибка — правь код; сознательное расхождение — правь макет отдельным коммитом и перечисли в разделе «Дизайн».
3. Макет живой: любые следующие UI-правки этого экрана меняют `.pen` в том же PR.
